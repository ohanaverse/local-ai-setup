# LiteLLM aliases and groups (phase 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A registry alias (`alias/<name>`, one or more ordered targets) becomes a set of LiteLLM database rows that wt-model keeps in step with the targets' liveness; a claude slot profile, pi or codex can name the alias; `wt-model alias set` re-points it with no gap and no restart; a group falls back across targets in priority order; the window an alias advertises is the smallest of its targets' windows, and models can carry a window of their own (#596, #626).

**Architecture:** `registry.toml` gains a top-level `[[aliases]]` array (never model rows) and an optional `context_window` on `[[models]]`. `internal/litellm` turns each alias into one database row per live target (model_name = alias id, the target's own `litellm_params` plus `order`), under a separate `wta:alias/` id space and a separate `wt_alias_managed` marker that the phase 1 model-row path (and any phase 1 binary) never sees, written add-first and deleting superseded rows only once the new ones are confirmed listed, so a re-point has no gap. The model server synthesizes one catalog row per alias from its targets' rows (state, action, location, min window) and counts a client session on an alias as use of the alias's local target. Sessions need no registry or route knowledge: the alias id is just another catalog row id and gateway id.

**Tech Stack:** Go 1.26.7 (`wt/` module), `github.com/BurntSushi/toml` and `internal/tomlw` (registry), `httptest` (fake proxy), LiteLLM 1.109.1 `/model/new`, `/model/delete`, `/model/info` (no `/model/{id}/update`).

**Spec:** `docs/superpowers/specs/2026-11-22-litellm-aliases-groups-design.md` (Approach A, phase 2; decisions 1 and 4). Builds on `docs/superpowers/plans/2026-11-22-litellm-db-routes-phase1.md` (shipped, PR #684).

## Global Constraints

Derived from the spec's "Constraints and risks" and "Design of A" (paraphrased, not quoted) plus phase 1's shipped rules.

- Alias ids are `alias/<name>`, `<name>` matching `^[a-z0-9][a-z0-9.-]*$`; the provider id `alias` and any model id starting `alias/` are refused by registry validation (reader and writer).
- An alias id never equals a model id: both are LiteLLM `model_name`s, gateway ids and catalog row ids.
- Registry writes go only through `config.UpdateRegistry` with a pure apply; validation stays touched-rows-only, extended by two alias rules: a model an alias targets cannot be removed, and a write touching a model (or its provider) re-checks every alias that targets it (`config.AliasFault`).
- Alias database rows: `model_info.id` starts `wta:alias/`, `model_info.wt_alias_managed: true` and **no** `wt_managed` key, `model_info.wt_alias: <alias id>`, `model_info.wt_alias_target: <registry model id>`, plus the stamped `wt_params_sha`. Phase 1's predicates (`isManagedDB && HasPrefix(id, "wt:")` in `owned`, `routeRows`, `PlanDB`, `AdminClient.Routes`, the foreign-id warning, and `ApplyDB`'s `wt:` id guard) therefore exclude them in this binary and in every shipped phase 1 binary; the alias path never sees any other row.
- Alias rows are never written to `config.yaml` and never cost a restart (spec constraint 7: aliases and groups live in the database, expressed with `order`; `wt-model litellm sync` leaves rows it does not own alone). When the database half is unavailable the registry write still happens and one warning names the reason and the repair; nothing falls back to the file.
- Every alias API call runs inside the existing `config.yaml` flock under the write's one 15 s deadline (`dbRoutes.context()`), after the model rows (phase 1 `route()`), in the same `Sync`/`ApplyChange` call, and plans from a registry re-read inside that lock (never the caller's possibly stale `cfg`). A duplicate `/model/new` is HTTP 500: convergence is by re-list and the stamped `wt_params_sha` (`addConverged`), never by error text.
- Wire changes are additive within `modelapi.SchemaVersion = 2` (the client checks equality); every new JSON key reaches its fixture in the same commit: `docs/contracts/model-api.sample.json`, `docs/contracts/model-list.server.sample.json` (`wt model list --server --json`), `docs/contracts/litellm-cli.sample.json`, `docs/contracts/registry.sample.toml` / `registry.written.sample.toml`, new `docs/contracts/alias-list.sample.json`. `docs/contracts/model-list.sample.json` (modeltiers') does not change (aliases are not inventory; modeltiers never sees them).
- No printed or JSON output carries an alias row's `litellm_params` (a cloud target's row holds its resolved key): ids, targets, orders and `h8` only.
- A window is declared only when known: an alias's window is the minimum over all its targets and is withheld when any target's window is unknown.
- Tests stay off the machine (`wt/CLAUDE.md` "Go tests"): fake proxy via `httptest`, scratch `WT_REGISTRY` plus `WT_LITELLM_CONFIG`, per-call seams on `host`, no new package vars; every `Test*` has a what-and-why comment.
- Import graph ratchet (`internal/depcheck`): alias admin logic in `config`, `modeladmin`, `litellm`, `modelserver`, `cloudsync`; session libraries (`catalog`, `agents`, `profiles`, `slotedit`, `tui`) read only `modelapi` fields. No allow-list entry is added.
- User text says "client session(s)" (style N7), stderr lines are `wt-model: note:`/`wt-model: warning:` for new code (route-sync warnings keep `SyncAndWarn`'s existing unprefixed form; not changed here).
- Guides embed no live aliases or windows; they show `wt-model alias list`.
- PR body says `Refs #596` and `Refs #626`, never a closing keyword; `make pre-pr` in the background before the PR; commit trailer is the attribution line the session's system reminder gives.

## Plan decisions

Each one is binding for this plan; "if wrong" is what reversing it later costs.

1. **Registry schema: a top-level `[[aliases]]` array, not flagged model rows.** `id` and `targets = [{ model = "<registry id>", order = N }, ...]`. `order` is optional; omitted means the target's 1-based position. No other keys in v1 (reserved: `notes`). Rules (`config.AliasFault`): at least one target; no duplicate target; every target names exactly one model row; no alias-to-alias targets; no native target; **at most one local target per alias** (keeps `/start` single-model and matches the slot-profile rule). *Why:* every one of the ~29 `range cfg.Models` loops, cloud-sync, modeltiers and llmbench would otherwise have to learn to skip a flagged row; a separate table is ignored by the typed reader and llmbench for free. *If wrong:* a schema migration of `[[aliases]]` into another shape is one `UpdateRegistry` rewrite; the one-local-target rule can be lifted later by a multi-model start job. *Cost now:* an older installed `wt-model` refuses every registry write once `[[aliases]]` exists (`ErrRegistryTopLevel`, #247), and an older binary (including a still-running serve LaunchAgent) ignores alias rows entirely: it neither deletes them nor adds or removes them as targets start and stop. The docs say `make install` and a serve restart before the first `alias set`.
2. **Database row ids: `wta:alias/<name>/<h8>/<target id>`**, `h8` the first 8 hex of the row's `routeHash` (model_name plus `litellm_params`, `order` included). Uses only characters phase 1 ids already use, and does not start with phase 1's `wt:` prefix, so no shipped predicate or `ApplyDB` guard matches it (downgrade included). Every content change is a new id, so a re-point is Add plus Delete (never Update), applied per alias as **Adds, then a confirming re-list, then the Deletes**, and the Deletes of an alias run only when every one of its Adds is confirmed listed with its hash; on any Add or confirm failure the old rows stay (two generations briefly coexisting beats none) and one warning says the next sync converges. The old and new row share the name for the moments between, which LiteLLM load-balances; accepted. An id match whose stored row is not `IsAliasDB` or fails `hashMatches` (edited outside wt, e.g. the LiteLLM UI) is replaced Delete-then-Add: that one row is already wrong, so its gap is acceptable. Equal `order` across targets is written as is and load-balances (LiteLLM deployment `order`); this is the design's claim and is checked in the live check, not only in tests. *Rejected:* stable ids plus `PATCH /model/{id}/update` (measured 40 ms in the spike) because wt has no PATCH client and phase 1 found the update endpoint not idempotent for params; reusing `wt:`/`wt_managed` because every phase 1 binary would delete the rows. *If wrong:* switching to PATCH changes only `PlanAliasDB`/`ApplyAliasDB`; ids are not stored anywhere else.
3. **A target that is not live gets no row; a target in doubt keeps its row.** Live = a local target that is routed after this write's model half, or a cloud target whose row builds. A cloud target whose row fails to build (`prepareModel` error, e.g. `secret_ref` unset in serve's launchd environment) is *frozen*, not dead: its existing rows stay, nothing is added, one warning names it. A frozen target (`Options.Untouched`/`UntouchedFamilies`) is the same. The freeze holds only while the (alias, target) pair is still configured: a row whose alias is gone or whose target was dropped from the alias is deleted whatever the freeze. A malformed alias, or one `AliasFault` rejects, is frozen whole (rows matched by `wt_alias`; neither added nor deleted; one warning naming the fault). An alias with no live and no frozen target has no rows: LiteLLM answers its unknown-model error, the sync outcome is `unrouted` and a warning says `alias/<x> has no live target`. *Why:* a row for a dead local `api_base` at order 1 adds a failed attempt to every request, while a deleted row for a merely unresolvable key unroutes sessions over an environment difference. *If wrong:* adding a "keep the lowest-order row" mode is local to `DBModelsFromAlias`.
4. **Database half unavailable (no admin client, `store_model_in_db` off, list failed, deadline hit): no file fallback.** The registry write stands; the sync prints one warning `alias routes unavailable (<reason>); registry written, LiteLLM not updated; run 'wt-model litellm sync' when the proxy answers`; existing alias rows in Postgres are left alone (they survive proxy restarts); the catalog row is `block` with that reason when the alias id is not in `/v1/models`. The repair is any full `Sync` (`wt-model litellm sync`, serve's start sync); `alias set` still exits 0. *Why:* a file alias would cost a restart per target start/stop, cannot be re-pointed hot, and becomes a twin the moment the database is back. *If wrong:* a file mode would need its own twin cleanup; nothing in this plan precludes it; a distinct exit code for a partial apply can be added to `alias set` alone.
5. **Catalog and wire shape (additive).** `modelapi.Row` gains `Kind string` (`json:"kind,omitempty"`, `"alias"` for alias rows) and `Targets []AliasTarget` (`json:"targets,omitempty"`; `AliasTarget{ID string; Order int; ProviderID, Location, State string; Context int}`). Alias row: `ID = GatewayID = alias id`, `ProviderID = "alias"`, `Family = "alias"`, `ModelName = <name>` (claude's `_NAME` label), `Registered = true`, `Order` after the registry models, tier copied from the lowest-order target (lowest tier among equal-order ones), no price. **Location** = `local` only when the lowest-order level contains the alias's local target, else `cloud`: a cloud-first group with a local fallback launches as a cloud model (no local-model profile prompt, cloud smoke timeout, `ResolveSlotProfileWire` label by location). **State**: with Location `local`, the local target's state; else `running` when any target is servable, `stopped` when none is but the local target can start, else `blocked`. **Action**, in order: lowest-order level holds a local target whose action is `start`, or holds a running local target while the alias id is not routed → `start` (an alias `/start` re-runs the target's route write, which adds the alias's rows; this keeps `catalog.NeedsStart` and the action in agreement); else any target servable and the alias id routed → `launch`; any target servable but the alias not routed → `block` "alias/x is not routed on the host (`wt-model litellm sync`)"; any target `start` → `start`; else `block` joining the targets' reasons. Old clients see an ordinary row and still launch it. *If wrong:* the policy is one pure function (`aliasAction`) with a table test.
6. **Context window rule, computed on the server.** A model's window is its registry `context_window` when set (any location; #626), else its tiers `context` when `context_basis = "host"` and the model resolves (`cfg.ResolveLocation`, provider row included) to cloud, as today. An alias's window is the minimum over **all** configured targets, withheld (0) when any target is unknown. Computed by one helper (`windows.Alias`) used by the catalog and by `alias set`'s shrink guard; sent in `Row.Context`; `catalog.ToModel` copies `Context` to `HostContext` for any row (the server now sends a local row's context only from the registry). Claude's existing strict/slot rules (`claudeWindow`, `claudeSlotWindow`) then apply unchanged. *If wrong (too strict):* lenient min-over-known is a one-line change in the helper, but over-declaring makes Claude compact too late, which is worse than the 200K default.
7. **Shrink guard on `alias set`:** a set whose new window is smaller than the old known window, or unknown where the old was known, asks y/N on a terminal (default No) and without one refuses, exit 3: `approval missing: pass --accept-smaller-window (there is no terminal to ask); nothing was changed`. The message names the number of client sessions using the alias when serve's runtime record answers (running sessions keep the window they launched with).
8. **Rename is deferred** (more than two tasks: persistent redirect state that outlives a server restart, plus slot profiles that live on the session machine and are written only by `wt`). Phase 2 documents the manual sequence: `alias set alias/new ...`, `wt profile slots set` on each session machine, later `alias rm alias/old` (guarded by the in-use check). The spec's taken decision 4 asks for a redirecting `rename`; deferring it is listed under "Unresolved for the owner". *If wrong:* nothing in phase 2 blocks a later `rename`; the row id scheme already contains the name.
9. **Command shape:** `wt-model alias list [--json]`, `wt-model alias set <alias/name> --target ID[:ORDER]... [--accept-smaller-window] [--dry-run]` (replaces the whole target list; prints `set alias: <id>` or `no change: <id>`; `--dry-run` prints each planned row as id, target, order and `h8`, never params), `wt-model alias rm <alias/name>... [--yes] [--force-in-use]` (as `model rm`; an alias with client sessions additionally needs `--force-in-use`, one meaning per flag, C7). Then the existing post-write route sync (`h.syncAndWarn`). No `--json` on set/rm (as `model add|edit|rm`), no `wt alias` pointer stub, no TUI screen (the spec puts a Models-tab screen in phase 2; deferred, see "Unresolved for the owner").
10. **#626 in this phase is minimal:** the registry `context_window` key on models, `wt-model model add|edit --context-window N` (0 clears), the catalog sends it, and claude declares it for local models too. Deferred: pi's hardcoded 262144 (`pi_models.go:88`), a window column in the picker or `wt profile slots`, a slot-profile `context` key, launch-time warnings for unknown windows.
11. **Model removal guard:** `RegistryDoc.RemoveModel` refuses a model any alias targets (`ErrModelInUse`, naming the aliases); `wt-model model rm` and the Models tab surface it; cloud-sync drops such models from its removal set **while planning, inside `internal/cloudsync`** (both the openrouter and the ollama flow, before the removal digest and before any ollama tag action) and warns `kept <id>: alias/<x> targets it`. *Why:* touched-row validation would not catch it, and a dangling target silently shrinks a group.
12. **Session accounting at read time:** `sessionreg.Registry` gains an optional expansion snapshot, `SetExpand(func() map[string][]string)` (alias id → its current local target), called once per read before `r.mu` is taken, so `Counts`, `Live`, `Users`, `Seen`, `IdleSince`, `Touch` and `Forget` treat a session on alias A as also using A's current local target: `Touch(A)` also sets the target's idle clock (registering it); `Forget(A)` first carries A's last-used time to each target that has a later-or-no clock; `Forget(target)` is a no-op while a live session's alias expands to it. Register-time expansion was rejected: a re-point would go unseen until the session re-registered.
13. **Cloud targets in alias rows carry their resolved key** into LiteLLM's database, exactly as phase 1 already does for rec's key (HMAC in the stamped hash, redacted from errors, never printed). The owner may veto (see "Unresolved" at the end).
14. **Rotation:** alias rows are `Registered` (stats families) but `catalog.RegisteredOrdered` skips `Kind == alias`, so a no-pin `wt` never rotates onto an alias; the picker and `-M alias/x` list and launch them.
