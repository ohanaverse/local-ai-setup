# Ornith-1.5 Benchmark — Design

**Date**: 2026-08-26
**Status**: Approved

## Goal

Configure the three local backends (Ollama, oMLX, llama.cpp) to serve the **Ornith-1.5-35B-A3B** model, then benchmark all downloaded 35B variants side-by-side, mirroring the existing `qwen3.8-benchmark` methodology.

## Variants Under Test

Four 35B variants across three backends, each measured **direct** and **via LiteLLM**:

| Backend | Model ID | Quantization | Size | Port |
|---|---|---|---|---|
| Ollama | `ornith-1.5:35b` | Q4_K_M | 22 GB | `:11434/api/chat` |
| oMLX | `Ornith-1.5-35B-A3B-MLX-4bit` | MLX 4-bit | ~19.5 GB | `:8000/v1/chat/completions` |
| oMLX | `Ornith-1.5-35B-A3B-MLX-6bit` | MLX 6-bit | ~28 GB | `:8000/v1/chat/completions` |
| llama.cpp | `local-llama` (Ornith Q6_K) | Q6_K GGUF | 29.2 GB | `:8080/v1/chat/completions` |

The Ollama `ornith-1.5:9b` model is **out of scope** (different model size, not a 35B variant).

## Deliverables

1. **`ornith-1.5-benchmark`** — standalone single-pass script, copied from `qwen3.8-benchmark` and adapted for the four Ornith variants.
2. **`ornith-1.5-benchmark-multi`** — multi-pass wrapper (N passes + cool-down), copied from `qwen3.8-benchmark-multi`.
3. **Configuration changes** (prerequisites, see below).
4. **`benchmarks/ornith-1.5-benchmark.md`** — reference doc (methodology, results, gotchas), mirroring `qwen3.8-benchmark.md`.

## Configuration Changes (Prerequisites)

1. **llama.cpp LaunchAgent** (`~/Library/LaunchAgents/local.llamacpp.server.plist`):
   - Repoint `-m` from the Qwen3.8 GGUF to the Ornith `Ornith-1.5-35B-Q6_K.gguf` snapshot path.
   - Resolve the exact snapshot symlink under `~/.cache/huggingface/hub/models--ornith-ai--Ornith-1.5-35B-A3B-GGUF/snapshots/...`.
   - Keep `--n-gpu-layers 999`, `--ctx-size 16384`, port `8080`.
   - **Model name**: llama-server serves one GGUF at a time and ignores the `model` field in requests. The direct request uses `local-llama` (same as qwen3.8); the LiteLLM entry uses a *unique* `model_name` (`llama.cpp/ornith-1.5-35b`) to avoid colliding with the existing `llama.cpp/local-llama` entry.

2. **LiteLLM config** (`~/.config/litellm/config.yaml`):
   - Add four Ornith entries alongside the existing qwen3.8 entries:
     - `ollama/ornith-1.5:35b` → `ollama_chat/ornith-1.5:35b` @ `:11434`
     - `omlx/Ornith-1.5-35B-A3B-MLX-4bit` → `openai/Ornith-1.5-35B-A3B-MLX-4bit` @ `:8000/v1`
     - `omlx/Ornith-1.5-35B-A3B-MLX-6bit` → `openai/Ornith-1.5-35B-A3B-MLX-6bit` @ `:8000/v1`
     - `llama.cpp/ornith-1.5-35b` → `openai/local-model` @ `:8080/v1`

3. **oMLX model discovery**:
   - Verify the 4-bit model (`~/.omlx/models/Ornith-1.5-35B-A3B-MLX-4bit`) is discoverable by `omlx serve`.
   - Currently `/v1/models` only lists the 6-bit model; the 4-bit may require an oMLX restart/rescan.

## Isolation Strategy

Same as `qwen3.8-benchmark` — each local variant runs in isolation to avoid Apple Silicon GPU/RAM contention:

- **`stop_all_local`**: `ollama stop ornith-1.5:35b`, `omlx stop`, `launchctl unload` llama.cpp LaunchAgent.
- **`start_one_local`**: start the target backend and warm up the *specific* variant with a short `"hi"` request, checking for a completed response.

**Key extension vs qwen3.8**: oMLX now serves **two** models (4-bit and 6-bit). The warmup request must name the exact variant so the correct model loads into GPU/RAM (oMLX uses LRU memory management). The 4-bit and 6-bit are benchmarked as two separate "backends" in the loop, each with its own `start_one_local` warmup targeting its model ID.

## Measurement

For each variant, direct and via LiteLLM:

- **TTFT** (time to first token) — prefill latency
- **Total generation time**
- **Tokens generated**
- **Throughput** (tokens/sec, generation-only, excludes TTFT)

Streaming requests with `stream_options.include_usage`, `temperature=0.0`, `max_tokens=200`.

## Output

- Single pass → `/tmp/ornith-1.5-benchmark-<timestamp>.md`
- `-multi` wrapper → N passes with cool-down (default 3 passes, 15s), each writing a separate timestamped file.
- Archive notable runs into `benchmarks/results/`.

## Script Structure

Mirror `qwen3.8-benchmark` exactly:

- `build_payload` (Python JSON builder)
- Associative arrays: `DIRECT_URLS`, `DIRECT_MODELS`, `LITELLM_MODELS` (4 entries each)
- `display_key` (map `llama_cpp` → `llama.cpp`, `omlx_4bit`/`omlx_6bit` → readable labels)
- `stop_all_local`, `start_one_local` (with per-variant warmup), `ensure_all_local_started`
- `run_streaming` (TTFT/throughput measurement)
- Main loop: direct pass over all 4 variants, then LiteLLM pass over all 4 variants
- No OpenRouter/cloud section (Ornith is local-only)

## Out of Scope

- The Ollama `ornith-1.5:9b` model
- OpenRouter/cloud comparison (Ornith has no cloud variant)
- Accuracy/quality benchmarks (this is performance-only, like qwen3.8)
- Modifying the existing `qwen3.8-benchmark` script

## Risks / Open Items

- **llama.cpp plist repoint breaks qwen3.8 reproducibility**: llama-server serves one GGUF at a time. Repointing `-m` to Ornith means the qwen3.8 benchmark's llama.cpp numbers can no longer be reproduced without repointing back. This is inherent to the task and accepted.
- **oMLX 4-bit discovery**: if `omlx serve` does not discover the 4-bit model, it may need to be moved to a direct subdirectory of `~/.omlx/models/` (currently the 6-bit is nested under `ornith-ai/` and *is* discovered, so the 4-bit at the top level should also work — verify).
- **llama.cpp Q6_K is 29.2 GB**: heavier than the Qwen3.8 Q4_K_XL (16 GB); load times and memory pressure will be higher.
- **Quantization mismatch**: the four variants use different quantizations (Q4_K_M, MLX 4-bit, MLX 6-bit, Q6_K), so this is a runtime+quantization comparison, not a pure runtime comparison — same caveat as the qwen3.8 benchmark.
