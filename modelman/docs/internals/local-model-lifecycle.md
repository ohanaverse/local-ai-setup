# modelman local-model lifecycle: start, stop, probe, discover

Internals reference for `modelman/`, reached from [`modelman/CLAUDE.md`](../../CLAUDE.md). Backticked paths are relative to `modelman/` unless they start with `../`.

## Local-model lifecycle

`modelman start <id>` / `stop <id>` / `stop --all` and the TUI's `s` key are the sanctioned non-benchmark start/stop paths (`local_control.py`; design: `../docs/superpowers/specs/2026-09-14-local-model-lifecycle-design.md`). **Per-provider process limits:** multiple local models may run concurrently across providers (advisory only — nothing stop-alls on start). ollama is multi-tenant; omlx is a pool that can hold several loaded models, and modelman hands its starts and stops to `wt` (`wt_bridge.start`/`stop`, below), so starting one omlx model leaves the others loaded unless memory forces omlx to evict; mtplx and mlx_lm_server serve one model per process, so starting a different model on one of them replaces its current occupant. `omlx`/`omlx-6bit` are ONE server (`_OMLX_PROVIDER_IDS`, shared port 8000), and wt is needed for the omlx start/stop paths (`wt start --json`, `wt start --plan`, `wt stop`; an older wt rejects those flags with cobra's `unknown flag`, which `wt_bridge` turns into a message to reinstall — for the start, the stop and the plan alike). wt ignores the `running` flag and probes providers itself.

- **Start** (`start_local_model`): resolve the name — registry id, an existing model's native provider-side name, or a discovered artifact's native name (or its `<family>/<name>` id), started from an unsaved `_discovered_entry` WITHOUT registering it and with no family asked (`_resolve_local_model`, #179 Phase B; its flag is kept under the discovered id, which matches wt's — `running_model_ids` probes such a flag through `_flagged_target`, and `same_provider_occupant` counts it) → reject cloud models and providers outside `SUPPORTED_PROVIDER_IDS` → an omlx model goes to `_start_omlx_via_wt` here (below) → resolve launch args (mlx_lm_server pairing, mtplx model name, env vars) fail-fast *before any teardown* → if already flagged running, probe: serving ⇒ no-op, dead ⇒ clear and start. ollama is flag-only (lazy-loads on first request). mtplx and mlx_lm_server find the same-provider occupant (`same_provider_occupant`, which returns `None` for omlx and ollama) and tear it down inside `isolate_provider(..., solo=True)`, so **the occupant's flag is cleared only after that call succeeds**. `isolate_provider()` failure clears this model's flag and raises. Every start (including an already-running no-op) closes with one `wt litellm sync` — that call is what routes the model (#179), and it is also why an ollama start refuses up front when the daemon isn't answering (`_require_ollama_daemon`): wt reads a *refused* ollama probe as "nothing is pulled" and prunes every configured ollama route, the model just reported started included. Sync warnings ride on the result; they never fail the start.
- **omlx start** (`_start_omlx_via_wt`, #213): `wt_bridge.start(id, replace=True)` runs `wt start <id> --json --replace` — `--replace` because `modelman start` has always replaced without asking on the command line (the TUI asks first, from wt's plan). wt loads the model into omlx's pool beside the loaded ones, holds the registry's `secret_ref`, and writes the route; it answers `started` or `already_running` plus `unloaded`, the ids omlx evicted to make room. There is no modelman-side already-running probe for omlx: wt's `already_running` is the answer. On success modelman sets the target's flag and clears the flag of each `unloaded` id that has a state row (`StartResult.unloaded`; `modelman start` prints them), then closes with the usual one `wt litellm sync`. A start wt refuses or that fails raises `LocalControlError` and **changes no flag**: wt reports no `unloaded` for a failed start (#260), so what omlx may have evicted on the way is not known here, and the next `running_model_ids()` probe clears any flag that went stale. A start that hits `START_TIMEOUT` (`WtBridgeTimeoutError`) is reported as one that may still be going on — the bridge kills wt, not omlx, so the message says the model may still be loading in omlx and to check before retrying. `wt_bridge` has three timeouts, each above the wt budget it waits on: `START_TIMEOUT` 660s (wt's warmup budget is 600s), `PLAN_TIMEOUT` 30s, `STOP_TIMEOUT` 330s (wt's unload budget is 300s); `_run_wt` is the one seam all three share, and the parsers (`parse_start_plan`, `parse_start_outcome`) reject any status outside wt's documented set. The `wt start --json` shapes are pinned by `../docs/contracts/wt-start-cli.sample.json`, read by `tests/contracts/test_wt_start_cli_fixture.py` and a Go test in `../wt/cmd/wt`.
- **Stop**: takes the flagged id — a registry id, or the discovered id of a model started without an entry (the provider is the id's prefix, so `omlx/<name>` stops the shared omlx server); no-op when the flag is false; ollama → `ollama stop <name>`, mtplx → `lifecycle.stop("mtplx")`, omlx → `_stop_omlx_via_wt` (below), others → `stop_provider()`; then a locked flag clear and, after it and outside the lock, one `wt litellm sync` (wt probes the providers itself, so the process must already be gone). Routing is not sticky across stop/start: for an mtplx or mlx_lm_server model the sync drops the stopped model's route (it must not stay routable to a dead backend), while a stopped **ollama** model keeps its route — wt's desired set counts a pulled model, not a loaded one, so a pulled model stays routable and lazy-loads. `stop_all_local_models()` is the only stop-everything path, with one sync for the lot; it is **unchanged** and still halts the omlx service through the Python backend (`modelman stop --all`). Sync warnings surface on `StopResult.warnings`/`StopAllResult.warnings` and never block.
- **omlx stop** (`_stop_omlx_via_wt`, #213): `wt_bridge.stop(id)` runs `wt stop <id> --yes`, which unloads that one model; the service and the other loaded models stay up, and their flags and routes are left alone. wt refusing with `is not running` or `unknown model` (`_WT_NOT_RUNNING`) is not yet a fact about the pool — the refusal also comes from a pool wt could not read at that moment, or an id it could not map — so the pool is read (`wt served omlx`) and **the model is looked for in the list it returns**, by the name omlx serves it under (`_omlx_side_name`: the registry model's `model_name`, else the id's tail after the first `/`, a discovered id being `omlx/<directory name>`; matched with `_name_matches`). The list holds the model: wt refused to stop a model omlx has loaded, an error that keeps the flag. The list is empty, or the name is known and not in it: the model really is not loaded (evicted, or timed out), the goal is met and the flag is cleared. The list is non-empty and no registry was given: the id may be a registry id (`omlx/org--name`), whose tail is no directory name, so its absence proves nothing — "cannot say", an error that keeps the flag. And when `wt served omlx` does not answer (a keyed omlx the registry names no `secret_ref` for), the model may well be loaded, which is "cannot say" too and never clears a flag (#249), so it raises `LocalControlError` naming the remedies (`auth.secret_ref`, or `modelman stop --all`). The one exception to that last case is an omlx positively not there: `stop_local_model(..., registry=)` passes the registry, `_omlx_origin(registry)` gives the omlx server's origin (the row standing for the family, plain `omlx` first, else the default port), and only a **refused connection** there (`local_process.connection_refused`) lets the stop clear the flag. A timeout, a reset or an unusable answer comes just as well from an omlx busy loading a model, so none of them count as down, and a refusal at the default port says nothing about an omlx on another host or port. Without a registry (`modelman stop` loads it through `_load_registry_for_stop`, which tolerates an unreadable one) that exception is not taken, so the case is an error; a refused stop then clears the flag only when the pool answers and is empty.
- Subprocess calls run outside `locked_state`; only the short per-model flag writes take the lock.
- **Resolving and listing local models (#194).** `_resolve_local_model` tries, in order: a registry id; an **exact discovered id** (only when the typed text starts with a local family or row prefix — a bare name or a repo id like `mlx-community/Name` cannot be one and costs no provider listing; it is what the listing printed, so it beats the lenient name match that follows, which for omlx and mtplx compares name tails and would hand `mtplx/Org/Name` to a registered omlx `Name`); a registered model's native name (`_typed_name_matches`: lenient for omlx/mtplx, but **exact for ollama** — the name with or without the `ollama/` prefix and the implicit `:latest`, since a user namespace is part of an ollama name and `someuser/qwen3:8b` is not a registered `qwen3:8b`); a discovered artifact by name, where an artifact named exactly what was typed beats the tail matches (`qwen3:8b` is the pulled `qwen3:8b`, not ambiguous with `someuser/qwen3:8b`). A typed `<prefix>/…` whose prefix names a **local** family or row is a claim about where the model is and never starts another provider's artifact; a prefix that names a **cloud** provider is accepted only when the whole typed text is an artifact's name (`openai/whisper` pulled under ollama), never in front of a shorter one. Listings (`inventory_local_models`, `discover_unregistered_models`) go through `_listable`, which drops an artifact whose discovered id is already a registry model's id — it can be neither started nor routed, and the TUI's `+` row would register a duplicate id; `_find_discovered` keeps it so the start refusal can explain the clash. `OllamaProvider.list_local` skips `ollama list`'s cloud rows (SIZE `-`): nothing is on disk.
- **Ollama start checks the pull** (`_require_ollama_pulled`): the start is flag-only, so an unpulled registered model used to "start", read as running and get no route. It now fails with `<id> is not pulled — ollama pull <name>`, but only on a positive "not pulled": it reads `/api/tags` at the provider row's origin — the same server `_require_ollama_daemon` and wt's probe ask, parsed as wt does (`remote_host` entries are cloud models, implicit `:latest`) — never the local `ollama list` CLI, which describes a different server when `base_url` points elsewhere. A tags read with no usable listing is unknown and the start proceeds. `conftest.py` no-ops this check for the whole suite (it would otherwise GET the developer's real daemon); its own tests patch the real function back.
- **`modelman sync` writes only what it observed** (#231): `sync.reconcile` updates `ready`/`disk_path`/`size_bytes` on the existing row (`dataclasses.replace`), and the `sync` command merges just those three fields, for just the reconciled ids, onto the state as it is on disk when the scans finish. `running` is never written from the snapshot: the command ends by re-probing every flagged model with `running_model_ids()` (as the TUI's mount does), which clears a flag only on a probe made at that moment against the state it re-reads under the lock (#243), and reports `No longer running, marked stopped: …`. Rebuilding the row reset `running`, so every sync recorded every registered local model as stopped (`modelman stop` then said "is not running"); writing the pre-scan snapshot back whole also undid a start or stop made while sync ran and resurrected a discovered model's deleted row. Never construct a fresh `ModelState(...)` for an existing model, and never `update()` the on-disk store from an older snapshot.
- **Flag clears leave no empty state row** (`_clear_running_flag`, used by stop, `stop --all` and `_clear_stale_running_flag`): clearing a flag deletes the `[model_state."<id>"]` row when nothing else is left on it — a discovered model's row exists only for the flag. The TUI's `_resync_running_flags` therefore reads a row missing from disk as `running = false`.
- **Provider rows for installed tools** (`sync._ensure_provider_entries`, used by `modelman sync` and `modelman migrate`): a default local provider gets its row when a model references it **or its command is on PATH** (`_installed_local_providers`: ollama, omlx, mtplx; mlx_lm_server only by reference; an installed omlx adds no `omlx` row beside an existing `omlx-6bit` one — same server). There is deliberately no opt-out: a row deleted by hand for an installed tool comes back on the next sync (decided in the #194 review). This is what makes a fresh machine usable — `migrate` used to write `providers = []`. `conftest.py` stubs the PATH lookup to "none installed".
- **Warmup on a keyed omlx (#256)**: `probe.warmup` is keyless. An omlx with an API key answers 401 to it — on the liveness URL (`/v1/models`), which `warmup` now reads as "up", and on the chat, where a 401/403 raises `probe.WarmupRefusedError` at once instead of polling out `WARMUP_TIMEOUT`. `OmlxBackend.warm` catches that and runs `wt_bridge.warm("omlx", model)` — `wt warm omlx <model>`, the same request with the registry's `secret_ref` resolved by wt. This path is now reached from `modelman provider isolate omlx` and the benchmarks' isolate, not from `modelman start`, which hands the load to wt (`wt start`, which sends the key itself). Only the warmup is covered: nothing else modelman sends to omlx (a benchmark's own requests) carries a key.
- **Probing** (`_probe_running`): omlx/omlx-6bit and mtplx match `/v1/models` ids lenient-prefix/strict-variant-tail — for omlx only after `_omlx_loaded` has cut the list down to what is loaded, because omlx lists its whole pool, loaded or not (wt#201): it asks `/v1/models/status` **without a key** first (`_omlx_status_loaded`; per model, loaded or mid-load counts, as in wt; a `models` list in which any entry lacks a boolean `loaded` is not the schema this code reads and counts as no listing, never as "nothing loaded"). `/health`'s `loaded_count` is no longer used: it reads a pool with one model still loading as "nothing loaded" (#213). An omlx with no API key answers, which settles every pool state; one that wants a key refuses, and since modelman resolves no `secret_ref` it asks wt — `wt_bridge.served_ids("omlx")` runs `wt served omlx --json`, wt's `localmodels.ServedIDs` with the registry's key. That is the one probe that shells out, reached only by a keyed omlx; an omlx that answers neither and predates the pool endpoints (its `/health` **answers**, with no pool counts) is read from the `/v1/models` list, as before; one whose `/health` has the counts will not say which models they count, so the answer is **unknown**: `_probe_running` answers `None`, not `False` (#249). When `/health` does not answer either, nothing answered at all, and the `/v1/models` list is the `[]` of a read that failed with the rest: only a **refused connection** to `/health` (`local_process.connection_refused`) reads as "nothing loaded"; a timeout or a reset is unknown too, since an omlx busy loading another model gives them inside the 2s probe timeout. The probe has three answers and only `False` may clear a flag: `running_model_ids()` and the no-arg `modelman start` inventory ask `is not False`, so a flag set by a start that succeeded survives a pool that cannot say (read as "not running", it cleared the flag of a model omlx was still serving, and `modelman stop` then no-opped); `start_local_model`'s idempotency check (which never probes omlx: wt answers `already_running` itself) asks for a definite `True` and reloads otherwise — except for ollama, whose start is flag-only, so an unknown probe there leaves the flag and reports already running; mlx_lm_server needs only a non-empty `/v1/models` (its reported spelling need not match the registry). **For ollama the probe asks "still pulled?", never "loaded?"** (#242) — `ollama ps` lists only currently-LOADED models, so asking that would self-clear the flag of a model started and not yet requested. `_ollama_pulled` reads `/api/tags` at the provider row's origin (the same read `_require_ollama_pulled` makes, so a remote `base_url` is asked at the right server) and only a listing that positively lacks the model reads as not running; a daemon that is down or unreadable is unknown and stays running. That is what clears the flag of a model removed with `ollama rm`, registered or discovered (#233). It costs one local HTTP read per flagged ollama model per `running_model_ids()` call. `running_model_ids()` is the shared flag+probe read path; neither it nor `_clear_stale_running_flag()` touches routes (the TUI's mount reconcile syncs once per run that cleared a flag — see the ModelScreen invariants), and neither syncs routes; the only wt call a plain read can make is the keyed-omlx `wt served` probe above.
- **Discovery** (`modelman start` no-arg inventory, TUI `+` rows — registering one is a deliberate add-and-save step, never part of start): "is this *registered* model on disk?" uses the provider's `resolve_local()`/`is_downloaded()`/`size_of()` (`_registered_presence`); "what's on disk that isn't registered?" uses `list_local()` (`_provider_local_models`, gated on `supports_discovery`). omlx's directory is read by `omlx_model_dirs(md)` (`providers/omlx.py`), omlx's own two-level rule (0.7.0 `discover_models`; wt's `scanOmlxModels` in `../wt/internal/localmodels/sources.go` follows the same rule and the two must list the same names, pinned by `../docs/contracts/omlx-model-dirs.sample.json`, read by `tests/contracts/test_omlx_model_dirs_fixture.py` and a Go test): an entry holding `config.json` is a model named after its directory; one holding `adapter_config.json` is a LoRA adapter and skipped; any other entry is an organization folder whose child directories holding `config.json` are models named after the CHILD (#261); dot-directories are skipped and the first of two equal names wins; and when nothing was found, the model dir itself is the one model if it holds `config.json` and no `adapter_config.json`, unless it holds a Hugging Face cache entry (`models--*/snapshots`), where omlx would have registered from the cache (#263; a conservative answer when that entry is unusable). An unreadable folder contributes nothing instead of hiding the rest. `OMLXProvider._target_dir` looks a repo-keyed model up in this order: the flat `<md>/<repo basename>`; then `<md>/<repo>`, the repo's own `org/name` path, when that is a model directory strictly inside the model dir; then the one scanned model directory with that basename, **only when exactly one has it** — two organizations can hold a model of the same name, and the first in sorted order is not this repo's; otherwise the flat path, so the entry reads as not downloaded. It **never returns the configured model dir itself** (the fallback's answer), and an unreadable directory reads as absent instead of raising. So for a repo-keyed model, a delete of a registered model found inside an organization folder removes exactly that model's directory, never another organization's of the same name, and the model dir is never a delete target (a `local_path` variant returns the user's path unchanged, and modelman never deletes it). A provider that can't be asked is named in a caveat line, never read as empty. A discovered artifact's id is `_discovered_id` — `<family>/<artifact>`, family-prefixed like wt's `config.DiscoveredModelID` (`ollama/<name:tag>`, `omlx/<dir basename>`, `mtplx/<org>/<name>` — mtplx keeps the `/`); the no-arg listing prints it with `(running)` when flagged and probe-confirmed. **`omlx-6bit` has no class of its own:** `ProviderRegistry` resolves it to omlx's (`providers/registry.py` `_ALIASES`, #194) wherever a class is looked up — discovery, reconcile, downloads, sync — and the instance is built from that row's own settings, so a registry whose only omlx-family row is `omlx-6bit` lists and starts an unregistered artifact as `omlx/<artifact>` (wt's id) through the `omlx-6bit` lifecycle backend. A row whose id names nothing modelman has code for is still unqueryable, never "reports nothing". **Two rows that resolve to the same class are one server, and anything keyed on a raw provider id is a place that can forget it** (`ProviderRegistry.resolve` is the comparison): the shared-artifact guard (`find_shared_artifact_owner`) checks entries on a sibling row too, each through its own row's settings (since #241 it does so for every row, so it no longer needs `resolve` to find the siblings), because the alias made `OMLXProvider.delete()` reachable for an `omlx-6bit` entry and that rmtree's a directory an `omlx` entry may own (#224); `modelman sync` picks model-directory rows and reconcilable entries by resolved class (`_is_modeldir_row`, and the same test in `reconcile`), where two fixed id lists used to skip `omlx-6bit` entries entirely (#225). The guard compares only what the deleting entry's `delete()` would really remove (`Provider.removable_paths`, default: all of `artifact_paths`) against everything the other entry lives in: omlx returns nothing for a `local_path` entry, whose delete is a no-op, so sharing a user-produced directory is not reported as a conflict (#227), while deleting a downloaded entry whose directory a `local_path` entry points at still is. mtplx does the same for its `local_path` entries. mlx_lm_server overrides it too, per side: only a target's or draft's repo-downloaded directory is removable, so two pairings sharing a `local_path` or `draft_local_path` directory are not a conflict. Its removable set is not a subset of its `artifact_paths` — a side carrying both a repo and a `local_path` (hand-edited; the forms reject it) removes the repo's downloaded directory, which `artifact_paths` does not list. The guard therefore compares the removable set as it stands, never its intersection with `artifact_paths`, so another entry living in that directory is still found (#229). The one repo-downloaded directory it keeps is one whose removal would take the pairing's own `local_path` or `draft_local_path` with it — the same directory, one inside it, or a parent, on either side (`_removable_dirs`, the same `paths_overlap` test): the guard skips an entry's own id, so the provider has to refuse that itself (#241). When adding an alias or a new id-keyed gate, grep for `MODELDIR_PROVIDER_IDS`, `RECONCILABLE_PROVIDERS`, `DEFAULT_PROVIDER_IDS`, `SUPPORTED_PROVIDER_IDS` and `provider_id ==`/`in` tests.
- **TUI `s`** always confirms (`Stop <id>?`, or a start dialog). For an mtplx or mlx_lm_server start that would replace the provider's occupant, the dialog names that occupant. For an omlx model its text comes from wt: `s` runs a `model-start-plan` worker that calls `wt_bridge.start_plan(id)` (`wt start <id> --plan --json`), and `pool_start_note` turns the plan into the dialog line — `would_unload` names the models (with their live wt session counts), `fits` and `running` add nothing, and `unknown`, no answer, or a `would_unload` naming no model says wt could not tell, never "nothing will be unloaded". The omlx test is `local_control.is_omlx_family`, so `omlx-6bit` rows take the same path. The worker hands the note to `_confirm_planned_start`, which pushes the dialog (`_confirm_start`) **only while the model screen is still the top screen** (`self.app.screen is self`): the plan can take up to `PLAN_TIMEOUT`, and over a form, a delete confirm or the quit dialog opened meanwhile, `ConfirmModal`'s bare `y` would take a keystroke meant for that dialog and confirm a start that may unload models. Otherwise the plan is dropped with a notification to press `s` again. A plan refused by a wt too old for `--plan` is notified as an error (the reinstall hint) and offers no start. The start itself is the `model-start` worker; the mtplx/mlx_lm_server path calls `_confirm_start` synchronously. `_lifecycle_worker_busy()` rejects a second `s` while a `model-start`, `model-stop` or `model-start-plan` thread worker runs. Textual cannot cancel a thread worker, so a warmup can hold it for minutes.
- **Quit with workers running:** `ModelScreen.action_back()` (Escape and Ctrl+Q) checks `self.workers` for anything `is_running` (start/stop, reconcile, price refresh) and shows `ConfirmForceQuitDialog`. "Force quit" → `_force_quit()` restores the terminal then `os._exit(0)` — the only way out, since a normal exit hangs in `asyncio.run()`'s executor join and then `concurrent.futures.thread`'s untimed `atexit` join. Safe because `running` is a hint the next probe self-heals.
- **`ctrl+q` routing:** `ModelmanApp.request_quit()` (`app.py`) `isinstance`-checks the top screen (`ModelScreen` → `action_back()`, `ConfirmForceQuitDialog` → `dismiss(True)`, else `self.exit()`). `ctrl+q` is a priority `App` binding resolved before any modal's bindings, so **any new modal that can be topmost during quit needs its own branch in `request_quit()`**, or a second `ctrl+q` silently bypasses it.
