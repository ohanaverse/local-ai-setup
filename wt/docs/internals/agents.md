# wt agent drivers and routes

Internals reference for `wt/`, reached from [`wt/CLAUDE.md`](../../CLAUDE.md). Backticked paths are relative to `wt/` unless they start with `../`.

## Agents (Go)

Each agent registers a `Driver` (`Build(m config.Model, yolo bool, r config.Route) LaunchCmd`, `YoloFlag() string`). `BuildLaunchCmdGateway(agent, m, worktreePath, yolo, gw, models, extraArgs)` (`gateway.go`) is the one launch constructor for both launch paths and `wt smoke`: it builds one `config.Route` with `GatewayRoute(gw, m)` and hands it to `Build`; drivers must not bypass it.

**The route is always the gateway.** Every session reaches its models through the model server's gateway (`agents.Gateway{Origin, Token}`, from the client's endpoint): `GatewayRoute` sets `BaseOrigin` to the gateway origin, `APIKey` to the gateway token, `ModelRef` to the model's gateway id (`GatewayID`, else its registry id) and `Litellm` to true. A native model, and the empty model a command agent passes, get the zero `Route` and launch bare; the gateway token never reaches them. There are no direct routes: `config.ResolveRoute`, the protocol intersection (`ProtocolDeclarer`, `Route.Forced`/`Protocol`), `IsLitellm` and `ErrLitellmUnconfigured` were deleted with Task 19, so no driver dials a provider's own `auth.base_url` and no session reads the `[litellm]` url or key (R4). An empty gateway origin or token refuses the build (`ErrGatewayUnconfigured`). litellm ≤ 1.98.0 cannot serve codex without a workaround — see [docs/wt-agents/codex-wt.md](../wt-agents/codex-wt.md).

**Model id contract** (in `GatewayRoute`): `Route.ModelRef` is the **gateway id** — the server's `GatewayID`, else the **registry id** (`m.ID`, e.g. `ollama/qwen3.8:27b-mlx`, LiteLLM's `model_list` key), never the provider-side name. `Route.Display` is always `m.ModelName`. Regression tests (`TestClaudeOllamaPrefix`, `TestOpenCodeOllamaPrefix`, the `TestGatewayMatrix*` cells, …) use distinct `ID`/`ModelName` so a wrong id can't slip through.

**copilot must use the chat-completions wire (`WIRE_API=completions`)** — its `responses` wire drops leading characters through the OpenAI-compatible bridge (verified against ollama and via LiteLLM). This deliberately diverges from `ollama launch copilot`, which prescribes `responses`.

**claude maps every model slot on a single-model launch.** Wherever `claudeDriver.Build` sets `ANTHROPIC_BASE_URL` (every non-native launch), it also sets `ANTHROPIC_DEFAULT_<SLOT>_MODEL` to `Route.ModelRef` (the `--model` value) and `ANTHROPIC_DEFAULT_<SLOT>_MODEL_NAME` to `m.ModelName` for each of the four slots, and names the same eight keys in `ClearEnv`, so `command` drops an inherited value and the built command holds one entry per key. The names and the label rule come from `claudeSlotVars` (`claude_slots.go`), which the slot-profile build uses too: change it there, never in one build. Precedence rests on order: `profiles.ApplyEnvAndArgs` appends an applied automatic profile's `env` after the driver's, and the last entry for a key wins in `exec.Cmd.Env`, so a profile value overrides wt's on both launch paths (`TestAutomaticProfileSlotVarWinsOverSingleModelLaunch`). The native launch sets and clears none of them.

Per-agent env/args/config shapes: [docs/wt-agents/](../wt-agents/) `{claude,codex,copilot,opencode,pi,agy,shell}-wt.md`. Notable: **agy is not a command agent** (`IsCommand("agy")` is false), so `-A agy` without `-M` errors "multiple models match" when >1 agy model is eligible.

**Optional capabilities** (type assertions: `GatewaySyncer` and `ArgSetter` in `BuildLaunchCmdGateway`, `Seeder` in `initseed.Seed`, `OneShotRunner` and `StateDirer` in `internal/smoke`):

| Capability | Purpose | Implemented by |
|---|---|---|
| `Seeder` | `InstructionPointers()` — the pointer files `wt --init` creates beside AGENTS.md (never on a launch) | claude, copilot |
| `GatewaySyncer` | pre-launch sync against the gateway (pi → `~/.pi/agent/models.json`: one wt-owned `litellm` block pointing at the gateway, listing the server's non-native models plus the launch target; every other block marked `_wtOwned` (the old non-ollama direct blocks) is removed, and an unmarked block — a user's own, or the old local `ollama` block, which was never marked — is left as it is) | pi |
| `ArgSetter` | passthrough args become argv | shell |
| `OneShotRunner` | `OneShotArgs(prompt)` for `wt smoke` | claude, codex, copilot, opencode, pi, agy |
| `StateDirer` | `StateDir(path)` — the agent's own per-working-directory state, which `wt smoke` removes for a temporary row directory | claude, pi |

**Slot support** is one more optional interface, `profiles.SlotCapable`, declared in `internal/profiles` beside `ProfileCapable` so that package never imports `internal/agents`: `SlotNames()` (the slots, in display order), `ReservedEnvKeys()` (the env keys wt owns for the launch), `CheckConfigContent(map[string]any) error` (the driver's own static rule for a profile's `config_content`) and `BuildSlots(profiles.SlotBuildInput) (profiles.SlotCommand, error)`. Only claude implements it (`claude_slots.go`: slots `fable`, `opus`, `sonnet`, `haiku`). `agents.SlotsFor(agent)` is the type assertion; `agents.BuildSlotLaunchCmdGateway` gives the driver's `SlotCommand` the treatment `BuildLaunchCmdGateway` gives a single-model launch — binary lookup, `ClearEnv` plus `ClearEnvPrefixes` filtering of the inherited environment, the worktree directory and `PWD`, passthrough args appended unchanged — after `CheckSlotPassthrough` refused the flags the driver names (`RefusedSlotPassthrough`, the optional `SlotPassthroughRefuser`; `--settings` and `--model` for claude, in both the two-argument and the `=` form). Its proxy is the gateway it is given (an empty origin or token refuses); it reads no `[litellm]` table. `agents.BuildSlotCommand` is the driver call alone, for `wt profile show`. Adding slot profiles to another agent is implementing this interface; the catalog, the picker and the launch flow do not change.

**A driver's `config_content` rule is checked twice by one piece of code.** Static validation reaches `CheckConfigContent` through `profiles.SlotDrivers.ConfigContent` (`agents.SlotDrivers()`), so a profile the slot build would refuse is a blocked row with the build's own message, listed by `wt profile list`, and never a launch row. Claude's rule is `claudeConfigEnv`, `claudeModelOverrides` and `claudeEncodable` (`claude_slots.go`): `config_content.env` and `config_content.modelOverrides`, when present, are tables (#412), every `modelOverrides` target is a string (#418: the first other key in key order is named, its value never echoed), and the content can be encoded as the `--settings` JSON (a TOML nan or inf would fail the build's `json.Marshal` at the launch, after the routes were written). `CheckConfigContent` and `claudeSlotSettings` both call them; the build's calls are the second line of defence, for a caller that did not validate. A `SlotDrivers` whose `ConfigContent` is nil fails closed: `ValidateSlots` refuses every profile that sets `config_content` (`config_content cannot be checked for agent "<agent>"`). The callback is asked only about a profile that sets `config_content`, after the mechanism and reserved-`env` rules and before the reserved-key rule for `config_content.env`.

**What a driver warns about never blocks.** The optional `agents.SlotConfigWarner` (`ConfigContentWarnings(cc, slotModels) []string`) is asked through `agents.SlotConfigWarnings(check)` for a Usable profile that passed validation, with the distinct ids its slots name; it is not on `profiles.SlotDrivers`, so a warning cannot reach a verdict. Claude's says one line per `modelOverrides` target that is not one of those ids, in key order (#412); a target that is not a string blocks instead (#418), so it never reaches the warning. `cmd/wt-session`'s `slotContentNotesFor(check)` prefixes each with the profile; `slotContentNotes` runs it over every check, for `slotWarningsRemote` and `wt profile list`, and `wt profile show` runs it over the shown profile's check alone (#419).

**`config_defaults` is an automatic-profile mechanism only.** claude's `ProfileMechanisms` declares `env`, `config_file` and `config_defaults` (`profiles.MechanismConfigDefaults`); `config_defaults` is written into the same `.claude/settings.local.json` as `config_content`, but only where that file has no value (`profiles.ApplyConfigContent`; see [launch-flow.md](launch-flow.md#profiles-internalprofiles)). No other driver declares it, so `Validate` refuses it for every other agent. A slot profile has no such field (the key is unknown in `slot-profiles.toml`) and `CheckConfigContent` is never asked about it.

There is no pre-launch ollama check: `internal/ollamacheck` was deleted with Task 19 (a session asks the model server, whose catalog says whether a model is running).
