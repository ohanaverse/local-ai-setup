# wt launch flow: launch directory, post-exit, survey, sessions, profiles, slot profiles

Internals reference for `wt/`, reached from [`wt/CLAUDE.md`](../../CLAUDE.md). Backticked paths are relative to `wt/` unless they start with `../`.

## Launch directory and the repository

The root command's `RunE` (`cmd/wt-session/main.go`) picks one of five entries into `runLaunchPath(…, launchPath, root)`, tried in this order:

| Entry | `launchPath` | `root` | Outside a git repository |
|---|---|---|---|
| `--root` | `worktree.PrimaryOf(".")`, the primary checkout from anywhere | the same path | refused (also in a bare repository); exclusive with `--cwd` and `-W` |
| `-W <name>` | the worktree `worktree.Resolve`'s `Plan` yields (`Plan.Ensure`), after `confirmLaunch` announced the creation (`launchwarn.ForNew`) or warned for the directory the name resolves to (`launchwarn.ForDir`; the root's own branch resolves to the root and warns like a root launch); an invalid name errors first, with `Resolve`'s own error; a `no` at the question creates nothing | the checkout root | refused: `not in a git repo: <git's error>` |
| `--cwd` | `os.Getwd()`, absolute; `confirmLaunch` warns when it is the root (a terminal with any warning is asked one question first; a `no` is `errCancelled`) | the checkout root, or `""` when `worktree.RepoRoot` finds none | launches |
| no flag, outside a repository (`!worktree.IsRepo(".")`) | `"."` | `""` | this is that case |
| no flag, inside one | `""` (the worktree picker resolves it) | `""` (the caller installs the guard itself) | never reached |

- **The launch warnings run in `RunE`, before `runLaunchPath`,** on the resolved directory: `cmd/wt-session/launchwarn.go`'s `confirmLaunch` over `internal/launchwarn` (`ForDir`/`ForNew` → `Collect` → `Check`), so no picker or launch work happens before the answer. `--root` is the consent for the root warning alone. A `no` is `errCancelled`: exit 3, one line (`approval missing: declined; nothing was launched`), no claim, nothing recorded. Choosing a picker row does not pass through this confirmation: the picker's launches ask their one question at the commit point instead (`internal/tui/launchgate.go`'s `launchGate`), where the root row's pick carries the root warning into that one question — only `--root`'s flag consents to it. `wt smoke --cwd` runs the same confirmation in `runSmoke`, before the model is resolved.
- **`root` gates the guard install and nothing else.** `runLaunchPath` calls `maybeInstallGuard` when `root != ""`. Nothing downstream reads it: `launchFilteredRemote`, `launchSlotProfileRemote`, `launchCommand` and `tui.Run` take the directory only.
- **No launch state is derived from git.** `rotation.state` and `last-picked.state` hold a model id, `usage.jsonl` is keyed by agent and model, and a session's name is the agent's own business. So `--cwd` outside a repository has no key to invent: it writes the same files as a launch inside one, under the same config directory, and cannot collide with a repository's state because no state belongs to a repository. The directory matters in two places, both by path and neither by repository: the agent's working directory (`cmd.Dir`), and an automatic profile's `config_content` target for claude (`<dir>/.claude/settings.local.json`, written only when a profile with that mechanism or `config_defaults` applies, and restored after the run). That target's backup under `profile-backups/` is the one piece of wt state keyed by a directory: `profiles.ConfigFileTarget` makes the path absolute before it is hashed, so two directories never share a backup, repository or not.
- **The TUI's `repoRoot` is already optional.** `newRunModel` seeds it from `worktree.RepoRootAt(prePath)` and leaves it `""` on an error; it is read only when the TUI creates a worktree (the new-worktree prompt, a branch row), and a pre-resolved path starts past the worktree picker.
- **`--cwd` and the no-flag launch outside a repository are the same launch**, except that `--cwd` passes an absolute path where the other passes `"."`. Both name the same directory; `agents.RelativeArgNotes` and `profiles.ConfigFileTarget` resolve either form. The no-flag branch is kept as it is rather than folded into `--cwd`'s.
- **`RepoRoot` (`--show-toplevel`) and `IsRepo` (`--git-dir`) disagree in a bare repository and inside `.git`**: a git directory with no checkout. `--cwd` there used to be refused and now launches with `root == ""`, so no guard is installed by that launch; the no-flag launch there still goes to the worktree picker.
- **`wt smoke --cwd` confirms before the model is resolved.** `runSmoke` reads the flag, takes `os.Getwd()` and hands it to `confirmLaunch` first, for the launch's reason above: a declined question costs no interactive pick and no model start (a `no` ends the run with exit 3, and smoke writes no root claim of its own). Standing in the repository root it warns and proceeds; with no terminal the warning prints and nothing is read. Every other directory warns only for what applies (root drift from anywhere in the checkout; a subdirectory of the root carries the checkout's held and default-branch state too) and runs as before — outside a repository included, which needs no repository for the run and prints no launch line (`ForDir` has no target there). An agent may still refuse the directory itself (codex: "Not inside a trusted directory"), which is why the default row directory is a temporary repository ([smoke.md](smoke.md)).

Pinned by `cmd/wt-session/cwd_norepo_test.go` (a real launch with a recording agent, inside and outside a repository, comparing the state files written) and `TestRunLaunchPath`.

## Launch on the model server (remote path)

Since the flip (Task 18, [wt-session.md](../wt-session.md)) `runLaunchPath` sends every launch that has its directory and its agent to `launchFilteredRemote` (`cmd/wt-session/launch_remote.go`) before anything else; a command agent goes on to `launchCommand` with no model server, and a model-driven one with none configured refuses at `openModels` (`*modelclient.NotConfiguredError`, exit 1) before anything starts. A launch still headed for a picker (no directory, or no agent) builds the model server's client first (`buildModels`) and refuses the same way when none is configured, unless the pinned agent is a command. The remote path reads `app.sessionCfg()` (config.toml only) and never the registry, `config.yaml` or a local provider: no `probeInventory` (`TestLaunchRemoteNeedsNoRegistry` and `TestLaunchRemoteReachesNoHostSeam` make it fail if reached), and the direct path it replaced — the ollama check, the launch-time route check, the refcount record, the in-process start — was deleted with Task 19. `cmd/wt-session/boundary_test.go`'s `TestSessionPathsNeverTouchTheRegistryOrLifecycle` keeps it out: a go/ast scan of every session file (the launch, resolve, smoke and profile files of `cmd/wt-session` and every non-test file of `internal/tui` but the host Models tab, `internal/agents`, `internal/smoke`, `internal/profiles` and `internal/modelclient`) fails on `config.Load` (except `app.go`'s host loader), `.ResolveRoute`, `.IsLitellm`, `.LitellmBaseURL`, `.LitellmAPIKey`, `lifecycle.Start`/`EnsureModelRoute`/`WaitPendingRoutes`, `localmodels.Inventory`, `refcount.*` and `provider.*`. Its order, pinned by `TestLaunchRemoteRegistersBeforeStart`:

1. `resolveModelRemote` (a `-M` pin through `Resolve`; else the catalog's one launchable row). Several and no pin: `rotation.NextFromOrder` over the launchable registered rows in the catalog's registered order (`catalog.RegisteredOrdered`).
2. A client session is registered with the model (`modelclient.Session.Start`) before any start; a failed register is one `wt: note:` and the launch goes on.
3. `modelclient.RunStart` only when `catalog.NeedsStart(row)` (a start row, or a local running row whose `routed` is explicitly `false`; R7: an absent `routed` never starts). Questions go to `cliAnswerer` (`cmd/wt-session/answerer.go`: `--replace`, `--others`, then `/dev/tty` when stdin is a terminal; the others question and warning are `othersQuestion`/`othersWarning`, over `[]modelapi.Resident`). Progress is `startProgressRemote`. A failed start re-registers without the model, ends the client session and exits 2 (`; nothing was launched`); Ctrl-C detaches (`*DetachedError`, exit 2; one that lands before the job has an id, in the active-jobs read or the submit, is `interruptedStartError`, the same exit 2).
4. `agents.BuildLaunchCmdGateway` (seam `buildGatewayCmd`) against the endpoint's origin and token; a native row gets no gateway. `rotation.RecordFor`, then `runLaunch` with `runTail{End: …, PriceNote: …}`.

`runAgentCmd`'s `runTail` carries the post-exit hooks: `End` (the client session's `DELETE`, on a context no Ctrl-C reaches, bounded at 3 s) runs before the `os.Exit` branch (`TestLaunchRemoteEndsTheSessionBeforeExit`); there is no stop picker (the model server stops an idle model after its grace); and `PriceNote` prints the stale-pricing notice from the catalog's `pricing` member through `agents.PrintRemotePriceNotice`, aged on the server's clock (`Client.Now()`, R16), from one cheap best-effort catalog fetch after the agent exits (the picker keeps the pricing of the catalog it loaded and fetches only when it loaded none); a failed fetch prints nothing and never changes the exit code, and a catalog with no `pricing` member (no OpenRouter-priced model) prints nothing. A command agent's tail is the zero `runTail{}`. An `End` that fails is a note, never an error, and says nothing after a register the server refused. Heartbeat notes (`modelclient.Session`) are `wt: note:` lines and never stop the agent. A Ctrl-C in a cooked-mode agent such as `shell` kills wt before `End` runs, so that client session is not deleted and expires at the server's 60 s TTL. Every error goes through `remoteExit` (exit 1 could not start, 2 a started job that did not finish, 3 approval missing or declined).

## Post-exit flow

After the launched subprocess exits, the TUI and non-TUI paths run the same fixed sequence — order and user-facing behavior are in [docs/wt-agents/README.md#post-exit-order](../wt-agents/README.md#post-exit-order); don't reorder one path without the other. Code notes:

- **Summary line** (`wt: <agent> · <model-id> · <duration>`): formatter `internal/agents.Summary`, the single source for both paths. Printed on success and non-zero exit; never affects the exit code. Duration is measured when the agent exits.
- **Exit status, last** (#412): wt exits with the agent's status on both paths, after everything below. The non-TUI paths `os.Exit(ee.ExitCode())` (`runAgentCmd`, `runSlotAgentCmd`); a session writes no route, so there is nothing to wait for first. The TUI cannot exit from inside `tea.Program`: `runAndWaitCmd` and `runSlotAndWaitCmd` return `launchDoneMsg{err}`, the handler keeps `err` on `model.agentErr` (and still sets the `agent exited: …` status), and `Run` returns it from `runResult` after `printPendingSummaryAndSurveyTail`. `cmd/wt-session`'s `runTUI` passes it through `agentExitStatus`: an `*exec.ExitError` becomes a quiet `exitCodeError` with the agent's code (a signal-killed agent's -1 becomes 255, what `os.Exit(-1)` gives the other path), cobra is silenced for it, and `reportExit` prints no `wt:` line; `main` waits for any host route restart (`lifecycle.WaitPendingRoutes`) and exits with the code `reportExit` returns. Any other run error is printed and exits 1, as `runAgentCmd`'s return does — a profile applier error included: `runAndWaitCmd` returns it as that `launchDoneMsg.err` (it does not print it itself, or the message and `main`'s would both appear), so a single-model picker launch whose profile could not be applied prints `wt: <err>` once and exits 1. Pinned by `internal/tui/launch_exit_status_test.go` and `cmd/wt-session/tui_exit_status_test.go`.
- **The client session ends first.** `runTail.End` (non-TUI) and `exitTail.end` (TUI, `remote_start.go`) delete the session's registration on the model server before anything else in the tail, so the server's idle scan sees the model free.
- **No stop picker.** Nothing is offered for stopping when an agent exits: the model server stops a model no client session holds once its idle grace has passed. `survey.Picker`, `survey.ReleaseSession` and the refcount store were deleted with Task 19; `wt stop` (with no argument, the numbered picker over the model server's running local models, `cmd/wt-session/model_cmds_remote.go`) is the one way to stop one by hand. Its stop loop on the host (`survey.StopEntries`, for `wt stop <provider>` and `--all`) runs the models as one `lifecycle.BeginStops` batch (#379: every ollama stop sent first, one shared wait) and settles from a `defer` with one `lifecycle.SettleRoutes` when some stop owed a restart (#142). The TUI stops no model (`TestTUIStopsNoModel`).
- **No worktree prompt.** `internal/exitprompt` (#521) is **deleted** (Task 304): nothing runs between the end of the client session and the summary, and nothing is asked when an agent exits — cleanup is user-driven (`wt worktrees`, `wt remove`). The deletion applied to all four tails at once (`runAgentCmd`, `runSlotAgentCmd`, and the two branches of `printPendingSummaryAndSurveyTail`); the min-age ruling in `docs/superpowers/specs/2026-11-06-wt-worktree-by-default-design.md` ("Exit prompt") now covers `wt remove` alone. A `[launch] exit_prompt` key in `config.toml` is tolerated and ignored (`config.LaunchState` round-trips it; no value is validated or consulted) and a non-empty value prints one note per process (`wt: note: config.toml: [launch] exit_prompt is no longer used and is ignored`).
- **Stale-pricing notice** (from the model server's catalog `pricing`, above; the rule below is the server's, which reads the registry): printed when the registry's OpenRouter prices are more than 7 days old, or were never refreshed (`wt: token pricing last refreshed <date> — run 'wt cloud-sync'` / `… has never been refreshed …`). Nothing stores the date: `config.Config.LastPriceRefresh` takes the newest `pricing_updated_at` among the OpenRouter-priced models (`Model.PricingUpdated`), and `wt cloud-sync`'s openrouter flow stamps every model it matches, changed or not, so the newest stamp is the last refresh. A missing or mistyped stamp is skipped, never an error, and so is one more than a day ahead of the clock (a typo such as 2062, which would otherwise silence the notice until then). wt never refreshes on its own (a refresh is a network call, a registry write and possibly a proxy restart); the notice is the only reminder. Skipped for command agents (`m.ID == ""`) and when the catalog has no OpenRouter-priced model (`config.Config.OpenRouterPricedModel`, #151: a model whose `provider_id` is `openrouter`, and no other; ollama cloud models and other cloud providers' models don't count): `wt cloud-sync` would have nothing to refresh. `internal/cloudsync.OpenRouterPriced` is the same rule over registry rows; `docs/contracts/catalog-predicates` pins both.
- **A slot-profile session has its own tail.** `runSlotAgentCmd` (`cmd/wt-session/slot_launch.go`) and the `launched.profile` branch of `printPendingSummaryAndSurveyTail` (`internal/tui/remote_start.go`) run end → summary, with no survey and no price notice. The summary is `agents.Summary` over an id-only `config.Model{ID: "profile/<name>"}`. Change the two together, as for the single-model tail.

## Session survey (Go)

> **The survey is switched off** (`survey.Enabled = false`, `internal/survey/prompt.go`; 2026-10-05, #136). `PromptRun` returns `""` at once, so no launch path asks anything or prints an after-survey block. Everything below still describes the code, which is kept so the survey can come back by flipping that one value: the questions, the store, `wt stats` (which keeps reporting the answers already in `survey.jsonl`, which thin out as they pass the 30-day window). The package's `TestMain` turns `Enabled` on so the kept code stays tested; `TestSurveyIsSwitchedOff` pins the shipped value. `wt stop`'s prompt (`Select`) and stop loop (`StopEntries`) live in this package but are not the survey and are unaffected.

`internal/survey` records a post-session verdict (worked? speed? quality? task description) for every launch with a model — skipped for command agents (`m.ID == ""`) and native models (`m.Native`). `survey.PromptRun` is the single implementation for both paths (`cmd/wt-session/launch.go runAgentCmd`, and `internal/tui` via the same capture-then-emit pattern the summary uses). It no-ops when stdin is not a TTY and **returns** the after-survey stats block rather than printing it, so the caller can place it after the summary.

- **Paste drain:** after the last question, `PromptRun` flushes the kernel TTY input queue (`drainTTYInput`: `TIOCFLUSH` darwin / `TCFLSH` linux / no-op elsewhere) — a multi-line paste at the free-text question delivers all its lines at once and anything unconsumed would otherwise execute as shell commands in the parent terminal after wt exits. Targeted at `os.Stdin`, not the injected reader, because the residue lives in the kernel queue for fd 0. Don't remove this to "simplify" the survey.
- **Store:** `~/.config/agent-wt/survey.jsonl`, wt-owned, 30-day retention, pruned on every write (mirrors `internal/usage`).
- **Worked%** = `worked / (worked + failed)` over *answered* surveys; skips are recorded but excluded from the denominator. The picker's SURVEY column is gone; `wt stats` is the only reader.
- **Model ids:** surveys and usage key on a free-form id and never require a registry entry. Unregistered on-disk models use `config.DiscoveredModelID(family, artifact)` (the probe family — `omlx` for an `omlx-6bit` row); a registry match keeps its registry id.
- Reporting: `wt stats` — see [docs/wt-stats.md](../wt-stats.md).

## Profiles (`internal/profiles`)

Opt-in overlays from `~/.config/agent-wt/profiles.toml` (absent = enabled, zero profiles), resolved per agent × model (`profiles.Resolve`). Operator reference and per-agent mechanisms: [docs/wt-agents/profiles.md](../wt-agents/profiles.md).

- **Where applied:** both launch paths via `applyProfileForLaunch` (`cmd/wt-session/launch.go`; the TUI reaches it through the `profileApplier` seam set in `main.go`), and `wt smoke` via `applyResolvedProfile` directly. Skipped for command agents and native models.
- **Confirmation:** an interactive launch asks `apply? [Y/n]` on `/dev/tty` (`confirmProfile`); with no TTY it auto-applies (default yes). `wt smoke` never prompts.
- **Apply order** (`applyResolvedProfile`): env/args → `config_content` (with `config_defaults`) → wrapper. Smoke's one-shot args are inserted after profile flags but before the wrapper — codex silently drops a `-c model_provider=...` that trails `exec <prompt>`, and the wrapper splices the current argv.
- **`config_content`** backs up and rewrites the agent's config file (claude `<worktree>/.claude/settings.local.json`, codex `~/.codex/agent-wt-profile.config.toml`; opencode merges into `OPENCODE_CONFIG_CONTENT` instead). The cleanup must be called explicitly after the run (not deferred — `runAgentCmd`'s `os.Exit` would skip it). `SelfHeal` restores an orphaned backup from a killed session; it runs on *every* launch of that agent, before profiles.toml is even loaded.
- **`config_defaults`** (claude only, `MechanismConfigDefaults`) rides on the same `ApplyConfigContent` call and the same backup: after `config_content` is merged, `collectAbsentLeaves` takes each defaults leaf the merged document does not have (a path that crosses a non-object counts as present) and `setLeaves` writes it. Its leaf records go into the same `.keys` marker as `config_content`'s, so restore cannot tell them apart; a value the file already had is never written, recorded or reverted (#402). "Absent" means absent from `settings.local.json`; `.claude/settings.json` and `~/.claude/settings.json` are never read. `ApplyConfigContent` is a no-op only when both tables are empty, and refuses `config_defaults` for any other agent (`profile: agent %q does not take config_defaults`), behind `Validate`'s own refusal. Slot profiles have no such field.
- **Failure posture:** load/validate/apply errors degrade to an unprofiled launch with a stderr warning (a `config_content` failure also reverts env/args already applied). The one fatal case: a wrapper naming a missing binary.
- **CLI:** `wt profile list`, `wt profile show -A <agent> -M <id>` (dry run), `wt profile status`, `wt profile on|off` (refuses to write if profiles.toml failed to parse).

## Slot-profile launch

A slot profile (`~/.config/agent-wt/slot-profiles.toml`, hand-editable; operator reference [docs/wt-agents/slot-profiles.md](../wt-agents/slot-profiles.md)) is its own launch unit, not a model with extras. It is loaded and statically validated once in `newApp` (`profiles.LoadSlots`, `profiles.ValidateSlots`, into `app.slotChecks`), resolved against the model server's catalog (`catalog.ResolveSlotProfileWire`), and launched by one function per path that runs the same steps: `launchSlotProfileRemote` (`cmd/wt-session/slot_launch.go`) and `beginRemoteSlotLaunch` (`internal/tui/slot_flow.go`). `TestSlotFlowParity` (both packages, `internal/profiles/testdata/slot_launch_remote_parity.txt`) holds them to the same server calls.

1. One catalog read; the profile is resolved against its rows (`ResolveSlotProfileWire`): a missing id, a native slot, a slot the server blocks or two local models block the row. A catalog that holds the `profile/` prefix (`catalog.SlotPrefixHolderWire`) blocks it too.
2. `agents.CheckSlotPassthrough` refuses a passthrough flag that would replace the slot mapping.
3. The client session is registered with every `ProfileRow.Distinct()` model before any start; a failed register is one `wt: note:`.
4. The one local slot model is started with a start job only when `catalog.NeedsStart` says so (an unknown route never starts, R7); its questions are answered as on any `-M` pin; Ctrl-C detaches (exit 2, nothing launched).
5. `agents.BuildSlotLaunchCmdGateway` against the gateway, the fail-closed applier (`applySlotProfile`; the TUI is handed the same function as `tui.SlotProfiles.Apply`), the launch recorded, the agent run with the heartbeat going, and the client session ended before any exit.

There is no cloud-route write, proxy restart or proxy probe on this path: the model server owns LiteLLM. The registry path's ten steps (`launchSlotProfile`, `catalog.ResolveSlotProfile`, `lifecycle.EnsureModelRoutes`/`RestartProxy`/`ProbeProxy` on the launch, `phaseSlot`) were deleted with Task 19.

- **Fail closed.** Every abort returns before the agent starts and before anything is recorded. No error on this path degrades to a launch without the profile. `applySlotProfile` is therefore not `applyResolvedProfile`, which reverts and launches unprofiled: it applies a hand-built `profiles.ResolvedProfile` holding only `ExtraArgs` and `Wrapper`, returns an `ApplyWrapper` error, never prompts and writes no file.
- **Automatic profiles are never applied.** Neither path calls `applyProfileForLaunch`, and the TUI's `runSlotAndWaitCmd` never calls `profileApplier`. `selfHealAgentConfigContentTarget` still runs first, so a leftover `settings.local.json` of an earlier automatic-profile session is restored.
- **`config_content` is delivered by the driver, not the applier.** For claude it travels in the inline `--settings` JSON (`claudeDriver.BuildSlots`, `internal/agents/claude_slots.go`); `.claude/settings.local.json` is never written. The gateway token is in the process environment only, never in argv.
- **Always the gateway.** A slot profile reads no `[litellm]` table; an empty gateway origin or token refuses the build.
- **Recording** is one call at the commit point, after the applier succeeded: `rotation.New().RecordProfile(agent, row.Model.ID)` (the usage event and `last-picked.state`; never `rotation.state`). A failed write prints a `note:` line and does not abort.
- **The pin.** `slotPinRemote` reads the loaded `slot-profiles.toml` only: a Usable profile of that name for the agent with no `-T`/`-F` goes to `launchSlotProfileRemote`; one hidden by `-T`/`-F` or only another agent's gets `catalog.SlotPinReason`, which the TUI pin shares; any other `profile/…` id goes to the server's resolve like any model id.
- **What `slotWarningsRemote` says.** The load error; one line per key of the file the schema does not name (`profiles.SlotStore.Unknown`, from the decoder's undecoded keys, with the keys under the free-form `config_content` left out; kept in `app.slotUnknown`, which can be set while `slotChecks` is nil); one line per profile that is not Usable; and one line per driver warning about a passing profile's `config_content` (`slotContentNotes`, `agents.SlotConfigWarnings`; claude's unrouted `modelOverrides` targets, #412; a non-string target blocks the profile instead, #418), read from the static checks, so no server call. A value of the wrong TOML type is not one of these: it fails `toml.Decode` for the whole file and is the load error.
- **A driver's `config_content` rule is static.** `profiles.ValidateSlots` asks `SlotDrivers.ConfigContent`, which `agents.SlotDrivers()` backs with the driver's `SlotCapable.CheckConfigContent`. For claude a `config_content.env` that is not a table is the static error `config_content.env must be a table`, a `config_content.modelOverrides` that is not one `config_content.modelOverrides must be a table` (#412), and one with a target that is not a string `config_content.modelOverrides["<key>"] must be a model id string` (#418), so the row is blocked and `wt profile list` and `wt profile show` report it. `claudeDriver.BuildSlots` applies the same functions again (`claudeConfigEnv`, `claudeModelOverrides`), as a second line of defence.
- **Commands.** `wt profile list` prints `writeSlotProfileList` whatever `profiles.toml` did. `wt profile show -A <agent> -M profile/<name>` is `showSlotProfileRemote`: one catalog read, `ResolveSlotProfileWire`, then `writeSlotProfileShow` builds the preview (`agents.BuildSlotCommand`) against the gateway origin with the client token already masked (`maskKey`), so the real token cannot reach the output. `wt stats` gives a profile's launches a row with no spend (`isSlotProfileID` in `buildUsageRows`).

## Sessions (Go)

wt does not manage agent sessions and never resumes one (#198, #204): no lookup, no prompt, no resume flag, on any launch path. `BuildLaunchCmdGateway` appends the user's passthrough args unchanged, so continuing a conversation is the agent's own flags after `--` — in the picker too:

| | Continue the latest | A specific session | Fork it |
|---|---|---|---|
| claude | `claude-wt -- --continue` | `claude-wt -- --resume <id>` | `claude-wt -- --continue --fork-session` |
| opencode | `opencode-wt -- --continue` | `opencode-wt -- --session <id>` | `opencode-wt -- --continue --fork` |

claude's `--continue` means "the most recent conversation in the current directory", and wt starts the agent in the worktree (or, with `--cwd`, the directory the command was typed in), so it finds the sessions for that directory.

> **Don't bring the lookup back.** wt used to find the newest session recorded for the launch directory and add the agent's resume flag itself (the `Resumer` capability, `agents.ResumeSession`, the `internal/session` package, opencode's `opencode db` query, the picker's resume prompt, `--debug-session`). That appended a one-shot run (`-- -p "..."`) to whichever conversation was newest, including one another process was using (#204), failed an opencode launch whose resumed session had stored a different model (#198), and doubled the flag when the user passed their own. All of it is removed; claude's project-directory slug survives only as the unexported `claudeProjectSlug` in `internal/agents/claude.go`, for `StateDir`.

> **Native models are not special-cased.** Whether a resumed session's stored model overrides the chosen one is the agent's behaviour; wt does not guard against it.


## Session claims (`internal/sessionclaim`, `internal/rootclaim`)

Every launch in a checkout writes a claim file for the worktree the agent runs in — the root or a linked one (a directory outside any repository, or a bare one, claims nothing) — `<git-common-dir>/wt-sessions/<pid>`, and the launch warnings first name (`held`) any other live wt session already holding that checkout — one default-yes question on a terminal, in the same flow as the other launch warnings. The file format and liveness rule: [docs/contracts/session-claims.md](../../../docs/contracts/session-claims.md). No `session-<pid>-<HHMMSS>` branch is ever auto-named: the shared-root menu that offered one is gone with the screen, and every worktree is created for a name the person typed or picked. `internal/rootclaim` is what both paths share around `sessionclaim`: `HoldLaunch` (the per-launch claim, keyed to `LocateSite`'s worktree top level), `Lookup` (the root — the primary checkout — its common git directory and branch, `(detached)` when none, all through `internal/worktree`), `Drift` and `Hint`. A `no` at the warning question ends a launch with status 0 and no message, as quitting the picker does.

- **Launch without the picker** (`--cwd`, which resolves to the current directory; the directory a `-W` names; and the no-flag launch outside a repository, a no-op because `RootOf` is false): `confirmLaunch` has already run in `RunE` — the warnings (or the one `launching in <dir>`/creation line) and, on a terminal when warnings remain, one default-yes `continue?` question; with no terminal it prints and reads nothing. Then the launch claims this session's worktree twice, early and late: `holdLaunch` in `cmd/wt-session/main.go`'s `launchHere` calls `rootclaim.HoldLaunch(launchPath, agent)` before any model starts (a launch that waits minutes for a local model is already visible to the next launch in that checkout; a path that is no checkout yet claims nothing), and `runAgentCmd` calls it again once the worktree exists (`runLaunch` wraps it — `agents.RelativeArgNotes` before the call — and `runSlotAgentCmd` in `cmd/wt-session/slot_launch.go` is the slot twin; every launch — the root or a linked one; a bare-branch launch claims the worktree it created, never the root; a command with no `Dir` names no directory and claims nothing) — both writes land in the same claim file, twice-safe. `HoldLaunch` writes through `sessionclaim.Hold`: it walks the parent chain (a `ps` per generation) before the lock, prunes the stale claims, and writes this claim under one flock on `wt-sessions/.lock`, so of two launches at once only one sees a free directory, and with live others both write and continue — the other session was named by the `held` warning already, so there is no second question (`HoldLaunch`'s `others` are dropped on purpose). A claim that cannot be read or written is one note and never a refusal. `holdLaunch`'s release is kept in `rootClaimRelease`; `runAgentCmd` and `runSlotAgentCmd` call `releaseRootClaim` before their `os.Exit`, and `launchHere` defers it for the other returns. `runAgentCmd` and `runSlotAgentCmd` keep their own `claimRelease` beside the hold (`defer claimRelease()` and the explicit call on the final path) and release on every exit path (that and `releaseRootClaim` take down the same claim file and are safe twice).
- **Picker** (`internal/tui/launchgate.go`): every picker launch learns its directory at the run command's commit point, where the per-call gate (`gateFor`) reads the Target (`launchTarget`: `ForDir` on the picked or preset path, `ForNew` for a bare-branch, remote-only or typed-name pick's owed creation — and a pick from the unified list has its row's own PR, upstream and dirt facts folded in over that live read, `launchwarn.FromRow`, with the row's gathered dirt passed to `ForDirKnownDirt` in place of ForDir's probe, so the full-tree `git status` scan never runs for a row that already answers it) and `launchGate` speaks: the collected warnings — or, with none, the one informational line `launching in <dir>`, which every pick with a directory prints (the creation line of a pick that owes a worktree is the one line in its place, in `launchwarn`'s frozen wording) — and, when warnings remain, one default-yes `continue?` on the released terminal; with no terminal the warnings print and the launch proceeds, stdin never read (`gateFor`'s `stdinTTY`, the probe `confirmLaunch` uses). A root pick carries the root warning into that one question (`RootChosen` is consent only for `--root` on the flag paths and `ForDir`'s ancestor-held case). A `no` declines (the run does not start and wt exits 3 with the same one line, `errLaunchDeclined`, unlike quitting the picker, which stays exit 0: nothing is created, claimed, recorded or summarised — no rotation or usage state, no summary line or survey; the model launch's writes are a closure, `launchAndRecord`'s `record`, that `runRecordAndWaitCmd` calls only once the gate is past, or when a profile fails to apply as before). What a start already loaded is not orphaned by the decline: `pendingSurveyState` is populated as on a real exit, so the standard tail still ends the client session, and the model server stops the model after its idle grace (nothing else auto-stops). A go makes the owed worktree (`launchCreation.ensure`: `Plan.Ensure` at exactly the plan's path, the path the launch's command was built for — nothing records the creation, the exit prompt's records died with it); a typed name that owes nothing runs its plan's `Ensure` there all the same (cmd/wt-session's `-W` runs it unconditionally) — the reused worktree's silent no-op, or git's own error for a path that is not a registered worktree — and claims the worktree (`claimLaunch`: `rootclaim.HoldLaunch` on the run's directory — every launch, the root or a linked one; a zero-Dir target claims nothing) — the warning has named the holder, so there is no second question — keeping the release in `rootClaimRelease`, taken by `releaseRootClaim` when the agent exits (`runRecordAndWaitCmd` claims its own run the same way; two claims of one process are one claim file, twice-safe). A creation that fails after the person continued is a failure, not a decline: the gate returns the error and prints nothing, and the run command carries it out as `launchDoneMsg.err`, so `main` prints it once and wt exits non-zero — exactly cmd/wt-session's `-W` path through `refuse`. A preset path (`prePath`: `-W`, `--cwd`, `--root` through the flag paths) was judged and answered by RunE's `confirmLaunch` already, so at the commit point the gate speaks and asks nothing and only claims: a root launch is asked at most once. Commit points are not serialized against each other: at most the later one is asked about a claim an earlier one wrote, and two truly concurrent commit points can each read a free root and proceed silently.
- **Skips.** The warnings decide on the resolved directory, not the flag: a `-W` naming a linked worktree is not the root and warns nothing, while `-W <root's branch>` resolves to the root and launches there with the root warning (`--root` consents to that warning alone). The root warning is silent when a parent wt session already holds the root (`sessionclaim.AncestorHolds`, which counts a claim only while it is live — pid running and started as recorded, `session-claims.md` — so a stale claim whose pid was recycled does not silence it), so a nested `shell-wt --cwd -- npm test` under an agent at the root is not newly warned. A worktree row other than the root is not the root. A launch in a subdirectory of the root is judged as the checkout top for claims (`ForDir` keys them to `worktree.RepoRootAt`; `rootclaim.HoldLaunch` resolves the directory to its worktree top the same way), so it carries the root's `held` warning and the other warnings its own directory earns (a drifted root, a default branch), and its claim names the checkout top — never the subdirectory's path. A claim by this process or one of its parents (the session a nested `wt` runs inside, as `shell-wt --cwd -- npm test` from an agent at the root) is not another session: the scan skips it and never deletes it, as the retired repo-cleanup script's `pid_is_ancestor` did. Whatever the warnings said, the launch still writes its claim so the next launch sees this one.
- **Root drift is a label, never a block.** When the root sits off the default `origin/HEAD` names, or on a detached HEAD, `rootclaim.Drift`'s line (the literal `root is detached`, or `root is on <b>, not <d>`) rides the warnings (`launchwarn`'s `root_drift`), the worktree list's root row (its `root_drift` reason, and in the manage list the same line again as a drift badge on that row) and the launch picker's header (its first line, whatever row the cursor is on; the picker's rows carry no badge, so it is said once). A plain launch prints it once, in `confirmLaunch`'s warning, followed by the `wt restore-root` hint on a named-branch drift only (a detached root gets no pointer, because `wt restore-root` refuses a detached root); `runLaunch` prints no note of its own. With no `origin/HEAD` default, no drift is invented (the rows' `main`/`master` base fallback never supplies one).
- **Claims never block.** A claims directory that cannot be read or written, this process's start time that cannot be read, or a failing `git rev-parse --git-common-dir` prints one note, `wt: note: could not check other sessions in <root> (<cause>); launching anyway`, and the launch goes on without a claim; a failing `git branch --show-current` records `(detached)` with no note in the root-claim flavor (`rootclaim.Root.Self`), while a `HoldLaunch` claim records an empty `branch=` (the contract spells both). Stale claims (dead pid, or a reused pid whose start time differs) are deleted only by the writers' locked scans (`sessionclaim.Hold` and `Join` prune before they write) and `sessionclaim.Prune`, which the `wt worktrees` list's `F` refresh and a fetch-first `--json` call (never the list's open, never a `--no-fetch` run); the readers — `Others`, `Holders` and `AncestorHolds` — delete nothing. A running pid whose start time `ps` cannot read is skipped: neither counted nor deleted.
- **Lifetime.** The claim belongs to wt's pid, so it lasts as long as wt, not the agent: a wt killed by SIGTERM or SIGKILL while its agent still runs leaves a stale claim, and the checkout looks free.

The full text of rules that [CLAUDE.md](../../CLAUDE.md) now keeps as one-line summaries.

- **wt exits with the agent's status on both paths, after the whole tail** (#412). Non-TUI: `os.Exit(ee.ExitCode())` in `runAgentCmd`/`runSlotAgentCmd`. TUI: `launchDoneMsg.err` (the run's error, or the profile error that kept the agent from starting) is kept on the model, `tui.Run` returns it (`runResult`), and `runTUI` turns an `*exec.ExitError` into a quiet `exitCodeError` (`agentExitStatus`; a signal is 255, what `os.Exit(-1)` gives) with cobra silenced, so `main` prints nothing more; a profile that fails to apply returns its plain error, which `main` prints once and exits 1, as `runAgentCmd`'s return does. Never `os.Exit` inside `internal/tui`.

- A batch of stops costs one LiteLLM restart and one ollama wait: `lifecycle.BeginStops` sends every ollama stop, the batch's `Stop` finishes each model under one shared 3-minute bound (#379), then one `lifecycle.SettleRoutes` (#142). A model ollama accepted and still lists at the bound is `*lifecycle.StillFinishingError`: the stop loop prints it as still finishing and does not count it as failed; every other caller gets an error.

- **The survey is switched off** (`survey.Enabled = false`, `internal/survey/prompt.go`, #136). The code is kept and tested so it can return by flipping that value; `wt stats` still reports stored answers. `wt stop`'s prompt and stop loop live in `internal/survey` and are unaffected. Keep `drainTTYInput` after the last question: it stops a multi-line paste running as shell commands once wt exits. Details: [docs/internals/launch-flow.md](launch-flow.md#session-survey-go).

- **Slot profiles** are a second kind, from the hand-editable `~/.config/agent-wt/slot-profiles.toml` (a launch only reads it; `wt profile slots add|set|rm` is the one writer): a named entry that maps an agent's model slots to registry models, shown as a picker row and pinned with `-M profile/<name>`. Claude is the only agent with slots (`profiles.SlotCapable`). A rule about what a profile may hold that belongs to one agent goes on that interface and is asked through `profiles.SlotDrivers` (claude's `config_content.env must be a table`, `config_content.modelOverrides must be a table` and `config_content.modelOverrides["<key>"] must be a model id string` (#418): `CheckConfigContent`, shared with the slot build; a rule that only warns goes on the optional `agents.SlotConfigWarner`, never on `SlotDrivers`), never written into `internal/profiles` or `internal/catalog`, which do not import `internal/agents`. Operator reference: [docs/wt-agents/slot-profiles.md](../wt-agents/slot-profiles.md).

- **The file's problems are warnings, never a stopped wt** (`slotWarningsRemote`, `cmd/wt-session/slot_launch.go`): a parse failure (a wrong TOML type included, which fails the whole file), each key the schema does not name (`SlotStore.Unknown`; the file still loads), each profile with no usable name or agent, and each driver warning about a passing profile's `config_content` (`slotContentNotes`, `agents.SlotConfigWarnings`: claude's `modelOverrides` string targets that are not the profile's slot models; a target that is not a string blocks the profile, #418). They are printed before the TUI and again after it. `wt profile list` prints every profile's content notes as `warning:` lines, and `wt profile show` the shown profile's alone, under its slot lines (#419): both word them through `slotContentNotesFor(check)`, the one per-profile helper `slotContentNotes` loops over.

- **A default may be an alias of the agent's** (`SlotCapable.DefaultAlias`; claude's `opusplan`, #391): it needs the slots in its `Requires` filled and rests on its `Rest` slot. Read the slot a session works on through `SlotCheck.RestSlot()` and list slots with `SlotCheck.FilledOrder()`, never `Profile.Default`, which may name no slot; only the slot build reads `Default` itself, to pass it as `--model`.

- wt launches a fresh agent every time and leaves session handling to the agent (#198, #204): `BuildLaunchCmdGateway` appends passthrough args unchanged, so continuing a conversation is the agent's own flags after `--` (`claude-wt -- --continue`, `opencode-wt -- --session <id>`). The removed session lookup and why it stays removed: [docs/internals/launch-flow.md](launch-flow.md#sessions-go).

> **A launch that has a directory needs no repository.** The repo root handed to `runLaunchPath` gates the guard install and nothing else: rotation and usage state are keyed by model and agent, never by a repository or branch (claude's `config_content` backup is keyed by the absolute settings path, which cannot collide). `--cwd` passes the checkout root when `RepoRoot` finds one and `""` when it does not (outside a repository, in a bare one, inside `.git`, or with no git on PATH), so it launches either way; only `-W` and the worktree picker refuse. Don't key new launch state on the repository without deciding what a launch outside one records. Details: [docs/internals/launch-flow.md](launch-flow.md#launch-directory-and-the-repository).
