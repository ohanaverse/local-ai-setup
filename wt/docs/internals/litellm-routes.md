# wt litellm: config.yaml route management

Internals reference for `wt/`, reached from [`wt/CLAUDE.md`](../../CLAUDE.md). Backticked paths are relative to `wt/` unless they start with `../`.

## LiteLLM routes (`wt litellm`)

`cmd/wt/litellm.go` + `internal/litellm`. Subcommands (`sync|list|providers|status|on|off|set`; `expose`/`unexpose` were removed in #179 — `sync` is the only CLI route write) and proxy lifecycle: [docs/wt-agents/README.md](../wt-agents/README.md#litellm-routes-are-wt-owned). JSON shapes are pinned by [../docs/contracts/litellm-cli.sample.json](../../../docs/contracts/litellm-cli.sample.json). Gotchas:

- **`sync` reconciles cloud and local rows (#179).** Desired = every `CloudModels` id plus the local models the probe found — running ones and pulled ollama models, registered or discovered (`desiredLocalModels`; #179 Phase B: a discovered route is written as `litellm.DiscoveredModel` under its discovered id, and a desired discovered id that already has an unmarked row is left to that row — no add, no adoption — on the start path too, `ApplyChange`); every row wt writes carries `model_info.wt_managed: true`. Sync removes a row only when it owns it (the marker, or an unmarked row named like a managed registry id — pre-marker rows, adopted on first sync); hand-written rows are never touched, and a marker-only removal spares an unmarked row of the same name. It never removes the row of a registry model with a data gap (`litellm.RegistryGap`: dangling `provider_id`, no location, or a location that is neither `local` nor `cloud`), and a cloud row whose build fails (e.g. a `secret_ref` resolving empty) keeps its existing row.
- **`sync` trusts only `ok` families** (and desires an ollama model when pulled, not only when loaded). A family whose probe ran and is neither `ok` nor refused (e.g. omlx/mtplx `/v1/models` failing) is frozen with a warning — its registry ids via `Options.Untouched`, and every row whose `litellm.RowFamily` is that family, discovered routes included, via `Options.UntouchedFamilies` (`untrustedFamilies`) — and providers with no probe (retired llamacpp) silently; the exception is a server that refuses the connection (`Snapshot.Down`) — its local routes are stale and removed. That case warns only when a local route of the family is in `config.yaml` or the family serves registry cloud models. A family that was never probed is frozen only when the registry references it unresolvably (`gapFamily`: a provider row with no location or one that is neither `local` nor `cloud`, or a `RegistryGap` model — warned as "could not be probed", with `gapReason` naming which); one the registry does not reference at all is not frozen, so its leftover marked rows are removed. A family frozen only for its discovered rows or its gap models' rows gets the warning when `config.yaml` holds a marked row of it. The removals are re-verified under the config.yaml lock (`Options.Recheck`) so a start landing between the probe and the write keeps its route.
- **Commands refuse only on a config *load* failure** (`app.loadErr`, so a default empty config is never acted on). Registry validation gaps (`cfgErr`) don't block: `sync` builds each desired row and reports broken ones per id (exit 1) while routing the healthy ones.
- **A duplicated id is routed from its own row, or not at all.** Two registry rows under one id fail `Config.Validate` (`duplicate model id`), which sync runs past on purpose (above), and a route's name *is* the model id, so the two rows can only ever share one route. Nothing in the sync path may therefore resolve "the row with this id" to the first one (`config.IndexModelByID`): `desiredLocalModels` pairs each running or pulled inventory entry with the row of the entry's **own provider** (`registryRowOf`: model id + provider id, then model_name), `planSync` wants a registry local row only when the caller handed in that very row (id, provider and model_name), and `providerCredErr` asks about the provider of the row being routed. So with one of the rows desired — one provider serving the id, or a cloud row beside a local one that is not running — the route is built from that row. With **more than one desired** (both providers serve it, two cloud rows, a cloud row beside a running local one), or **one desired beside a local row that is frozen** (`planSync`'s `undecided`: a cloud row whose id a local row of an untrusted or unprobed family also carries — that server may be serving the id, and routing the cloud row would rewrite a route the family's warning says was left unchanged), the id names two servers and no single route is right: `planSync` routes none of them, leaves whatever row the id has exactly as it is (its `ambiguous` map is read by the removal loop, beside `gap` and `frozen`; `Options.Untouched` would not do, since it does not hold back a cloud add) and adds one line to `SyncPlan.Warnings`, which `Sync` copies into `Result.Warnings` — `model "<id>" is in the registry twice (providers A, B); its route is left as it is — fix the entry in <registry path>` (every row's provider in registry order; `3 times` and so on for more; the first half is `config.DuplicatedModelText`, shared with the registry writer's `ErrModelAmbiguous`). It is printed once, on stderr or in the `warnings` array of `--json`, by `sync`, `sync --dry-run` and the sync that follows a `wt model` write; the JSON shapes are unchanged. With none desired the id's stale route is removed as usual. A cloud row that shares its id with a local row is not pruned by `Options.Recheck` (`cloudAdd`): the recheck un-desires local ids that stopped, and by id alone it took the cloud row's add with them, so the real sync left unrouted what its dry run had announced. The start and stop hooks and the launch-time check (`routeModel`, `ApplyChange`) still look a row up by id alone: they run only behind the validation gate (`wt`, `wt start`, `wt stop`, `wt smoke`), which refuses such a registry before they are reached. `RowFamily` answers by the first row too, so `Options.UntouchedFamilies` freezes a duplicated id only when its first row is the untrusted family's; the id of every registry local row of such a family is also in `Options.Untouched`, and that holds the id's local rows back whatever the row order. Neither holds back a cloud add — the `undecided` rule above is what keeps the id's cloud row from being routed over the frozen route. The "refused the probe connection … treated as stale" warning (`syncUntouchedAndWarnings`) is decided by id as well, so it does not count an id that more than one registry row carries: the route may be another row's, or left alone as ambiguous, and the sentence would follow a sync that removed nothing. When every row of such an id is stopped the route is still removed, with its outcome line and without that sentence. Pinned by `TestSyncRoutesADuplicatedIDFromTheRowHandedIn`, `TestSyncFreezesAnIDWithTwoDesiredRows`, `TestSyncRoutesADuplicatedIDWithOneDesiredRow`, `TestSyncChecksTheCredentialsOfTheRowItRoutes` (`internal/litellm`), `TestDesiredLocalModelsPairADuplicatedIDByProvider`, `TestLitellmSyncLeavesTheRouteOfADuplicatedIDAlone` and `TestSyncDownWarningIgnoresADuplicatedID` (`cmd/wt`).
- **An OpenAI-compatible local row's `api_base` is `Provider.Origin() + "/v1"`** (`BuildEntry`, `Policy.V1Base`): the address wt's own probes use, so the proxy dials the server wt started. For an mtplx `base_url` on this machine that names no port that is port 8003, where `wt start` serves it, not the url as written (#348); see [local-models.md](local-models.md) for the rule. An ollama row's `api_base` is the registry's `base_url` as written.
- **Every write fills an empty `api_base` on ollama rows (#202)** — `File.EnsureOllamaAPIBase`, called from `applyTo` (the in-memory apply step `applyPlanned` saves and `PlanSync` runs on a discarded `File`, so a dry run's `repair` is exactly what the real sync reports), with the registry ollama provider's `base_url`, or `config.OllamaBaseURL` when the registry names none or has no ollama provider (`OllamaAPIBase`, never `""`; `BuildEntry` applies the same default to the ollama rows wt builds, so the two cannot disagree — #206). LiteLLM runs `ollama serve` at proxy startup for any ollama row without one, which puts a second server on port 11434 and splits clients between the two; a model then stays loaded in the one wt cannot see. It is the one field wt sets on a hand-written row; a row that names an address — its own key, or one inherited through a YAML merge key (`mergedGet`) — is never changed, and a repaired row stays unmarked. Nor is an empty or null value that carries a YAML anchor (`api_base: &base ""`): replacing the node drops the anchor, and a row aliasing it (`*base`) then makes the saved file unparseable; keeping the anchor would push the ollama address into every aliasing row. It is skipped, and a null one is left to `ollamaServeWarnings`. Reported as outcome `litellm.ActionAPIBaseSet`, `api_base set` (dry run: `repair` / `would set api_base`); the lifecycle route writes print it too (`applyReported`: `wt: LiteLLM route for <id>: api_base set`). A repaired row with no `model_name` is reported as `(no model_name: <model>)` (`rowLabel`), never under an empty id. Test fixtures that assert a hand-written ollama row is byte-identical after a write must give it an `api_base`.
- **`sync` warns about the rows that repair cannot reach (#206).** LiteLLM's trigger is `"ollama" in model and api_base is None` — a substring, and `None` only (absent or null; an empty string does not trigger) — wider than wt's `ollama/`/`ollama_chat/` prefixes. wt cannot fill `openai/ollama-proxy` with the ollama address, so `File.ollamaServeWarnings`, read after the repair, names each such row in `Result.Warnings` (`Sync`) and `SyncPlan.Warnings` (`PlanSync`; `runLitellmSync` prints both ahead of the probe warnings). Only the sync asks for the scan (`Options.reportOllamaServe`): a start, stop or launch is not the place to hear about a row it never named, so it does not pay for it. **An `os.environ/VAR` api_base is the same trigger when VAR is unset for the proxy (#211)** — LiteLLM resolves the reference first and an unset variable is `None` — so `ollamaServeWarnings(env)` warns about it too, naming the variable and where it looked, and `EnsureOllamaAPIBase` still leaves it alone (never rewrite a reference: it may name another server on purpose). "Set for the proxy" is `litellm.ProxyEnv` (`proxyenv.go`, `LoadProxyEnv`): the LaunchAgent plist's `EnvironmentVariables` (`ProxyPlistPath`: `WT_LITELLM_PLIST`, else `~/Library/LaunchAgents/local.litellm.proxy.plist`), parsed from XML with no subprocess; a readable plist without the key means nothing is set. wt's own environment stands in only when the plist cannot answer — `RestartCommand()` is not the launchctl fallback, or the plist is missing, binary or malformed — and `ProxyEnv.Source` says which, so the warning never claims a file it did not read. Do not replace this with `os.Getenv`: a shell-only variable would hide the failure and a plist-only one would be reported unset. A variable set to `""` is set. A bare `os.environ/` (no name, or only spaces) is the same trigger and has its own warning sentence — the named one would interpolate an empty name three times (#218).
- `sync` takes `--dry-run` (its plan: add, adopt, rewrite, remove, repair, errors). `list` prints a wt row as its bare id and a hand-written row as `id<TAB>(hand-written)`; `--json` adds `rows` with `managed`. `status` never prints the api key (JSON `api_key_set`, text last 4 chars).
- **`config.yaml` handling:** comment-preserving yaml.v3 edits, but sequence indentation is normalized and blank lines dropped on the first wt write. Permission bits preserved; atomic write guarded by flock on `<config>.lock`. Path `WT_LITELLM_CONFIG` (legacy `MODELMAN_LITELLM_CONFIG`), default `~/.config/litellm/config.yaml`. Restart via `WT_LITELLM_RESTART_CMD` (legacy `MODELMAN_LITELLM_RESTART_CMD`), run as given, else the graceful restart below. A write that restarts with no `Options.Restart` of its own (`wt litellm sync`, and with it every command that syncs after a registry write) runs `RestartAndWait`: `litellm.Bounce.Run` over the package's `bounce` seam — one `Listening` probe of the `[litellm]` url before the restart, the restart, and `WaitReady` up to `ProxyReadyTimeout` (30s) only when that probe found a listener — so the command returns once the proxy answers again (#382; it used to return while the proxy still refused connections). A failed wait is one more `Result.Warnings` entry, printed as `warning: …` like the restart's own; it never fails the sync. The lifecycle route hook runs the same `Bounce.Run` over its own seams on its asynchronous goroutine (see [Lifecycle](local-models.md#lifecycle-internallifecycle)); a caller that passes `Options.Restart` replaces the whole default, wait included.
- **The default restart drains (`litellm.RestartContext`, #377).** `launchctl kickstart -k` makes launchd send SIGTERM and then SIGKILL after the job's exit timeout, 5 seconds for the proxy's plist, which cut off every request in flight. A SIGTERM that does not come from launchd arms no such timer, and uvicorn answers it by closing its listener and exiting once its open responses have ended. So, with no override: (1) read the pid from `launchctl list local.litellm.proxy` (`parseLaunchctlPID`; a loaded job that is not running prints no `"PID"` line and exits 0, which is "not running"); (2) send it one SIGTERM; (3) poll `kill(pid, 0)` every 100ms for at most `proxyDrainTimeout`, 3 minutes, printing one notice after 2s; (4) once it is gone, run a plain `launchctl kickstart gui/$(id -u)/local.litellm.proxy`, a no-op when `KeepAlive` has already respawned the job (launchd does that about a millisecond after the exit) and the start when it has not; (5) at the bound, SIGKILL that pid, wait for it to go, run the plain kickstart and give the cut-off notice. The kill names the old process and never the job: a `kickstart -k` there would also kill a proxy launchd had just respawned, had the old one exited between the last look and the command. A kill that finds no process (ESRCH) is that exit, so nothing was cut off and no notice is given; a kill refused otherwise falls back to `kickstart -k`. No pid, a failed lookup, no `launchctl` (Linux) or a SIGTERM that could not be sent: `kickstart -k` directly, as before. Things to keep:
  - `restartTimeout` (30s) bounds each launchctl command and the override command, never the wait. Wrapped around the whole restart it would turn every drain over 30s into `failed to restart LiteLLM proxy`, which `lifecycle` records and `ProbeProxy` then refuses on.
  - The plain kickstart can block for about ten seconds: launchd will not spawn a job twice within ten seconds, and the command returns when the delayed spawn happens.
  - The proxy exits on the signal it re-raises, so launchd's `LastExitStatus` is 15 after a clean drain. Do not read it as a failure.
  - The proxy refuses connections for the whole drain. That is the cost of the design: the old behaviour refused them for about 5s plus the boot.
  - Every warning `RestartContext` returns is a failed restart. What it says of a restart that was made is a `Notice` (the drain line, `InProgress`; the cut-off), never a warning, so no caller matches on a warning's text. The failed-restart warning keeps the wording `docs/contracts/litellm-cli.sample.json` pins and always names `kickstart -k` as the manual fix.
  - A caller cancelled during the wait gets one warning at once; the signal is sent, so the proxy still drains and launchd restarts it. A caller already cancelled sends no signal.
  - The notices go to the function the context carries (`WithRestartNotice`), else to stderr (`wt litellm sync` and the other synchronous callers).
  - `wt litellm restart` (`runLitellmRestart`) is `RestartAndAwait` on the `[litellm]` url and nothing else (`Bounce.RunWaiting`: no pre-restart probe, `WaitReady` whenever a url is set, so a proxy that was down is not reported restarted until it answers, where `sync`'s `RestartAndWait` skips the wait for one), so a script can make this restart: any warning is its error (exit 1). `bin/update/litellm` runs it after an upgrade when the wt on PATH lists the subcommand, which it asks of `wt litellm --help` (cobra answers an unknown subcommand's `--help` with the parent's help and exit 0).
  - Restarts wt does not make still kill at 5 seconds: a manual `kickstart -k`, `bin/update/litellm` under a wt too old for `wt litellm restart`, and any override command.

- The spend database is `litellm.DatabaseURL()`: `WT_LITELLM_DATABASE_URL`, legacy `MODELMAN_LITELLM_DATABASE_URL`, then `general_settings.database_url` in `config.yaml`. An `os.environ/NAME` value — and `DATABASE_URL`, when `config.yaml` names no `database_url` — is looked up in wt's own environment and then in the proxy's (`ProxyEnv.Lookup` over `LoadProxyEnv`, the LaunchAgent plist); wt's own wins, and a blank value is unset everywhere. Read-only, used only by `wt stats`; under a redirected registry with `config.yaml` unnamed it answers `ErrNoDatabase` rather than read the default file or the plist. Its errors name variables and files, never a value; a `spend.ErrUnreachable` names the host and port `psql` tried and nothing else from the connection string.
