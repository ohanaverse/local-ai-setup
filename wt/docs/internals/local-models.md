# wt local models: rows, inventory, lifecycle, rotation

Internals reference for `wt/`, reached from [`wt/CLAUDE.md`](../../CLAUDE.md). Backticked paths are relative to `wt/` unless they start with `../`.

## Local-model resolution

Every model row wt shows or resolves — the TUI picker, `wt start`/`wt smoke`'s picker, and the non-TUI launch path — is built by `internal/catalog` from the agent's eligible list plus one `localmodels.Inventory` snapshot. The TUI only decorates rows (counts, survey, sort, rendering).

- **rows** — local rows come only from the inventory (#179 Phase B): a registry local model is listed when its entry is running, on disk, or of a family whose discovery failed (status `unknown`, so a flaky probe hides nothing); one confirmed missing from disk, a non-running model of a running-only family (`localmodels.RunningOnly`: an `mlx_lm_server` pairing), or one with no inventory entry has no row. A registry entry is an overlay matched by family + `model_name` (`source.matchArtifact`, `inventory.go`); unmatched artifacts are `new` rows under `config.DiscoveredModelID`, hidden whenever `-T`/`-F` is set. A hidden registry id still reserves its id, so an unregistered artifact spelling the same id is not listed under it.
- **launch** — a cloud row, or a local model the probe reports running and not still loading (`catalog.Row.Ready`).
- **start** — a non-running local row of ollama/omlx/omlx-6bit/mtplx (a pulled ollama model is a start, not a launch), or an omlx model that is still loading (#259, see "Loading is not loaded" below).
- **block** — a non-running row of a provider with no start engine (the reason names how to start it: for an `mlx_lm_server` pairing, `llmbench provider isolate --solo mlx_lm_server <target> --draft <draft>` with the row's own `fetch` and `draft` — `catalog.PairingStartCommand` — and for any other provider wt has no engine for, that provider's own tool; a stopped pairing has no row at all, so its pin gets the same reason from `MissingReason`, which reads the target and the draft from the config it is handed; in the TUI that reason is the agent picker's status, which is wrapped so that the command is on screen — see [tui.md](tui.md)). Separately, an `Unmapped` cloud model (its provider has no `PolicyFor` mapping, so sync never routes it) is refused ("not in LiteLLM") when its route goes through the proxy, and launches normally direct (LiteLLM off). A discovered model is never refused (#179 Phase B: wt routes it under its discovered id). The rule and its wording are `catalog.Row.RefusedByRoute`/`RouteRefusal`; `renderTable` (TUI), `pickerBlockedReason` (non-TUI) and `wt smoke` apply it.

**Inventory** (`localmodels.Inventory(cfg)`): probes ollama (`/api/tags` + `/api/ps`, cloud `remote_host` entries excluded), omlx/mtplx (model-dir scan + what the server is serving, `localmodels.ServedIDs`; the two scans differ — mtplx's directory is flat `org--name` directories (`scanModelDirs`), while omlx's is scanned two levels deep as omlx itself does (`scanOmlxModels`, after omlx 0.7.0 `discover_models`): a top-level directory holding `config.json` is a model named after it, one without is an organization folder whose child directories holding `config.json` are models named after the **child**, a directory holding `adapter_config.json` is a LoRA adapter and never a model, a name found twice is listed once, and a model dir that is itself a model (`config.json`, no `adapter_config.json`) is the one model, but only when nothing else was found and the scan saw no Hugging Face cache entry at the top level (deliberately conservative: omlx registers a model from a usable cache entry and then skips its own fallback, so wt skips it whenever an entry is present; when the entry is one omlx cannot use, omlx itself would serve the model dir and wt does not list it). The shared fixture `docs/contracts/omlx-model-dirs.sample.json` pins the names this scan gives for a set of trees. The folder itself is never listed. Hugging Face hub cache entries (`models--Org--Name/snapshots/…`), which omlx also resolves, are not listed. The names must equal the ids of omlx's `/v1/models/status`, which `Pool.Find`, `matchArtifact` and the load/unload requests match on. A test that builds an omlx model directory uses `localmodels.MakeOmlxModelsForTest`, since a bare directory is not a model) and mlx_lm_server (running only — `/v1/models`, no artifact discovery, so `ArtifactKnown` stays false; with 2+ registered pairings and none name-matching a served id it is `partial` + `Snapshot.Ambiguous`, since `/v1/models` lists HF repo ids, never a `+draft-` pairing name — so a pairing row's `Running` is a guess there, shown and built on by nothing else: pairing identity is [#299](https://github.com/ohanaverse/local-ai-setup/issues/299)) concurrently. Per-family status `ok` / `partial` (the running-state probe failed, so `Running` is untrustworthy) / `unreachable` (discovery failed); a refused connection also sets `Snapshot.Down`. **Never reads a stored flag.** Probe origins resolve here (`FamilyOrigin`; `FamilyOriginPort` returns origin *and* port from one resolution, so a command-line port and dialed URL cannot disagree) and are shared with `internal/lifecycle`, so both describe the same server. **A registry `base_url` is read through `config.Provider.Origin`, and so is every other use of a provider's address** — a LiteLLM route's `api_base` (`litellm.BuildEntry`), a direct route (`config.ResolveRoute`) and pi's `models.json` — so the address wt probes, the one a start waits on and the one a route names are one (#348; `TestStartProbeAndRouteAgreeOnAProvidersAddress` in `internal/lifecycle/origin_test.go` reads each from where production does). `Origin` is `BaseOrigin(base_url)`, with one rule about a url that names no port: for the `mtplx` provider, over `http`, on a host the server wt starts answers on, by the url's text (`localhost` or `localhost.`, `127.0.0.1`, and the unspecified `0.0.0.0` / `::`, which a dial takes to the local host; not `::1` or the rest of `127.0.0.0/8`, which are this machine but not where a `127.0.0.1` listener answers, and not a name that merely resolves here, an `/etc/hosts` alias: those must name their port), the port is `config.MtplxPort` (8003), because mtplx is the one server wt hands a port to (`mtplx serve --port`, `--host 127.0.0.1`) and that is where a start put it. Read as written such a url is port 80: the start polled 8003 and succeeded, and the inventory, the occupant check and the check after the start asked a port nothing listens on, so every `wt start mtplx/…` failed with `mtplx no longer answers at http://127.0.0.1`. Everything else is as written, a missing port meaning the scheme's own: a url that names a port; an mtplx url that is `https` or names any other host (not a server wt could have started: with no port, `wt start` refuses it before it spawns anything, `lifecycle.MtplxAddressError`, where it used to put 8003 on it for the start alone and leave the probes on port 80; a stop and the loading-server check fall back to the default origin there; a port-less mtplx url that really means port 80 is now written `:80`); and omlx, ollama and mlx_lm_server, which wt hands no port — `omlx start` and the ollama daemon listen where their own settings say, the probes, the wait after `omlx start` and the routes already asked one address, and a default port there would be a guess. `FamilyOriginPort` adds no port of its own: its origin is always `FamilyOrigin`'s, and one with no port is an error for every family, so it cannot hand a caller an address `FamilyOrigin` does not (`TestFamilyOriginPortNeverNamesAnAddressFamilyOriginDoesNot`, `TestMtplxStartRefusesABaseURLWithNoPortItCannotServe`). "This machine" for a route's settings is the wider `config.IsLoopbackHost` (it includes `::1` and `127.0.0.0/8`), which `internal/litellm` asks for `use_chat_completions_api`. A test that needs a server "on 8003" never binds it: it gives the client a transport that forwards that one host to a fake and refuses the rest (`servedAt` in `internal/lifecycle`, `onlyHost` in `internal/localmodels`). `Entry.ArtifactKnown` distinguishes "confirmed missing" from "could not determine". `Entry.Path` is the artifact's directory (omlx and mtplx: where the scan found it) and `Entry.Size` its size in bytes (ollama: the `size` of `/api/tags`), and `Entry.LoadedSize` the memory a running model holds as its server says (ollama: the `size` of `/api/ps`, which `OllamaLoaded` returns beside each name; omlx: the pool's resident estimate, only when `Pool.SizesKnown`; mtplx and mlx_lm_server give none); each is zero when the probe's own answer does not carry it, and nothing is walked or stat'ed to fill them. `localmodels.FormatSize` prints a size as `ollama list` does, for `wt model list`, the Models tab and the start engine. **For a registered entry `Path` is the model's own directory or `""`, for every consumer** (#266: a path wt prints is a path someone may delete). The match is by leaf name, so a row for `org-a/Name` is matched to `org-b/Name` when that is the only copy on disk; the inventory decides at the match (`source.ownDirectory`, `inventory.go`) whether the directory is the row's, and withholds the path when it is not — `Artifact` still says the model is there, so presence, routes and status are unaffected. The organization a row claims is its `fetch.repo`'s, or its `model_name`'s when that is written `org/name`; a row that names none (a repo or name with no `/`) has nothing to contradict the match and keeps the path. One that names an organization keeps the path only for an omlx directory directly in the scanned model directory or in a folder named after that organization, and for an mtplx directory named `<org>--…` (one with no `--` names no organization and is kept). A name omlx has in more than one directory has no path at all (`scanOmlxModelPaths`), and a discovered entry, which has no row to contradict the scan, keeps the directory it was found in. A caller prints `Entry.Path` as it is and adds no check of its own: `modeladmin.Rows` copies it. Pinned by `TestInventoryPathIsTheModelsOwnDirectoryOrEmpty` (`internal/localmodels`) and, for the copy, `TestRowsShowThePathTheInventoryGives` (`internal/modeladmin`). `internal/modeladmin.Rows` builds the registry-centric list `wt model list` and the Models tab show from the same snapshot: unlike `catalog.Build` it hides nothing — a registered model that is not on disk is a `missing` row, a stopped pairing a `-` row, and a row with `fetch.local_path` takes its path from that key and its presence from a stat.

**`wt served <provider>`** (`cmd/wt/model_cmds.go` `runServed`) prints `ServedIDs` for omlx, mtplx or mlx_lm_server and exits 1 on a probe error, never an empty list. It has no caller in this repo; it is a diagnostic that answers with the key the registry names.

**omlx's `/v1/models` is not what is running (#201).** It lists every model in omlx's engine pool — the whole model directory, minus hidden ones — loaded or not; read as "running" it made every omlx model on disk a launch row, a sync route and a stop candidate for as long as the service was up, and made a start into an idle server ask to "replace" a model that was never loaded. `localmodels.ServedIDs(cfg, client, family)` is the one answer to "what is this server serving", used by both the inventory (`probeFamily`) and the lifecycle occupancy re-probe (`liveServed`) so they cannot disagree. For omlx, `localmodels.OmlxPool(cfg, client)` is the one reading (`Pool`: `Models` with `Loaded`/`Loading`/`Pinned`/`LastAccess`/`Size`, the `Ceiling` and `InUse` memory, and `SizesKnown`), carried on `Snapshot.OmlxPool` so the picker, the occupancy check and the eviction plan read the same data, and `ServedIDs` is its loaded-or-loading models. It asks `/v1/models/status` **first**, with the registry key — that endpoint reports on-disk ids (an aliased model is not mismatched), includes hidden models and says `is_loading`, so none of those cases needs special handling. It is behind omlx's management auth — it wants the server's API key whenever one is set, even on loopback, unlike `/v1/models` under `allow_unauthenticated_inference` — so the key is the registry omlx provider's `auth.secret_ref` (`localmodels.FamilyAPIKey`), sent only then. Only when status refuses or does not answer does the reading fall back to `omlxLoaded`'s `/health` (no key; the pool's `model_count`/`loaded_count` — zero loaded is "nothing" on a healthy (2xx) answer, while on the 503 omlx sends while pinned models preload, zero built still asks status) plus `/v1/models` (the list counts as the loaded set **only when it is as long as the pool** — a hidden model is counted, not listed), and then `SizesKnown` is false: the loaded set is known, the sizes are not. Mixed counts that status will not explain are an **error**, i.e. `StatusPartial` / `*OccupancyUnknownError`, never a guess. An omlx with no `/health` counts falls back to the list. mtplx and mlx_lm_server serve one model per process, so their list is the answer. A listed-but-unloaded omlx model is therefore a **start** row (the start loads it with `POST /v1/models/{id}/load`; omlx itself would load it on first request, but that hides a long load and a possible eviction). Two loaded omlx models are both routed, by sync and by a start alike (see Lifecycle).

**Loading is not loaded (#259).** `localmodels.Entry.Loading`, copied to `catalog.Row.Loading`, is true when omlx's status reading lists the model `is_loading` and not `loaded` (`source.isLoading`, which asks `Pool.Find`, so the name resolves to the pool model a load of it would act on). `Running` is true for it too, and everything that reads `Running` alone is unchanged: the model occupies the pool (`runningOthers`, `poolVictims`), is listed (`catalog.listed`), keeps its route (`desiredLocalEntries`) and is still offered by `wt stop` (`survey.StopState.Candidates`). Offered is not the same as stopped: omlx 0.7.0 answers an unload of a model mid-load with `400 Model not loaded`, `omlxUnload` then finds it still in the pool, and the stop fails with `omlx is still loading <id> and will not unload it mid-load` (the message goes on to name `wt stop omlx`) while the load goes on; a model that is loaded and still in the pool after an unload keeps `omlx still has <id> loaded`. `wt stop omlx` halts the service and the load with it. Three things read `Loading`. `catalog.Row.Ready()` is `Running && !Loading`, and `Row.Action()` launches only a `Ready` local row, so a loading row is a **start** row: `launchableModels` leaves it out, a `-M` pin starts it, and `sortRows` puts it with the start rows; its RUNNING cell reads `load`. `lifecycle.isRunning` is false for a loading target, so `start` goes on to `omlxLoad`, which returns when the model is loaded — omlx 0.7.0 holds the second load request open until then, and a 409 or 503 answer is polled — so a start on a loading model waits for the load. And `evictions` names no victims for a target that is itself loading: the start that began the load already asked, so the one that joins it asks nothing. Only the status reading can see a load. Under the fallback reading (`SizesKnown` false) a model mid-load reads as not running, as it did before, and is never `Loading`.

**A `-M` pin is looked up among ALL rows, discovered ones included** (`catalog.Find`). Its row decides: launch row → launch; start row → start flow; blocked → error with the row's reason; no row → `catalog.MissingReason` (`<id> is not on disk — pull or download it first`, or the llmbench command that starts it for a running-only family), else `catalog.SlotPinReason` for a `profile/<name>` pin a Usable profile holds (hidden by `-T`/`-F`, naming the flags set; or another agent's; `""` while the registry holds the `profile/` prefix), else "not in the eligible list". The TUI pin uses the same fallback; `wt start` and `wt smoke`, which build no profile rows, use it without `SlotPinReason`. A table with no rows at all — on entry or after a refresh — routes back to the agent picker with `catalog.NoRowsReason`.

**Non-TUI (`cmd/wt/resolve.go`):** with no `-M`, only launch rows are eligible (`launchableModels`) — rotation never hands an agent a server that is not up, a start row is never auto-selected (only a pin may start one), and rotation (`NextFromEligible`, which walks `cfg.Models`) never lands on a discovered row. `startForLaunch`: stderr progress, Ctrl+C cancels (second Ctrl+C exits wt), an occupied provider needs TTY `y/N` or `--replace`. In the TUI, `--replace` covers only the pinned row. Other providers' models loaded beside the target (#412) are a second question, which `driveStart` asks after the y/N, from the same `*OccupiedError` (`decideOthers`, `othersQuestion`, `askChoice` in `cmd/wt/start_others.go`): one line per resident (`Resident.Label`, `Resident.Figure`, its `sessionCounts`), a `cannot tell whether <family> at <origin> is serving a model` line per `OthersUnknown` family (`localmodels.FamilyOrigin`), then `[s/k/N]`, or `[k/N]` when no resident is `Stoppable`; read from `/dev/tty` through the `chooseOthers` seam, raced against Ctrl+C like the y/N. `s` sets `OthersAnswer{Decided: true, Stop: <every Stoppable id shown>}`, `k` `Decided` alone, anything else (EOF included) returns `cancelled — <ids> still loaded`. Both answers go in one retry; `AllowReplace` is set on it only when a same-family question was answered (never by an others answer), and `--replace` never answers the others. The root `--others=keep|stop` flag (`othersMode`, an `othersFlag` whose `Set` refuses any other value) answers unasked: `keep` sets `Decided` on the first call, so the engine reads no residents; `stop` takes the refusal and stops every `Stoppable` id. When stdin is not a terminal (`stdinTTY`; scripts, CI) and `--others` is unset the driver keeps them and prints one stderr line (`othersWarning`) and never asks or stops; only stdin counts, so `wt smoke <id> --json | jq` run from a terminal still asks on `/dev/tty`. The root launch reaches `driveStart` only when it skips the picker screens (`-W`, `--cwd`, outside a repository); a launch that opens them starts through the TUI, whose dialog asks the same question and which takes `--others` for the pinned row only ([tui.md](tui.md)). Each question is asked at most once and a refusal that asks only what was answered is a failure, so a start makes at most three engine calls (an `*OccupancyUnknownError`, which comes before the engine reads the others, then the others). A refusal not retried returns `stillOwed` as the y/N does, so a slot profile's owed restart is settled. Both paths use `lifecycle.StartErrorMessage`. No launchable match → "no cloud or running local model for agent X — start one with `wt -M <id>`".

- **`config.Provider.Origin` is the one reading of a provider's address** (#348): the probes (`localmodels.FamilyOrigin`), a route's `api_base`, a direct route and pi's `models.json` all go through it, so the server wt starts, the one it probes and the one it routes to are one. It is the `base_url` as written, except an `http` mtplx url with no port on `localhost`, `127.0.0.1` or the unspecified address (`0.0.0.0`, `::`) — the hosts the server `wt start` spawns with `--host 127.0.0.1` answers on, by the url's text — which is `config.MtplxPort` (8003): mtplx is the only server wt hands a port to, and `wt start` refuses any other mtplx url with no port (`lifecycle.MtplxAddressError`). A new reader of a provider's address goes through it (an ollama route's `api_base` is the `base_url` as written, #202). Pinned by `TestStartProbeAndRouteAgreeOnAProvidersAddress`; a test never binds or dials 8003 (`servedAt`, `onlyHost`).
- **Slot-profile rows are opt-in and are not model rows.** `catalog.Build` appends them only when `catalog.Input.SlotProfiles` is set, which `buildRows` (the agent's model picker), `resolveModel` (for a `-M profile/<name>` pin) and `wt profile show` do. `wt start` (`localRowsSnap`) and `wt smoke` (`smoke.walk`) never set it. A profile row is a `Row` whose `Model` holds only the id `profile/<name>` and whose `Profile` (`*catalog.ProfileRow`) holds the resolved slot models; `Row.Action` and `Row.BlockReason` return the profile's verdict (`catalog.ResolveSlotProfile`). **Code that reads a `Model` field other than `ID`, calls `ResolveRoute`, or hands `Model` to a launch or a start tests `r.Profile != nil` first** — `ResolveRoute` on the id-only model fails with `unknown provider`. `launchableModels` skips profile rows, so rotation and the single-launchable auto-launch never return one. Rows are hidden under `-T`/`-F` (`HideDiscovered`) and when the registry holds the `profile/` prefix (`catalog.SlotPrefixReserved`: a provider with id `profile`, or a model whose id begins with `profile/` under any provider). The profile's one local model is judged by the catalog's own policy: a one-model `Build` over the same snapshot, independent of the agent's eligible list.

## Lifecycle (`internal/lifecycle`)

The engine: `Start(ctx, cfg, Target, Options{AllowReplace, Progress, Out, RestartOwed, Others})` (`Out`: every line the start prints goes to this writer instead of stderr, the proxy restart's warnings included, so the text is complete once `WaitPendingRoutes()` has returned; `RoutesPending()` says whether a restart is in flight; the model picker passes one, `wt start` does not), `Stop`, `BeginStops` + `SettleRoutes` (one proxy restart per batch, #142; `BeginStops` returns a `StopBatch`, the only model-stop path, the stop loop's: every ollama stop of the batch is sent first, then each `Stop` waits under one bound the batch shares, so N models finishing requests cost one bound, not N; `Accepted` names the stops ollama accepted that a Ctrl+C left unreported, #379). Backends: ollama (`Shared`; daemon must already answer — wt never kickstarts it; a model stop is `ollama stop` pinned to the registry origin (`sendStop`), then `/api/ps` decides (`awaitUnload`): gone is success on any exit, listed after a non-zero exit is the CLI's error at once, and listed after exit 0 is re-probed every `pollInterval` for at most `ollamaUnloadTimeout`, 3 minutes (a 1,500-word generation queued behind another request kept a model listed for 55s), because ollama unloads a model with a request in flight only when the request ends; a model still listed at the bound is a `*StillFinishingError`, an error to every caller but the stop loop, which reports it as its own outcome; after `stopNoticeAfter` (2s) of waiting the stop gives one `StopNotice` (`waiting for ollama to finish a request in flight (up to …)`) to the function the caller put on the context (`WithStopNotice`), else as a route line; a probe that cannot answer, the first or a later one, leaves the verdict to the CLI's exit, and a cancellation is always returned as one), omlx (`Pool`: `omlx start` if down, then `POST /v1/models/{id}/load`; a model stop is `/unload`), mtplx (`Exclusive`; `mtplx serve` in its own session with the pidfile and log paths llmbench's mtplx backend also uses; torn down on failure/cancel). Used by the TUI start flow, `startForLaunch`, `wt start`, and `wt smoke`.

- **A keyed omlx (#256).** omlx started with an API key answers 401 to keyless `/v1` requests, chat completions included, unless it allows unauthenticated inference. The omlx warmup (`omlxWarm`) therefore sends `localmodels.FamilyAPIKey(cfg, "omlx")` as a Bearer token; the liveness probe stays keyless, since `probe` counts any HTTP answer, a 401 too, as "up". `env.warmup` ends on the first 401/403 with `*KeyRefusedError` (`KeySent` tells a missing key from a refused one) instead of polling out `warmupTimeout` — for every backend, though only omlx passes a key. `lifecycle.Warm` / `wt warm <provider> <model>` (`cmd/wt/model_cmds.go` `runWarm`) is that warmup alone, omlx only, which llmbench's omlx backend calls. **Keyless-inference mode.** An omlx with an API key and `allow_unauthenticated_inference = true` answers a keyless `GET /v1/models` and `POST /v1/chat/completions`, and `/health`, but refuses its management endpoints without the key: `GET /v1/models/status`, `POST /v1/models/{id}/load` and `POST /v1/models/{id}/unload` all answer 401. A registry with no `auth.secret_ref` on the omlx provider is the common local setup, so wt sends no key there. A start still works: when `/load` answers 401/403 and no key was sent, `omlxLoad` falls back to `omlxWarm`'s keyless chat completion, on which omlx loads the model (a server that refuses inference too answers that with `*KeyRefusedError`, at once). A key that was sent and refused gets no fallback. What wt cannot do in this mode follows from one fact: without the key wt cannot see **which** models are loaded in a partly loaded pool. `/health` gives counts only, so `omlxLoaded` returns an error ("omlx has N of M models loaded and would not say which") and the omlx family is `StatusPartial`. That is the ordinary state as soon as the pool holds more than one model and one is loaded; only an empty or fully loaded pool reads (`OmlxPool`'s fallback, `SizesKnown` false). While it is partly loaded: (1) no omlx model reads as running — in the picker, `wt served` (exit 1), or `wt stop`; (2) a second start normally gets `*OccupancyUnknownError`, the "cannot tell — replace?" prompt. The named-victims prompt is the exception, when every pool model is loaded and `poolVictims` names every other one; (3) wt cannot size the pool, predict evictions or report them, and `reconcilePool` does nothing without a status reading; (4) `wt litellm sync` does not correct the routes: it freezes an untrusted family (`untrustedFamilies` → `UntouchedFamilies`) and warns, so the route of a model omlx evicted stays until the pool is empty or fully loaded; (5) `wt stop <model>` ends at `model "<id>" is not running` (`unknown model "<id>"` for a discovered model with no registry row), because the stop candidates (`candidatesFrom`, `internal/survey/stop.go`) leave out entries that are not `Running` or whose family probe is untrusted — including a model wt just started through the fallback. Only when every pool model is loaded (a one-model pool included) does the stop reach `omlxUnload`, which returns an error that unwraps to `*KeyRefusedError` and names both ways out; it never falls back to stopping the service, because a model stop must not take siblings down; (6) a model omlx cannot fit or does not know fails the chat warmup with a non-401 error, which is polled for the whole warmup budget as on `main`, instead of the immediate `*NoRoomError` / not-found errors `/load` gives. The two ways out of all of it: set `auth.secret_ref` on the registry's omlx provider, which gives full pool behavior, or run `wt stop omlx`, which stops the service and removes the family's routes. Not covered: the LiteLLM route still carries `api_key: not-needed` (`internal/litellm/policy.go`), so a keyed omlx that refuses unauthenticated inference starts but is not reachable through LiteLLM.
- **Tenancy and the eviction plan** (`tenancy.go`, `evictions.go`). `TenancyOf(providerID)` says how a family holds models: `Exclusive` (mtplx — a start replaces the occupant, a stop stops the process), `Shared` (ollama — loads beside, nothing is displaced), `Pool` (omlx — loads beside and may evict, a stop unloads one model); every caller switches on it. `evictions(tenancy, family, t, snap)`, which the engine reaches through `resolveEvictions`, returns the running models a start is expected to displace plus `known`: `Exclusive` the one other occupant, `Shared` none, `Pool` the plan. The plan fits the target when `InUse + size(target) <= Ceiling - Ceiling*poolAdmissionMarginPct/100`; the margin (15%, one constant) exists because omlx begins evicting at `ceiling * soft_threshold`, not at the ceiling. `soft_threshold` defaults to 0.85 and omlx does not report it, so wt assumes the default; a prediction against the ceiling itself, or with a smaller margin, says "fits" on loads that evict. When it does not fit, wt walks the other loaded, unpinned models by `LastAccess`, oldest first, until the projection fits; a walk that never fits names every unpinned model, and omlx gives the final answer at load time. With `SizesKnown` false or no ceiling, every other loaded model is named (the loaded set is still known, so `known` stays true). A target absent from the pool reading has size zero. `known` is false, for any tenancy, only when the family's probe is not trusted — that alone yields `*OccupancyUnknownError`. A family whose probe was refused (`Snapshot.Down`) is the exception: nothing is serving, so the plan is known and empty. The engine still re-probes such a server before it acts (`resolveEvictions`), in case it came up since the snapshot. The prediction can miss, so the omlx start (`omlxLoad`, `omlxpool.go`) reads the pool before and after the `/load` and `reconcilePool` handles whatever omlx unloaded: it removes each such model's route (deferred; `e.restartOwed` makes `Start`'s one settling bounce apply it), prints `wt: omlx unloaded <id> to make room` (marked `(not predicted)` when the plan did not name it; never for a start that joined a load in progress, which made no plan of its own). It runs **on failure too**, since omlx can evict before a load fails. It acts only on a status reading (`SizesKnown`): the fallback reading names models by the list's ids, an alias included, so a still-loaded sibling can be missing from it, and a fallback or failed reading therefore changes nothing and leaves the routes to `wt litellm sync`. A refused connection during the load ends it at once (omlx went away, most likely out of memory) instead of being retried for the whole budget. omlx answers 507 with `*NoRoomError` (its `detail` names what holds the memory) and 401/403 to a key the registry named with `*KeyRefusedError`; a keyless load that is refused falls back to the chat warmup (see "A keyed omlx" above). The load carries the registry key and is bounded by `warmupTimeout`.
- **Never replaces without `AllowReplace`** (`*OccupiedError`, whose `Occupants` lists the Exclusive occupant or the Pool victims). If the probe cannot determine occupancy (a single-model server accepted then stalled, or answered unusably) it returns `*OccupancyUnknownError` rather than assuming empty; connection refused is an ordinary cold start. Failure wording: `message.go` (`StartErrorMessage`, `StageLabel`). **A failed start is printed once (#344).** `main` prints every command's error after `wt:`, and cobra prints it too, as `Error: …`, unless the command says otherwise; a failed start's message carries the server's log tail, so it came out twice in full. `wt start` and `wt smoke` set `SilenceErrors` (as `wt cloud-sync` does), so all of their errors are main's one line. The root command keeps cobra's print for its other errors: `resolveModel` marks whatever the start of a `-M` pin returned (`asStartError`: the driver's `*startError`, or a refused replace or a cancel wrapped in one, text unchanged) and `printOnce` in `runLaunchPath` silences cobra for that run only — the error line and the usage block the root command prints after every error, since a start that failed is not a usage mistake; `wt smoke` marks its start's error the same way (`asStartError`) and prints no usage after it. The TUI shows the message on the picker's status, under whatever the start printed, and returns no error; when the start printed something, those lines and the message under them are also printed on the terminal when wt exits (#275), and a start that printed nothing leaves the message on the status alone. The log tail an mtplx failure carries is `pidProcess.logTailLines(512)`: `logTail` reads one byte more than it shows, and everything up to the first newline is dropped, so the tail begins at a line start without the log being read (a tail with nothing but blank lines after that newline, or with no newline, is one long line and is kept as cut).
- **Other providers' models loaded beside the target (#412)** (`evictions.go`: `residentOthers`, `env.residents`; `lifecycle.go`: `Resident`, `OthersAnswer`, `env.stopOthers`). A start lists, from the one snapshot it already takes, every running model of another family (`Resident{Entry, Stoppable, PID}`; `Stoppable` is `CanStop`, so an mlx_lm_server pairing is listed and never stopped, and false for an omlx model still loading, which omlx refuses to unload), and a family whose probe cannot be trusted as `OthersUnknown`, never as empty; a `Down` family is empty and is not re-probed. An mtplx still loading refuses its port, so it reads `Down`: for a non-mtplx target `env.residents` asks wt's pidfile (`loadingMtplx`), lists a verified server as loading under its `--model-id` (`PID` set), and makes mtplx unknown when the process table cannot be read. Nothing is listed when the target is already running or already loading. `Options.Others` is the answer, and its zero value asks: such a start refuses with the one `*OccupiedError`, whose `Others` and `OthersUnknown` sit beside the same-family `Occupants` (either half may be empty, and `Error()` words each), touching nothing, so `RestartStillOwed` holds. `OthersAnswer{Decided: true}` keeps them; `Stop` names the ids to stop. The order inside `start()` is the refusals (same-family `*OccupancyUnknownError` first), then the approved stops (`StageStoppingOthers`), then the same-family replace, then the backend start. Each stop is the backend's `stopModel` (an mtplx still loading only `stopLoadingMtplx`), and its route removal goes through `onOccupantStopped` with the restart deferred, so Start's one bounce publishes it (an ollama model keeps its route, #179). A failed stop (ollama's `*StillFinishingError` included) returns `stopping <id> before starting <model>: …` and starts nothing, the removals already written still bounced; an approved id no longer loaded is skipped; a stoppable model the answer did not name while it named others appeared after the question and is kept, with `wt: <id> (<figure>) is also loaded; not stopped` (printed only when `Stop` is non-empty, and only for a stoppable resident: one wt cannot stop, such as an mlx_lm_server pairing, is not announced unless the answer named it: an approved model that is no longer `Stoppable`, an omlx model loading again since the question, is kept with the same line) (`Resident.Label`, `Resident.Figure`: `9.6 GB loaded`, `18.2 GB resident (omlx estimate)`, or `memory use unknown`, never 0). The non-TUI driver asks (see Non-TUI above); the TUI's `runStart` passes the answer its dialog or `--others` gave, unanswered on a first attempt. A start with `Decided` and no `Stop` (`--others=keep`, a keep answer) does not read the residents at all (no pidfile read, no process-table lookup).
- **Route hook** (`routes.go`): after a successful start/stop, `config.yaml` routes are updated via `internal/litellm` — a started model is routed under the catalog row's own id (`StartRouteChange` resolves `Target.ModelID`: the registry model with that exact id, else `litellm.DiscoveredModel`; `litellm.ModelFor`'s name match is the fallback only for a `Target` with an empty `ModelID`); an `Exclusive` start (mtplx) removes every marked route of the family (`Change.RemoveFamilies` — discovered siblings included, plus the family's registry ids; never a hand-written row; minus the started id), while a `Pool` start (omlx) adds the one id and removes only the ids of models it evicted (`poolRouteIDs`: the entry's own id when it is a catalog row id, plus the id of every registry model that names the model under any provider id of the family — `localmodels.FamilyProviderIDs`, so an `omlx` row and an `omlx-6bit` row naming one directory both go; the discovered id is the fallback, used only when none of those gave an id), never the family — clearing it is what once made sync and the start hook undo each other with two models loaded (#213); a stop removes with `routeRemoveModel` (`Exclusive`: the family; `Pool`: that model's ids, its loaded siblings keep theirs; `Shared`: nothing) and `lifecycle.Stop` of a whole provider with `routeRemoveFamily`; ollama adds one on start; stop leaves an ollama route in place (a pulled model stays routed — #179). The hook runs only when wt performs the start/stop. A launch row (already running, perhaps started outside wt) gets the launch-time route check instead, `lifecycle.EnsureModelRoute(cfg, model) bool` (#192): for a local model, or a registry cloud model sync would route (`litellm.CloudModels` — the repair for a config.yaml that lost its cloud rows; sync still owns keeping them current, so the cloud change is `Change.AddMissingOnly`: a cloud row that is there is not rebuilt, which would resolve the provider's `secret_ref` on every launch — a warning in a shell without the key, a rewritten `api_key` and a proxy restart in a shell with another — and a row that is missing is a build the picker's non-blocking form defers, `Options.DeferMissingAdd`, #253), it writes the model's route if it is missing, prints `wt: LiteLLM route for <id> updated` on stderr when it wrote **that model's own row** (`litellm.Outcome.Written`, set by `applyPlanned` from per-row digests taken around the write — only when the plan adds a row, since nothing else can produce a `routed` outcome; a `routed` outcome is reported for every row a change sets, identical or not, and `Result.Changed` is about the whole file), and restarts the proxy only if the file changed. A write that changed the file some other way (#206: another row's `api_base` repair, an enforced `litellm_settings` key) prints that repair's own line or, with nothing more specific already printed, `wt: LiteLLM config.yaml updated` (`reportEnsured`, shared by both forms of the check) — the restart wait that follows must not come unexplained. It is Add-only — it never removes a route (no `RemoveFamilies`; stale routes are left to the next start, stop or `wt litellm sync`), never starts or stops a model, never replaces a hand-written row whose name is not a registry model id (one named like a registry id is adopted as wt's own row by `litellm.ApplyChange`, the rule `wt litellm sync` applies — guide 04, `docs/guides/04-litellm-config.md`, Gotchas) and never fails a launch. Callers: `launchFilteredImpl` (`cmd/wt/launch.go`: `-M` pin, single auto-resolved model, rotation) and the picker's `proceedToLaunch` (`internal/tui/app.go`), both only when the launch's route goes through LiteLLM; `wt start <running id>` (then `wt: <id> is already running`) and `wt smoke` on an already-running target, both unconditionally. LiteLLM failures only warn; a missing `config.yaml` is silent. It comes in two forms, differing only in how long they will wait for the `config.yaml` lock: `EnsureModelRoute` (bounded at `ensureRouteLockTimeout`, 10s; `EnsureModelRouteTo(out, …)` is the same check printing to the caller's writer) and `TryEnsureModelRouteTo`, which attempts the lock exactly once and reports `done == false` rather than waiting — for the TUI picker, whose update goroutine cannot block (see TUI). That form also sets `litellm.Options.DeferMissingAdd`, so a cloud model whose row is missing is named in `litellm.Result.Missing` instead of being built there: building it resolves the provider's `secret_ref`, and an `exec:` ref runs its helper synchronously, bounded only by `execSecretTimeout` (15s), which is the same freeze by another route (#253). A write that defers a row saves nothing at all — not the `litellm_settings` or `api_base` repairs either — so the retry makes the whole change in one write and the proxy restarts once, not once per attempt. Both "not established" outcomes report `done == false` and print nothing; the retry, through the blocking form, does the work and reports. `litellm.ErrRegistryRedirected` is the one failure it reports itself, with `done == true`: no wait changes a refusal. `Start` reports `StageRouting` before the hook.
- **`config.yaml` write is synchronous; restart + readiness wait are async** in a goroutine tracked by `WaitPendingRoutes()`. Every process exit must call it (`cmd/wt/main.go`, plus `runAgentCmd`'s exit-code propagation and `wt smoke`'s failure exit, which bypass main), **and every path about to hand the model to an agent must call it first** (`startForLaunch`, `start_flow.go`'s `runStart` goroutine before it reports the start, `smoke.go` before the first `RunRow`, and right after the launch-time route check: `ensureRouteBeforeLaunch` in `cmd/wt/start.go`, and the picker's `checkLaunchRoute` in `internal/tui/start_flow.go`, which waits in a command behind `phaseRouting` and only when the check changed `config.yaml`) — the agent talks through the proxy, so proceeding mid-restart gets a refused connection or the old route table. On the CLI paths that wait is the only stretch of a launch with nothing else on stderr to show for it, so `ensureRouteBeforeLaunch` announces it and repeats the line with elapsed time every `routeWaitInterval` (`waitForProxyRestart`) — the counterpart to the picker's `phaseRouting` screen. Which paths wait is the check's own return value: the write is the only thing that restarts the proxy (`restartIfChanged`), so an unchanged route — the common launch — prints nothing and its `waitPendingRoutes` returns at once.
- **A start is confirmed after the proxy wait** (`confirm.go`, #343). `Start` returns as soon as `config.yaml` is written; the long part of "updating LiteLLM routes" is the caller's `WaitPendingRoutes()`, and a `wt stop` from another terminal lands there, after `Start` returned nil. So a `Start` that returned nil is followed by one call, `lifecycle.SettleStart(ctx, out, cfg, target)` (#349), which is the whole sequence: `WaitPendingRoutes()`, the check (`confirmStarted`, unexported), and after a `*StoppedError` `WaitPendingRoutes()` once more, for the restart the check's route removal started — so `out` is complete, and no restart is running, when it returns. Each package reaches it through one seam its `TestMain` stubs: `lifecycleSettleStart` in `cmd/wt`, called by `settleStart` in `cmd/wt/start.go`, which is every non-TUI start (`wt start`, `wt start --replace`, the no-argument picker, `wt smoke`, a `-M` launch) and passes a nil writer, so the check prints to stderr; and `settleStart` in `internal/tui`, called from the start's own goroutine (`runStart` in `internal/tui/start_flow.go`, never `Update`) with the writer it gave `Start` as `Options.Out`, so the removal's lines and its restart's warnings join the start's output (see TUI). **`SettleStart` drops the caller's cancellation itself** (`context.WithoutCancel`; the context's values are kept) and callers hand over the context they have: Ctrl+C in the proxy wait leaves the CLI's signal context done, a cancel that lost to a start that finished anyway leaves the picker's done, and under a done context the ollama probe, which reads it, would settle nothing and report a daemon that is gone as running, and the route removal would give up on a `config.yaml` lock another wt holds (`TestSettleStartChecksUnderACancelledContext`, `TestSettleStartRemovesTheRouteUnderACancelledContext`). The two waits take no context. The check makes one request to the provider's server (`env.startedGone`) and returns `*StoppedError` only for an answer that settles it: mtplx (`Exclusive`) refuses the connection (`ECONNREFUSED`) or answers `/v1/models` without the model; omlx (`Pool`) refuses, or `localmodels.OmlxPool` finds the model neither loaded nor loading (the fallback reading lists only loaded models, under names that can be aliases, so a model missing from it settles nothing); ollama (`Shared`) refuses. An ollama model that was only unloaded is not gone: its route follows the artifact and the next request loads it. A timeout, an error status or a cancelled context is never "gone". On `*StoppedError` the model's own route is removed (`routeAfterGone`: the id `routeModel` gives, on a Pool `poolRouteIDs`), whichever of the stop and the start wrote `config.yaml` last, so a stop's family removal followed by the start hook's add does not leave a route to a dead port; never the family, because an mtplx that answers with another model is another start's server. `StartErrorMessage` words it `<id> is not running: …`, not "failed to start". The removal's proxy restart is asynchronous like any other, and `SettleStart` waits for it before it returns, for both callers (the CLI used to leave it to `main`'s wait at exit). A new caller of `Start` that goes on to use the model, or to say it is running, calls `SettleStart` after a nil return and nothing else: `ConfirmStarted` and `ConfirmStartedTo` are no longer exported, so the check cannot be made without the waits around it.
- **Route output belongs to the operation:** everything `routes.go` prints (the `updated` line, every warning, the async restart's included) goes through one mutex-guarded helper, `routePrintf(ctx, …)`, to `routesWarn` (stderr) — unless the operation's context carries its own writer (`withRouteOutput`), which is how `EnsureModelRouteTo`/`TryEnsureModelRouteTo(out, …)` send one check's output to the caller, `Start` everything it prints to `Options.Out`, and `SettleStart(ctx, out, …)` its check's route removal's. The writer rides on the context so that it follows the check into the restart goroutine (`context.WithoutCancel` keeps values) and nothing else: an unrelated operation's restart still in flight keeps printing to stderr instead of being collected as this check's (the process-wide `SetRouteOutput` redirect this replaced did exactly that — pinned by `TestRouteOutputIsNotSharedWithAnotherOperation`). `out` is safe to read only after `WaitPendingRoutes()`. The TUI picker is the one caller of all three (below) — stderr is not reliably visible under the alt screen.
- **That goroutine runs on `context.WithoutCancel(ctx)` on purpose.** Callers `defer cancel()` the instant the hook returns; inheriting cancellation means the restart never runs. Don't "restore" cancellation propagation — `TestRouteRestartSurvivesCallerCancelAfterReturn` and `TestStartWrapperRestartSurvivesCancelledCaller` pin it. Restart warnings are therefore always printed.
- **Readiness wait:** the probe, the restart and the wait are `litellm.Bounce.Run`, the sequence `wt litellm sync`'s default restart runs too (#382), here over the package's `probeProxy`/`restartProxy`/`waitProxy` seams. Before the restart, `litellm.Listening` probes `/health/liveliness` once (1.5s; false only for refused/unresolvable, so a slow or 503 proxy counts as present). `WaitReady` (up to 30s) runs only if the hook restarted the proxy **and** that probe found a listener — a stopped proxy costs nothing. The 30s starts when `litellm.RestartContext` returns, which is after the old process has exited: the default restart first gives a request in flight up to three minutes to finish (`proxyDrainTimeout`; see [LiteLLM routes](litellm-routes.md)), so the goroutine, and with it `WaitPendingRoutes()`, can run about three and a half minutes. Its one line during that wait (`wt: the LiteLLM proxy is finishing a request in flight; …`, after 2s, a `litellm.Notice` marked `InProgress`) reaches `routePrintf` through a function the restart's context carries (`litellm.WithRestartNotice`, set by `withRestartNotice`), so it follows the operation's writer like the warnings. A writer that is a `RestartNoticer` gets each notice itself instead of a printed line: the TUI shows the in-progress one on the screen that waits (`drainView`), where printed into its notes it would be read only once it was no longer true.
- **A request cut off at the bound is not a failed restart.** `RestartContext` reports it as a notice, not a warning, so every warning it returns is a failed restart (`restartFailure`) and nothing matches on a warning's text. `bounceProxyAsync` and `RestartProxy` print the notice, still make the readiness wait, and record the restart as one that worked: the proxy was restarted and the new routes are live, so `ProbeProxy` must not refuse the next slot-profile launch over it.
- **Replace (`Exclusive`):** the occupant's route is removed as soon as it's stopped (`env.onOccupantStopped`, wired only by `defaultEnv`) so a start that then fails can't strand it; that write uses `litellm.Options.NoRestart`, and `Start` owns one settling bounce (`routeAfterStart`, or `bounceRoutes` on failure) — one restart per replace, not two; a `Pool` eviction's removal is written the same way (`reconcilePool`), so a start that evicts also costs one restart. `bounceRoutes` writes nothing, so it has no lock wait to bound — it only triggers the async, detached restart (`bounceProxyAsync`).
- **The slot-profile seams** (`profile_routes.go`). The launch-time check (`EnsureModelRoute`) is single-model, restarts on change and never fails a launch, so a profile launch has its own calls. `EnsureModelRoutes(ctx, out, cfg, models, owedIn)` writes each distinct model's missing route with one locked write per model (`applyRoutes` with `NoRestart`; the changes cannot be one `litellm.Change`, since `AddMissingOnly` is a flag on the whole change and cloud and local slots need different values), never restarts on success, and returns whether a restart is owed. It returns, as a `*RouteEnsureError` naming the model, what the single-model check swallows: a missing `config.yaml` (`litellm.ErrMissing`), `litellm.ErrRegistryRedirected`, a lock that was not free in time, a row's own `Outcome.Err`, and a model `modelRouteChange` declines (`ErrNotRoutable`). On an error it settles what was owed with one asynchronous restart, so a route written before the failure is not left unpublished. `Options.RestartOwed` hands that debt to `Start`: a successful start restarts once for both, a failed one bounces once, and a refusal that touched nothing leaves it owed (`RestartStillOwed(err)`). `RestartProxy` restarts and waits, returning the failure `bounceProxyAsync` only prints (`RestartProxyTo(ctx, out, cfg)` is the same call printing the restart's two notices to `out`; the TUI passes its notes buffer, since stderr is under the alt screen); `ProbeProxy` requires a 200 from the liveness endpoint (`WaitReady`, not `Listening`, which counts a timeout as an answer). Two more rules bind a slot-profile launch. `internal/lifecycle` remembers the outcome of the most recent proxy restart attempt in the wt process (`lastRestart`: `RestartProxy` and the asynchronous `bounceProxyAsync` both record it), and `ProbeProxy` refuses with `the last LiteLLM proxy restart failed, so routes written since may not be live: <cause>` until a later restart succeeds or a new wt process starts. Both launch paths call `WaitPendingRoutes` immediately before `ProbeProxy`, since a restart still in flight has recorded no outcome.

- **wt signals a process only after identifying it** (`mtplx_loading.go`): the one stop with no port to go through is an mtplx still loading, found by wt's pidfile. A pid is never enough — alive, the user's own, an mtplx server on the provider's port by exact argv, and the recorded start time when there is one, checked again before SIGKILL. A process that is exiting (`kern.procargs2` gives `EINVAL` while the kernel frees its memory) has no argv: it is never identified, never signalled, and a stop waits for it instead of killing it. The pidfile stays a bare pid (llmbench shares the path); wt's start record is `<pidfile>.wt`; both are read only as the user's own regular files (`readOwnFile`). Both are removed when the server they name is confirmed gone, and only then: by the stop of a loading server, and by the ordinary `mtplx stop` path, which identifies the pidfile's process before the stop and waits for it to be gone after (`forgetStopped`). Ctrl+C after a signal was sent is a `*StopInterruptedError`, which `wt stop` reports as "was sent SIGTERM", never "was not stopped".

## Rotation (Go)

Global rotation: each successful single-model launch records its model id in `~/.config/agent-wt/rotation.state` (atomic write); the picker cursor lands on the model *after* it (`FirstAfter`, shared by the picker and `wt rotate`). Launch paths call `rotation.RecordFor(agent, id)`, which also writes the same id to `~/.config/agent-wt/last-picked.state` and appends the agent-tagged usage event to `~/.config/agent-wt/usage.jsonl`. Rotation positions the cursor only when a last-launched registry model exists (else first launchable row) and never advances onto a discovered row.

**The marker and the rotation pointer are two files.** `rotation.state` is one bare registry id, read whole by `Last()`, so it cannot carry a second value without breaking an older binary. `last-picked.state` (one line, a row id) is where the picker's `> ` marker comes from (`LastPicked()`, which falls back to `Last()` when the file is missing or empty). A slot-profile launch calls `RecordProfile(agent, "profile/<name>")`: it writes `last-picked.state` and the usage event and never touches `rotation.state`, so the marker moves and the rotation position does not. A single-model launch writes both, so a stale profile marker never survives it.

- **The sort order is also the default selection.** `newPickModel` (the standalone `wt smoke`/`wt start` pickers) never calls `Select`, so its highlighted row is index 0; `enterModelPhase`'s no-rotation fallback picks the first actionable row. Native-first (#172) therefore makes a native model what a bare Enter launches there — deliberate, and pinned by `TestPickStartModelDefaultsToNativeRow` / `TestEnterModelPhaseNoRotationDefaultsToNativeRow`. Changing `sortRows` changes what Enter picks; don't add a display-only rule to it without deciding the default too.
- The last-launched row gets a `> ` prefix — **plain ASCII on purpose**: Unicode geometric shapes are East Asian Ambiguous width and misalign CJK terminals.
- The leftmost column is the live "in use" count from `refcount.Store.Counts` (2-rune prefix, clamped at 9), before the rotation marker.
- Columns: FAMILY, MODEL, TIER, LOC, STATUS, RUNNING, COST, 1D, 7D, 30D, SURVEY. TIER is the model's advisory tier from modeltiers' `tiers.toml` (`internal/tiers`, read once per table by the `loadTiers` seam in `buildRows`, looked up by `ProviderID` + `ModelName`; `tableRow.tier`): the code and the rounded aligned score (`S44`), the code alone with no score, `-` for an unrated or unlisted model, a slot-profile row, or a missing or unparseable file. RUNNING reads `run`, `load` (omlx is still loading the model, `runningText`) or `-`. COST is the price in force at the instant the table was built (`tableRow.price`, which is `config.ModelCost.PriceAt` over the model's `cost.time_prices` rows, resolved once per row by `tableRow.pricedAt`; `costCell`), followed by `~` when the model has such a row that is applied (`tableRow.timePriced`, from `ModelCost.TimePriced`; a row the registry's validator refuses is passed over, `TimePrice.Problem`), and the heading is then `COST (~ varies by time)` (`costLegend`, used only when the column is already that wide). `wt smoke`'s picker has no agent context: SURVEY is empty and usage uses model-level `Counts`.
- Sort: three bands. Native models first (#172); then slot-profile rows, in file order (`ProfileRow.Check.Index`); then every other row. Within the first and last band: cloud + running local by cost (output then input price, each the price in force when the table was built, so a time-priced model sorts by what it costs now; local/subscription-only = $0; no-data last), then 7-day usage; local that is not running, or still loading, alphabetical. Native-first is a *partition*, not an exemption: native rows still fall through to the group rules among themselves.

- Starting cursor: when the last-picked row is a profile row that is present and not blocked, the cursor starts on it; profiles do not rotate. Otherwise today's rule, read from `rotation.state`: the next actionable registry model after the pointer (`NextFromEligible` over the actionable rows that are not profile rows), else the first actionable row in sort order, profile rows included.
- TUI callers fetch the agent's full catalog once (`cfg.ModelsForAgent`), narrow it with `cfg.EligibleModelsIn` (single-traversal filter), and pass it to `enterModelPhase`.

```bash
go run ./cmd/wt rotate code    # debug helper: print the model after the last-launched in the "code" tag group
```

## Start/stop (`wt start`, `wt stop`)

`cmd/wt/model_cmds.go`; user-facing behavior in [docs/wt-start-stop.md](../wt-start-stop.md). Code notes:
- `wt start <id>` resolves through `catalog.Find` over `localRowsSnap` (locals on disk or running, registered or detected, one snapshot), falling back to `catalog.MissingReason` for an id with no row; no-arg uses `tui.PickStartModel` via the `pickStartModelTUI` seam.
- `wt stop` uses `survey.ReadStopState` (the `stopState` seam), `survey.StopEntries` (shared stop loop), and `survey.PickerWith(..., Options{IncludeInUse: true})`; the no-arg picker probes once and reports whether it had anything to offer and which families it could not read (`stopPickerAll`), so `no running local models` is printed only when `StopState.Unknown()` is empty and no pidfile behind a refused port names a server still loading or a pid wt could not inspect (`StopState.Loading()`, see "A loading mtplx" below). `StopState` is one inventory round and one read of the live sessions: `Candidates` (every running, trusted, stoppable model — a family whose probe is not trusted, `lifecycle.ProbeTrusted`, contributes none) and `Families`, keyed by `localmodels.Family`: `Untrusted`, `Down` (`Snapshot.Down`, a refused connection) and the family-wide `Sessions`/`Users`, counted from every live refcount entry (`refcount.Live` after a `Sweep`) and resolved by `modelFamily` — the registry model's provider, else the id's prefix, so a model that does not read as running, an `omlx-6bit` row and a discovered model no registry lists all count. `Families` also carries `Probed`: false for a family the inventory did not probe (a provider row with no `location` and no local model) or that is known only from a live session, whose zero `Untrusted`/`Down` are nobody's answer. **A halt (`haltProvider`) asks with the family's count, never the candidates'** (#307): `haltsWhole` says when a stop is a halt — a `Pool` always, an `Exclusive` provider when it has no candidate, was `Probed` and its port did not refuse (#308: `/v1/models` answered with an error, an empty list or not within the probe's 2s), or when it is `Down` and `FamilyState.Loading.PID` names a verified server (an mtplx that has not opened its port yet — see "A loading mtplx" below), a `Shared` provider never — and when the family is `Untrusted` the question adds `, and wt could not tell what it has loaded` (`unreadClause`); a family that is `Down` serves nobody, so its halt counts no session and asks nothing (`haltImpact`) — unless it is loading, when the family's sessions count and the question says `is still loading (pid N)`. A `Shared` family that is `Untrusted` and not `Down` cannot be stopped blind (wt leaves ollama's daemon up): `errCannotTell`, exit 1, instead of `nothing running on ollama`. `wt stop <provider>/<name>` is unchanged: with no candidate of that id it is `model "<id>" is not running` (plus a pointer to `wt stop <provider>` when that provider is loading: wt records no model for the loading process, so a model id stops nothing; and `errLoadingUnknown` instead when `Loading.Err` is set, since "not running" is then not known). A bare provider is validated against `stoppableProviders` (what `lifecycle.CanStop` accepts). A target on mtplx (`Exclusive`) widens to every running model of that provider (`withFamilyCollateral`); omlx models are never widened — `wt stop <omlx model>` unloads just that one (`POST /v1/models/{id}/unload`, the service stays up) and `wt stop omlx` calls `lifecycle.Stop`, which runs `omlx stop` and clears the family's routes. Targets stopped model by model go through `confirmStop` with `stopImpact` (sessions summed, an `Exclusive` provider counted once); `--yes` skips. That includes an mtplx stopped through a candidate: the process goes down either way, but there the count is the candidates', so a session recorded on an mtplx model that is not the one listed is not counted. Bare `wt stop` (`unreadHint`) names `wt stop <id>` / `wt stop --all` for an unread family only when its tenancy is not `Shared`, and prints it as a note after a picker that did list models. `stopArgError` holds the command's two usage mistakes (unknown provider, no TTY for the picker); past it `stopCmd` sets `SilenceUsage`, as `--all` does.
- `wt stop --all` (`runStopAll`) asks once — `stopImpact` over the candidates it stops one by one plus the family-wide count of every family it halts — runs those candidates through `survey.StopEntries`, then halts one provider per halted family (`haltProviders`, in id order, so mtplx before omlx; `omlx` and `omlx-6bit` are one service) through `haltProvider`, the halt `wt stop omlx` uses. A pool is halted whether or not it has a candidate; an `Exclusive` provider is stopped through its candidates when it has any and halted when it has none, was probed and its port did not refuse or a verified server is loading behind it; a `Shared` provider is stopped only through its candidates, and one whose probe was neither trusted nor refused (`unreadShared`) is a failure joined into the exit status after everything else was stopped. One signal context (`startSignalCtx`) is installed before the model loop and spans the command: the loop's own context ends with it, and `survey.ErrStopCancelled` from the loop, or this context cancelled after it, ends the command before any halt (`notHalted` names the servers left up). Before every halt that follows the loop or another halt it calls `waitPendingRoutes`, because the loop's settle and each halt's route removal start a proxy restart and nothing else orders them — so a `--all` that stops an mtplx model and halts omlx restarts the proxy twice. Past the argument check the command sets `SilenceUsage`: nothing it returns from there is a usage mistake.
- **A loading mtplx** (`internal/lifecycle/mtplx_loading.go`, `procinfo*.go`; #308). mtplx loads its weights before it opens its port, so a load in progress is `Down` and `mtplx stop --port` cannot reach it. For a `Down` family `stopState` asks `lifecycle.LoadingServer` (the `stopDeps.loading` seam), which reads the mtplx pidfile and returns a `Loading`: `PID` (a verified server), `Stray` (a live process that is not verifiably one — a note, nothing signalled, exit 0) or `Err` (the process table could not be read — `errLoadingUnknown`, exit 1). Everything else — no pidfile, one that is not a regular file this user owns (`readOwnFile`: opened with `O_NOFOLLOW`, checked on the descriptor; the pidfile and the record are in `/tmp`, where another user can create either while it is absent), an unreadable or garbage one, pid ≤ 1 or wt's own, a dead, zombie or exiting pid — is the zero value, "nothing running"; a stale pidfile is never deleted by a read, as `wt start` never prunes one. **The pid alone is never trusted** (`loadingMtplx`, `notMtplxServer`, in this order): the process exists and is not a zombie; its uid is wt's; if wt recorded a start time for that pid it matches; its argv is an mtplx server on the provider's port (`isMtplxServer`). The argv rule compares whole arguments at fixed positions, because the pid wt spawned has two forms: `sh|python <path>/mtplx serve …` (what wt passes; `mtplx` itself as `argv[0]` is accepted too), and — after `mtplx serve` calls `os.execvpe` in the same pid, which is the process that loads the weights — `python [-opts] -m mtplx.server.openai …` (verified against mtplx 2.12.0, `commands/public.py`); either must be followed by `--port` and the port as two arguments. A future mtplx that changes that module name fails the rule, and wt then reports a `Stray` and stops nothing. The interpreter's name is compared without case (`Python.app/Contents/MacOS/Python` is what a framework Python re-execs into). The process table is read through one seam, `describeProc` (`realDescribeProc`: `sysctl kern.proc.pid` and `kern.procargs2` on macOS — exact argv, since `ps` joins arguments with spaces and mtplx's own paths contain one; no implementation elsewhere, where it errors). **`EINVAL` from `kern.procargs2` is `procInfo.exiting`, not an error** (`procArgv`): after a fatal signal a process stays in the table, not yet a zombie, with no arguments to give while the kernel frees its memory — measured at 7 to 13 ms per GB, so 200 ms and more for an mtplx. An exiting process has no argv, so it is never identified and never signalled; `waitGone` keeps waiting through it, and signals go through `signalProc` (`syscall.Kill`). **What wt records at start**: the pidfile stays a bare pid — llmbench's backend (`llmbench/src/llmbench/providers/lifecycle/backends/mtplx.py`) reads and writes the same path with `int()`/`str(pid)` — and `recordStart` writes `<pidfile>.wt` beside it, atomically: `{"pid":N,"started":"<sec.usec>"}`. The start time survives exec, so it identifies the process across both argv forms; a record whose pid is not the pidfile's, or that is not this user's own regular file, is ignored (llmbench started the server, or an older wt did), and the command line then decides alone. The record also says wt created the process group (`spawn` sets `Setsid`): `stopLoadingMtplx` signals the group (`-pid`) only then and only while the pid still leads it, the pid alone otherwise. **The stop** (`lifecycle.StopLoading`, the `stopLoading` seam in `cmd/wt`, reached from `haltProvider` when `Loading.PID > 0`) re-reads the pidfile and the process itself and refuses unless they still name the pid the question was asked about; SIGTERM; waits `stopGrace` (10s, `mtplx stop`'s own grace) for the process to be gone (`waitGone`: no such pid, a zombie, or another start time); re-reads it and sends SIGKILL only if it is still the same process and still an mtplx server — to the group only if it still leads it — or, if the process is exiting, sends nothing; waits `stopTimeout`; removes the pidfile (if it still names that pid) and the record; then removes the family's routes as `Stop` does. **The ordinary stop** (`mtplxBackend.stop`, `mtplx stop --port`) removes the same two files through the same helper (`forgetMtplx`), under the same care (#343): `loadingMtplx` is asked before `mtplx stop` runs, while the server is still there to be identified, and `forgetStopped` removes the files only when that reading verified a server and `waitGone` (up to `stopTimeout`) then shows that process gone. No verified server, a process table that cannot be read, a process still exiting when the wait ends, or a pidfile that names another pid by then: nothing is removed and the stop is still a success, since the port closed. It signals nothing. Any stop it cannot confirm is an error, including a process that is still exiting when the second wait ends (not killed: wt can no longer verify it). A context that ends during either wait is a `*lifecycle.StopInterruptedError` naming the pid and the last signal sent: `haltCancelled` in `cmd/wt` then says the server was signalled and how to check, instead of `notHalted`'s "was not stopped", and names the halts that were to follow as not stopped. The pidfile, the record and the routes stay as they were. `WT_MTPLX_PIDFILE` names another pidfile (log and record follow it) for tests and for a built wt run against scratch state; llmbench does not read it. `errLoadingUnknown` takes the caller's ending, as `errCannotTell` does: `nothing was stopped` for `wt stop mtplx` and `wt stop mtplx/<model>`, `nothing was stopped there` in `--all` (which has stopped everything else by then), none after a picker that listed models. **Bare `wt stop`** gets `StopState.Loading()` back from the picker as a third result (`survey.PickerWith`, the `stopPickerAll` seam) and prints, through `pidfileFindings(..., pickerNote)`, `wt: mtplx is still loading (pid N) — "wt stop mtplx" or "wt stop --all" stops it` in place of `no running local models` or after the picker; it stops nothing there. Not covered: the TUI's stop key, a second `wt start` and `wt start --replace` still see a loading mtplx as an empty port (a second start overwrites the pidfile, so only the newer server can then be found); an mtplx started by hand has no pidfile; and the check and `kill(2)` are separate calls, so a pid reused in between would be signalled — with a start record the checked process is known to be wt's, with a pid-only pidfile the command line is all there is.
