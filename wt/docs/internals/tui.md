# wt TUI

Internals reference for `wt/`, reached from [`wt/CLAUDE.md`](../../CLAUDE.md). Backticked paths are relative to `wt/` unless they start with `../`.

## TUI (Go)

`internal/tui` is the Bubble Tea shell (`tea.WithAltScreen()`). Phases: worktree picker → agent+command picker → model picker → launch (plus the catalog, starting, launching and replace-confirm screens; every model the picker shows comes from the model server, below). Each picker is skipped when its selection is already resolved (`prePath` from `-W`/`--cwd`/outside-repo, `-A`, `-M`; a pinned row the server must start starts at once). Every picker uses `ThemedListDelegate` — production code never uses `list.NewDefaultDelegate`. The worktree picker is not a bubbles list: it is the row list `wt cleanup` shows, in launch mode (below).

> **The worktree picker is a view over `internal/cleanup`'s rows** (`picker_rows.go`; the user-driven cleanup design's "The list"). `Init` returns `loadPickerCmd`, which resolves the repository root once (the `findRepoRoot` seam, #390) and runs `loadRowsCmd`, which fetches nothing on open: `cleanup.GatherFacts` (the facts stage — worktree list, refs, base and claims, plus the git-free hard blockers `factBlockers`/`nestedBlockers` so the first paint already locks primary, current, locked and nested rows; no gates, no ladder, no gh: every detail cell is `-`, every row is `Pending`, nothing is removable — `pickerInputs`: this process's claim, four gh calls at a time once the PR stage runs, no protected artifacts, `Fetched: FetchResult{NotAttempted}` so the header reads `fetch: not run (this list does not fetch when it opens)`) and `Classify`. The one fetch is the user's `F` (`refreshRowsChosenMsg`): the same load re-runs with `worktree.FetchRemotes` first (`git fetch --all --prune`, 5s — what runs when the per-call `GatherInputs.FetchRemotes` seam is nil, as in production; a test's hook runs in place of it as the counting seam, never alongside it), its ok or failure recorded in `Fetched` so the header reads `fetch: ok, …` or `fetch: FAILED (…)`, and `gotRows` swaps the fresh facts in with `withReport` (filter, cursor and scroll kept) and dispatches that load's fill, as at open. The header's last line is the refresh note: `refreshed 3m ago` / `not refreshed here`, from `worktree.LastFetched` at the list's root (`refreshedNote`; the stamp is read by the load command, off the update loop, carried in `rowsLoadedMsg`/`cleanupRefetchMsg` and kept in the list's opts so a report swap never reads git; a fetch recorded as failed gets no note, since git truncates FETCH_HEAD when a fetch starts and the stamp would contradict `fetch: FAILED`). While `F` runs the header adds `fetching every remote… (up to 5s)`, and the not-run line says `press F to fetch`. `rowsLoadedMsg` builds the row list (`cleanup_list.go`) in launch mode: "+ New worktree…", then every row in `cleanup.ListOrder` — the root first, then the local worktrees and branches together and the remote-only rows after, each group by display name, with no kind headings — the default branch, held and in-use rows included, each launchable. The cursor starts on the innermost worktree holding the caller's directory (`deepestCurrent`; the root when standing in it). A row's line carries only what warns (`rowTags`: `dirty`, `upstream gone` on a row that is not proven, plus the root's drift badge); the identity facts — the root, the current worktree, a session holding it, its age — are the detail screen's (the PR and its state read in the `PR#` column), and the verdict column is its short word (`verdictWord`: `safe`, `check`, `work`, `locked`, `-` while pending). `gotRows` dispatches `loadRowFillCmd` (stage 2): `rowsFilledMsg` carries `cleanup.FillDetails`'s report (gates, records, ladder, own-repo — the PR lookups still skipped) and its message swaps the report in through `withReport` (the pending-tick rule: a pending row is unseen and takes the new default) and applies the `RemoveFuncs` built from the FILLED snapshot (`swapRemoveFuncs`) — nothing is removable from a facts-only report, and `rowKeys`/the handlers say so until the fill lands. A fill for a superseded load drops by `rowsGen`, one dispatched before an `F` refetch drops because the refetch spends `fillGen`, and a failure is one `fill failed:` status line on the still-showing facts (F can still re-read). The filled report has `?` in the `PR#` column of every row whose PR is unknown; `loadRowPRsCmd` (stage 3) then runs `cleanup.FillPRs` off the update goroutine, classifies again and clears the PR tag of a branch whose name was reused after its PR ended (`dropStalePRTags`: an ended PR whose head is neither in the tip nor ahead of it, by `merge-base --is-ancestor`; #389, #451), and `rowPRsLoadedMsg` swaps the report in with `withReport` (cursor on the same row by kind, ref, path and name; filter and scroll kept). `rowsGen` drops a fill for an older load. Enter on a row emits `rowChosenMsg`, which the app turns into the `selectedEntryMsg` the launch flow has always taken (`entryOfRow`: the root and worktrees by path, a local branch as a path-less branch entry whose worktree the launch gate creates at the commit point (`launchCreation.ensure` → `Plan.Ensure`), a remote-only branch as `origin/<name>` with `RemoteBranch`). `n` and Enter on "+ New worktree…" emit `newWorktreeChosenMsg` (the new-worktree prompt). `/` opens the filter (`filterKey`): while it is typed every printable key, `q`, `n`, `x` and `j` too, goes into it; it matches the row's name, branch, tags and `PR#` column cell (so `#383` finds its PR's row); enter keeps it, esc clears it. `x`, `d`, `o`, `r` and `R` act on the highlighted row through the list's own confirm flow and the `RemoveFuncs` the app builds per load (`removeFuncsFor`, over the `RemoveFuncsBuilder` cmd/wt-session hands in); a PR fill landing mid-flow defers the funcs swap to the list's return to rest (`swapRemoveFuncs`), and `r`/`R` end the picker session (`finishRowSession`; no re-entry). The picker's gather sets `OriginRows` so `o` can find the origin ref. Enter still launches. PR lookups are `cleanup`'s (`gh pr list --head <branch>` per branch, own repository from origin's URL); the seams are `cleanup.StubPRListForTest`/`StubPRBaseListForTest` (both stubbed to fail by `internal/tui`'s `TestMain`) or `GatherInputs.PRList` per call.

Start-on-select (`start_flow.go`, `remote_start.go`): Enter on a start row → `phaseStarting`, a start job on the model server (next note). The in-process start (`runStart` through `lifecycle.Start`, `settleStart`, the routing stage, `startOutput`'s engine lines, the `sessionCounts` refcount read) was deleted with Task 19. `*OccupiedError`-shaped questions arrive as the job's `modelapi.Problem` and open `phaseReplaceConfirm` (Cancel is the default; `problemHeader` lists every model the start would stop or, on omlx, unload, one occupant per line under `Starting <id> will stop:`, wrapped to the terminal by `replaceFrames` above the list, the key hints dropped before any of it on a short terminal, and a question still too tall keeping its first lines and a `…` line). **The same dialog asks about other providers' models** (#412): `Also loaded, by other providers:` under any `will stop` lines, one line per resident (`Resident.Label() — Resident.Figure()`), then one line per family the server could not read. Its choices (`buildOthersChoices`): `Cancel` first and default, `Start and keep them` (`othersKeepChoice`), `Stop them, then start` (`othersStopChoice`), absent when no resident is `Stoppable`, and withdrawn while the question is cut (`replaceState.syncStopChoice`, from `fitLists` on every message: a stop approves every stoppable model listed, so it is never offered while some of them are off the screen; `TestOthersDialogOffersStopOnlyWhenEveryModelShows`, `TestOthersDialogStopFollowsTheTerminalSize`). Keep and stop start again once (`retryStart` → `beginRemoteStart`) with the answer, and a refusal asking only what was answered is reported, never asked twice. `--others` reaches `Run` beside `allowReplace` (`model.othersMode`) and answers only for the pinned row (`id == pinnedModel`). Pinned by `others_dialog_test.go`. **The start screen is wrapped, not only clipped** (`startingView`): a `Starting <id> — <stage> (<elapsed>)` line wider than the terminal is broken between the id and the stage.

> **Enter talks to the model server, never from `Update`** (`remote_start.go`; with no client configured the model phase either launches the agent natively, when `tui.Run`'s `native` parameter is set (no server configured at all and no `-M`/`-T`/`-F`, #615: `launchNative` builds the native model with a zero Gateway and says `agents.NativeNote` once the launch gate is past, so a declined gate says nothing; no client session, rotation or usage record), or sets the status `no model server is configured: set url and token_file under [model-server] in config.toml` and loads nothing). The table comes from the catalog (`models_client.go`: `phaseCatalog`, `fetchCatalogCmd` on a context esc, a superseding `F` and the program's end cancel; the eligible rows are kept by id in `m.wire`). Enter on a row (`chooseRemote`), or a `-M` pin once the table loads (the pin is the user's act): a blocked row sets its reason; a row `catalog.NeedsStart` says the server must start runs `beginRemoteStart`; any other launches (`launchRemote`). The start's command registers the client session first (`clientHold.hold`: the first model registers it and starts its heartbeat, later ones re-register the set; a refused register is a status note, never a refusal), then runs `modelclient.RunStart` with no `Answerer`, each poll's `JobView` arriving as a `startStageMsg` on the start's channel. The start screen is `startState` (`jobID`, `job`, `cancelSent`; R8): it shows the step or `queued behind another start or stop on the model server`, the client's elapsed time from the job's own progress and the job id. **Keys (T1, T5, T6):** esc and q are inert on this screen on purpose (the footer names only keys that act; `ctrl+c` is the way out); before the job has an id `ctrl+c` leaves wt (`ctrl+c quit`); once it has one `ctrl+c` detaches — back to the table with `detached — job ID keeps running on the model server`, the polls stopped, the job never cancelled, the model taken out of the client session — and `c` cancels it (`CancelJob` in a command); `c` is shown (`ctrl+c detach · c cancel job`) and acts exactly while `startState.canCancelJob` holds. `c` sets `cancelAsked`, which a refused cancel does not clear: a job that finishes anyway goes back to the table with `started <id>; launch cancelled (job <id>)` , drops the model from the client session and launches nothing. A detached or quit start's goroutine never blocks on its channel (its result is dropped when nothing will read it). A question in the job's problem (occupied, others, occupancy unknown) opens the replace or others dialog, its question from `modelapi.Problem` (`problemHeader`: occupants, each resident's `Label — Figure`, a line per family the server could not read, client session counts from the catalog; every piece flattened, M11), Cancel first; the answer starts again with `allow_replace`/`others`, and a refusal asking only what was answered is reported, never asked twice. A start that fails re-registers the client session without the model. A successful start, or a launch row, launches in two steps, the non-TUI `launchFilteredRemote`'s: **the server work first, behind the launching screen** (`phaseLaunching`, `launchPrep`, `prepRemoteLaunchCmd`: hold the model, read the server's non-native models for an agent that syncs them, build the agent against the gateway with `buildGatewayLaunch` over `agents.BuildLaunchCmdGateway`; `esc back · ctrl+c quit`, both call it off, ctrl+c marks it `quitting` so its result is dropped and no agent is built or run), then `handlePrepared` hands the built command to the run command (`runRecordAndWaitWith`), which records the rotation once the launch gate is past. A prep failure returns to the picker with `launch failed: …` and drops the model from the client session. The picker's rotation cursor and the non-TUI endpoint launch rotate over the same list: the launchable registered rows in the server's order (a start row is never the rotation's next). Without a terminal, an endpoint launch with several launchable models and no `-M` refuses (`pickerNeedsTTYError`); on a terminal it opens this picker. What the API path says under the alt screen (a launch row's register note, heartbeat notes) goes to `clientNotes`, printed with the route notes. **After the program**, `Run` stops waiting on a start the user quit out of (`settleRemoteStart`), and the post-exit flow (`printPendingSummaryAndSurveyTail` with `exitTailOf`) ends the client session — even when nothing launched — and prints the price notice from the catalog's pricing; there is no stop picker (the server stops an idle model after its grace).

> **A status too tall for the terminal has the screen** (`statusAlone`, `model_list.go`). The picker's status is wrapped to the columns the picker has (`modelFrames`, `tuilayout.WrapText`), never cut at the edge: an engine line ends in its reason, and a route line is wider than 80 columns (#209 was the same cut on the agent picker). The lines the wrapped status takes come from the margin, the header and the footer, in that order. A start's report can be long, and Bubble Tea drops a too-tall view's lines from the top, which is the status. When the frame as drawn is taller than the terminal, `phaseModelView` draws `tuilayout.MessageAlone` instead: the status wrapped to the width, its middle cut behind `… N lines not shown …` if it is still too tall, and `press a key to go back to the models`. The next key clears the status and does nothing else (ctrl+c quits). It is a measurement of the drawn frame, never a count of status lines, and it does not apply while the list's full help is open (that view may run over a short terminal, and `?` closes it) or while a filter is being typed. Pinned by `TestStatusAloneLeavesTheOtherScreensTheirKeys`.

There is no launch-time route check in the TUI (`checkLaunchRoute`, `tryEnsureModelRoute`, `phaseRouting` and the restart notice screen were deleted with Task 19): the model server writes and publishes the routes, and a session only builds the agent against its gateway. What the client path says under the alt screen (register and heartbeat notes) goes to `clientNotes` and is printed with `pendingRouteNotes` by `flushRouteNotes` once the terminal is released; `Run()` prints whatever is left after the program ends.

> **A slot-profile row is drawn from the profile, not from a model** (`modeltable.go`, `modelrows.go`, `layout.go`). The catalog load resolves each Usable profile of the agent against the server's rows (`catalog.ResolveSlotProfileWire`) and adds its row unless `-T`/`-F` is set or the catalog holds the `profile/` prefix. For a row with `Profile != nil`, `renderTable` adds no route decoration: FAMILY is `profile`, LOC is `ProfileRow.Loc`, COST is priced as the model of the slot the session rests on (`tableRow.costModel`: the default slot, or the sonnet slot for an `opusplan` default), and the in-use prefix is blank. While it is highlighted, `slotLine` replaces the mode line under the table (`modelFrames`): the filled slots, the slot the session rests on first and marked `*` (an `opusplan` default leads by name), whole entries only, the rest as `+N more`; on a blocked row, the reason. It adds no line to the frame.

Slot-profile launch (`slot_flow.go`): Enter on a profile row that is not blocked calls `beginRemoteSlotLaunch`, the twin of `cmd/wt-session`'s `launchSlotProfileRemote` (`TestSlotFlowParity`). Its prep, in a command behind the launching screen, reads the catalog once, resolves the profile against it, refuses a passthrough flag that would replace the slot mapping and holds every distinct slot model in the client session before any start; `handleRemoteSlotPrepared` then runs the start flow for the one local model when `catalog.NeedsStart` says so, and `launchRemoteSlot` builds the profile's command against the gateway (`buildSlotGatewayLaunch`) and returns `runSlotAndWaitCmd`, which applies through `slotApplier`, records, and runs; an applier error comes back as `slotAbortMsg`. No route is written and no proxy restarted or probed. A `-M profile/<name>` pin reaches the same launch from the catalog load, and a blocked pin routes back to the agent picker like any blocked row. The registry flow (`beginSlotLaunch`, `phaseSlot`, `settleSlotAfterStart`, `settleQuitSlot`) was deleted with Task 19.

> **A view must never be taller or wider than the terminal** (`internal/tuilayout`, which `wt config` uses too; `layout.go` holds the launcher's frames and keeps the lowercase names its code and tests use — `listFrame`, `fitTo`, `fitList`, `frameSides`, `listExtent`, `drawnFrame`, `clip` — as one-line forwarders). Bubble Tea drops a too-tall view's lines from the *top*, which is where every screen here puts its header and status line, and cuts a too-wide line at the right edge — so a mis-sized list does not clip the list, it silently removes the header, the status, or the last columns. Every list screen renders through a `listFrame` (`modelFrames`, `agentFrames`, `worktreeFrame`, `choiceFrame`); `fitTo` measures that same frame for the list's height (`fitList`) and side columns (`frameSides`), and measures the list itself (`listExtent`) for its least height and for the width at which bubbles really draws within the columns given — a bubbles list is not exactly as wide as it is told. That measuring happens only in `Update`: `View` picks its frame with `drawnFrame` — the fullest frame that leaves the list the height it already has, which is the one `fitTo` sized it for — and renders no probes. `Update` calls `fitLists` after every message, so a resize, a status appearing or clearing, or `?` expanding the help cannot leave a list stale; the standalone `pickModel` (`wt start`/`wt smoke` with no id) does the same through its own `frame()`/`fit()`, with its blocked-row notice as part of the frame. `fitTo` sizes through `tuilayout.SizeList`, which repeats `SetSize` until the page count, the rows per page and the page keys stop changing (at most three passes): bubbles computes rows-per-page from the pagination line and the help as they were *before* the call, and the expanded help is two rows taller once the page keys are enabled. Don't `SetSize` those lists anywhere else; add any new line to the frame, not to `View`; frames `clip` their own free text (status, path, hints) to the width. The agent picker's status is the exception: `agentFrames` wraps it between words (`tuilayout.WrapText`), because that screen is where a refused `-M` pin comes back to and its reason ends in what to do — for an mlx_lm_server pairing, the llmbench command with the pairing's target and draft, which a clip cut off at every width (#209 again). Its frames are, fullest first, path + wrapped status, wrapped status, path + unwrapped status, unwrapped status; the unwrapped form is for a terminal too short to hold the wrapped status above the list, and marks each cut line with an ellipsis (`cutLines`). `TestRefusedPairingPinShowsItsStartCommand` pins the command on screen at 80x24 and 120x50 and the fit at 40x12. The model picker's status is wrapped too (`modelFrames`, #275; see the note on a status too tall for the terminal, above); the worktree list's status line is still clipped. A test that sets state by hand must go through `Update` before measuring — or even reading — `View()`: a list still at its construction size is drawn in whichever frame leaves that much. A terminal too short for the model picker gives up its margin, then the agent/tag header, then the mode line and key hints — never the status or the table; a status too tall even for that sparest frame has the screen to itself (`statusAlone`). `TestEveryListPhaseFitsTheTerminal` measures every screen at widths 40/80/120 and heights 12/24/50.

> **The model table prices every row at one instant, read once per build** (`modelrows.go`). `buildRows` reads `tableInput.now`, or the package clock `pickerNow` when it is zero, once, and prices every row at that instant with `tableRow.pricedAt`: the one place a row is priced. It keeps the instant (`tableRow.at`), the price in force (`config.ModelCost.PriceAt`, a pure function: the clock is always an argument) and whether the model's price depends on the time (`ModelCost.TimePriced`). `tableRow.price` and `tableRow.timePriced` hand those back, so nothing that sorts or draws the table resolves a price again (`TestBuildRowsPricesEachRowOnce`): resolving checks each `cost.time_prices` row against the registry's rules and reads its timezone. A zone is read from the host's zone database once per run (`config.loadZone`, a cache; `TestAZoneIsReadFromDiskOnce`). `costCell` (the COST column), the `~` mark and the mode line's price read `tableRow.price`, never `Model.Cost`'s flat fields. Price does not affect row order. Nothing reads a clock while a screen is drawn: a resize or a cursor move redraws the same rows, so the prices of an open picker do not change under the cursor at a window boundary; a rebuild (`refreshTable`, after a start attempt) reads the clock again. A row built by hand in a test has a zero `at` and is priced flat. To draw a picker at a chosen instant a test sets `tableInput.now`, or replaces `pickerNow` for a whole program.
>
> **A time-priced row is marked, and the mark costs width** (`modeltable.go`). `costCell` puts `~` (`timePricedMark`) after the three numbers of a row whose model has a `cost.time_prices` row that is applied, and a table with such a row has the heading `COST (~ varies by time)` (`costLegend`) in place of `COST`. The heading is 23 characters and is used only when the column is at least that wide, which a marked cell of three prices (24) makes it, so the heading never makes a row wider. The table is still not the table it would be with no marked row, in two ways. (1) The mark makes the COST column one character wider, so every column after it needs one more column of list width: at the one width where 1D only just fitted, the marked table shows no 1D, and likewise for 7D and 30D, each at one width. (2) Where COST is the last column drawn, its heading is the end of the header, and `Columns.Fit` wants the header to clear the list's title bar by `tuilayout.TitleRoom` (3). A trailing `COST` is 4 characters and never the limit (the rows are), while the 23-character legend plus 3 is 26 against rows of 24: the marked table needs three columns more than a plain one before COST is drawn, so at three list widths it has no COST column where a table of single prices has one. Neither is a fit failure (a column is shown whole or not at all), and both are stated to the user in `docs/wt-cloud-sync.md`. The mode line is why (2) hides no price: the line under the launcher's table names the highlighted row's price (`modelItem.cost`, from `costNote`, placed by `remoteModeLine` in `modelFrames` beside the row's client-session count) whether or not the column is drawn. It adds no line, so the frames' heights are what they were. The price is on it whole or not at all, because `clip` cuts the footer at the edge with no ellipsis and a price cut there reads as another price: `remoteModeLine` is given the inner width, drops the session count when the two do not fit together, and drops the price when it does not fit alone. There is no LiteLLM mode to name: the model server routes. The mark is in front of the numbers there (`cost~`), where no cut can part it from them. The standalone picker (`wt start`, `wt smoke`) has no mode line and gets the column only.
>
> **The model table drops whole columns on a narrow terminal** (`modeltable.go`, `tuilayout.Columns`). The header and every row share one `tuilayout.Columns`; `tuilayout.FitTo` (what `fitTo` and the standalone `pickModel` call) finds it through the rows' `TableColumns()` and shows the columns that fit the list's width, giving up `colDropOrder` — 30D, 7D, 1D, COST, TIER, LOC, FAMILY; `unratedDropOrder`, with TIER first, in a table where every TIER cell is `-` — and never MODEL, STATUS or RUNNING. Nothing is rebuilt on a resize: rows redraw from the shared layout, so the inventory is not re-probed and the cursor, marker and filter survive. `modelItem.line` stays the *full* row and is the filter value, so a query still matches a hidden column. With everything shown the table is byte-for-byte the old one with the TIER column added after MODEL (`TestModelTableUnchangedWhenItFits`).

> **The tier is guidance, read once, never an error** (`modelrows.go`, `modeltable.go`, `layout.go`, `internal/tiers`). `buildRows` calls the `loadTiers` seam (`tiers.Load`: `MODELTIERS_OUT`, else `$XDG_CONFIG_HOME/local-ai/tiers.toml`, else `~/.config/local-ai/tiers.toml` — modeltiers' own rule) once per table and rates each row by `ProviderID` + `ModelName` (`tableRow.rate`); a slot-profile row rates each slot model instead (`tableRow.slotTiers`). A missing, unreadable or unparseable file is no ratings and no message. The TIER cell is `tiers.Entry.Cell(digits)`, with `digits` the widest `ScoreDigits` in the table so the scores right-align (`S44`, `Q 9`; no low-confidence mark, by the owner's choice). `Index.Rating` also returns an unrated entry that has an aligned score: its cell is the score with the code column blank (`  9`) and its note `unrated · score 9 (2 sources)`, since a weak score is guidance too. The slot line names rated slot models only (a bare number after a model name would read as part of it). The highlighted row's long form (`tiers.Entry.Notes`: `tier standard · score 44 (3 sources) · high confidence`, then shorter) is appended to the mode line by `remoteModeLine` after the session count and the price, the longest form that fits, so it never displaces either. `slotLine` puts each filled slot's short form (`tiers.Entry.Short`) after its model name and drops the tiers before it drops a slot. `tiers.IsolateForTest` in the `TestMain`s of `internal/tui` and `cmd/wt-session` points `MODELTIERS_OUT` at a file that does not exist; a test that wants ratings sets it with `t.Setenv` (`writeTiers`, `tier_column_test.go`).

> **`wt config` is a second Bubble Tea program** (`internal/configeditor`), with the same two rules. Its Models tab draws a `tuilayout.Columns` table through `modelsFrames` and is sized by `tuilayout.FitTo` after every message (`fitModels`), which then cuts the MODEL column — and with it the middle of the ids longer than it (`middleCut`) — when the three columns that are never dropped do not fit; `modelsFrames` gives up, in order, the blank lines, the selected row's path, table rows down to one, for a pairing row its target and draft (`modelsDetailLines(false)`; `TestPairingRowsFitTheTerminal`), the key hints and the id line (with the line for a malformed `fetch`/`draft` under it, `malformedLine`, in `config.Model.Malformed`'s phrases). The status is never given up: when it is so long that even the sparest frame is taller than the terminal, `modelsView` draws the tab bar and the status without the table, because Bubble Tea would otherwise drop the top of that very status. That screen, and the form's error when it has the screen to itself, is drawn by `tuilayout.MessageAlone` (`alone.go`): the key hint is always the last line, and a message taller than the terminal even so (one that ends with a long registry path) loses lines from its *middle*, behind one marker line that counts them (`… N lines not shown …`), so that its start and the end of the path stay on screen — never `lipgloss`'s `MaxHeight`, which cuts from the bottom with no mark (`TestMessageAloneCutsTheMiddleAndKeepsTheHint`, `TestALongRefusalKeepsItsHintAndThePathsEnd`; #318). A test that asserts on such a message sets the registry path's length with `newTabMachineAt`, not through `TMPDIR`. The table's title bar is styled by `tuilayout.StyleTableTitle`, the same call the launcher's tables make. A probe's rows can hold one id twice (a registry `Validate` refuses, listed so that it can be repaired): `applyModels` keeps the cursor by id and, among rows that share it, by where it stood. Free text is wrapped by `flow`, between words only (lipgloss also breaks at a hyphen, which is inside every model path; `flow` and `wrapText` are `tuilayout.Flow` and `tuilayout.WrapText`, which the launcher's agent picker wraps its status with too); the remove prompt wraps its text to the terminal's width, and where that makes it taller than the terminal `modelsRemoveView` gives up its two blank lines and then its closing sentence before the bottom is cut — never a line of the question or the path while those are left to give (`TestRemovePromptGivesUpLinesBeforeThePath`). The model form (`models_form.go`, hand-built on `bubbles/textinput` like the agent form) draws as many fields as the terminal has rows for, always including the focused one, with a marker row for the fields above and below (`formWindow`, `modelFormLayout`); its title wraps, a fixed value too long for its row loses its middle and an unfocused one its end. While the add form's cursor is on Provider, `modelFormLayout` puts one dim line above the key hints that names `wt model add mlx_lm_server <target> --draft <draft>` (`modelFormPairingHints`, a shorter spelling at 40 columns): the Provider choice does not offer mlx_lm_server and nothing else on the tab says where a pairing is added. The line is part of `foot`, so it is counted like the hints and costs the fields a row on a short terminal; it is left out beside an error and wherever it would leave the fields fewer than three rows (`TestAddFormPairingLineFitsTheTerminal`). Its Family field offers the registry's families as suggestions; the form accepts one itself — right, with the cursor at the end of the text, sets the field to the suggestion whole — and bubbles' own accept binding is off: bubbles v1.0.0 accepts wherever the cursor is, keeps the case of what was typed, and panics when a value is set after a suggestion matched; its previous-suggestion key (`ctrl+p`) leaves the index at -1 when nothing matches, which `CurrentSuggestion` then indexes with, so `updateModelForm` asks only when the match list is not empty and the index is not negative (`TestModelFormPrevSuggestionWithNoMatchDoesNotPanic`). A save runs in a command (`saveModelFormCmd`: `modeladmin.CheckAdd`, then the ollama lookup, then the write), and what it refuses is drawn over the hints: a `modeladmin.FieldError` moves the cursor to its field, any other refusal — an id the registry holds twice (`config.ErrModelAmbiguous`), a row whose `fetch` the writer will not write back, the one refusal the form adds `(fix the entry in <registry>)` to (`saveErrorText`, for a row that opened with `Row.Malformed` set; a refusal a field of the form repairs, such as a hand-written row with no family, names no file) — moves nothing, and one too long to leave the fields three rows (the focused field and the two markers) has the screen to itself until the next key (`errorAlone`), which only brings the form back: a form never draws one or two fields with nothing counting the rest. A saved form puts the cursor on its model when the re-probe lands (`selectID`) and marks the routes pending like a removal; `n`, `enter`, `d` and `r` typed while that probe is out add `probing providers...` to the status (`noteProbeOut`). A quit held for a registry write — a removal or a form's save — (`leave`, `quitPending`) goes through `quit` when the write is in, so agent edits made while it waited get the unsaved-changes prompt; edits already answered with "discard" are not asked about again (`discardHeld`, which a refused write undoes). A save-before-quit that fails brings the Agents tab forward (`showQuitSaveFailure`): `m.status` is drawn only there. The tab's load error is worded `config load error: `, not `registry: ` — the probe loads `config.toml` too. Nothing on the tab reads a file or dials a server in `Update`: the probe (`probeCmd`) and every registry write are commands, and a probe's result carries a generation number so that a late one cannot replace a later one's rows. A bubbles list sends its filter's result back as a message that does not name the list; every command either tab's list returns goes through `tagFilter`, and the result comes back as a `filterMatchesMsg` for the right one — an editor that drops it has a `/` that filters nothing. Both lists have bubbles' own quit keys off (`DisableQuitKeybindings`): `esc` is one of them, and the list's quit goes round the editor's. The tab reaches the machine only through `Options.Models` (`ModelsDeps`: load, probe, seeding environment, ollama lookup), which `cmd/wt-session` fills from its own seams and a test fills with a machine of its own. `TestModelsTabFitsTheTerminal` measures it at widths 40/80/120 and heights 12/24/50.

> **TTY required.** `WithAltScreen` opens `/dev/tty`; from a pipe/CI it fails with `could not open a new TTY`. Flag paths (`--version`, `wt rotate`) skip the TUI. `-W`/`--cwd` need a TTY only when `-A` or `-M` is omitted (command agents like `shell` launch directly with no model layer).

- **A model table is priced once, when it is built** (`modelrows.go`): `buildRows` reads one clock (`pickerNow`, or `tableInput.now`) and `tableRow.pricedAt` resolves each row's price in force (`config.ModelCost.PriceAt` over its `cost.time_prices` rows). The COST cell, the `~` mark and the mode line's price read `tableRow.price()` / `timePriced()`, never `Model.Cost`'s flat fields and never a clock, so an open picker's prices do not change at a window boundary. The rows are the ollama flow's `off-peak` one, the openrouter flow's `openrouter` ones (one per level of a schedule other than the dearest, which is the flat price) and any written by hand. The mark and the heading `COST (~ varies by time)` cost width (one usage column at one list width each; the COST column at three), and the mode line's price is whole or absent (`remoteModeLine`): read the two notes on them in this file before changing either. LiteLLM's route carries the flat price at every hour.


## The launch gate and other screens: new worktree, `wt cleanup`

One gate and two screens sit beside the launcher phases above (`internal/tui`).

- **The launch gate** (`launchgate.go`): the one question before a launch commits — `launchGate`, asked by the run commands (`launch.go`, `slot_flow.go`) at the commit point on the released terminal, over `internal/launchwarn` (`launchTarget` → `Collect` → `Check`; a pick from the unified list carries its row's PR, upstream and dirt facts into that target through `launchwarn.FromRow`, which maps the already-gathered row and probes nothing). No warnings and no creation is the one informational line `launching in <dir>` and no question — any pick with a directory states where it launches this way (a root pick instead carries the root warning into the one question; `--root` alone consents to it) — and the creation line of a pick that owes a worktree is the one informational line in its place. Any remaining warning is one default-yes `continue?` (skipped with no terminal: the warnings print and the launch proceeds, stdin never read), and a `no` ends the run with exit 3 and one line, `approval missing: declined; nothing was launched` (`errLaunchDeclined`; nothing created, claimed, recorded or run). A bare-branch, remote-only or typed-name pick that owes its worktree carries its owed creation (`launchCreation`: a `worktree.Plan` resolved read-only at the pick), stated in launchwarn's frozen creation wording and made only once the person continues — a creation failure after the continue travels out as the run's error (main's one `wt:` line, non-zero), never a quiet decline. A preset path (`prePath`) was answered in RunE's `confirmLaunch` already, so the gate speaks and asks nothing there and only claims — a root launch is asked at most once. Every launch claims the worktree the run lands in (`claimLaunch` → `rootclaim.HoldLaunch` on the run's directory — the root or a linked one; a zero-Dir target claims nothing), the release kept in `rootClaimRelease` and taken by `releaseRootClaim` when the agent exits; every claims failure is one `wt: note:`, never a refusal. Where the claim is written and released: [launch-flow.md](launch-flow.md#session-claims-internalsessionclaim-internalrootclaim).
- **New-worktree prompt** (`new_worktree.go`, `phaseNewWorktree`): the picker's "+ New worktree..." row. It never asks whether to create; Enter resolves the typed name read-only through `worktree.Resolve` and binds the owed creation to the launch (`launchCreation`, exactly like a bare-branch row — cmd/wt-session's `-W` rule decides which typed names owe one), so nothing exists until the commit point creates it with `Plan.Ensure` (nothing records the creation — the exit prompt's records died with it). The commit point runs `Plan.Ensure` for every typed name, owed or not (cmd/wt-session's `-W` runs it unconditionally, `main.go:551`): a reused worktree is the idempotent no-op that keeps the pick silent, an unregistered path is git's own error rather than a launch at a directory that is not a worktree. A declined gate leaves no branch, directory or worktree behind.
- **The row list and removal** (`cleanup_list.go`, `cleanup_confirm.go`, `rowtable.go`; `newRowList`, run for `wt cleanup` by `RunCleanupList` in manage mode): each row is ONE table line — `rowPrefix` (session digit, cursor, checkbox; prefix 4 in launch, 8 in manage) plus `rowLine` through the shared `tuilayout.Columns` (`newRowTable`: columns `WORKTREE BRANCH PR# DIFF IGN STATUS VERDICT`, rune-measured widths, DIFF and IGN right-aligned, PR# left-aligned free text, drop order `PR#`, `IGN`, `STATUS`, `DIFF` — the worktree, branch and verdict columns never drop; fitted to the list's width in `layout()` every frame), with the row's badges (`rowTags`: `dirty`, `upstream gone` on a row that is not proven, plus the root row's drift badge) trailing the line, and its verdict word (`verdictWord`: `safe`, `check`, `work`, `locked`) in the VERDICT cell. There are no headings: `cleanup.ListOrder` orders the rows — root first (a root the report does not mark Primary is found by its `primary_checkout` blocker), then local worktrees and branches together by display name, then the remote-only rows by display name; the order is stable across the facts→fill swap, so rows never jump under the cursor when details land. The row's verdict-shaped cells read `-` while `Pending` and its sentence and age live in the detail line for the highlighted row, which gains the dropped PR# column's `PR #N state` / `PR lookup unknown` (`prLine`) and the dropped DIFF column's `+N/-N · N ignored` (`diffLine`, whole or not at all). The table header is a dim line in the top block, with the filter/status lines above it; blank filler pins the bottom block (detail + footer) to the terminal's last line, and the give-up ladder is unchanged (report header, title, detail, footer last). A single step past either end of the row list wraps (`move(dir, 1)`; paging stops at the ends), the model selector and agent picker wrap through `InfiniteScrolling`. In manage mode `RunCleanupList` may receive a facts-only report with `RemoveFuncs.Fill`: `Init` dispatches it, `cleanupFillMsg` swaps through `fillGen` (spent by an `F` refetch or the post-run refresh) and applies the returned funcs. In launch mode the header leads with the root drift line (`rootDriftOf`); the manage list keeps it to the row's badge. Manage mode: a checkbox column, space ticks, `a` ticks every proven local row, enter opens the confirm screen, then a progress screen and the results, and `r` hands a row to `wt rescue`. Launch mode (no ticking): a first `+ New worktree…` item (enter or `n` emits `newWorktreeChosenMsg`), enter on any row emits `rowChosenMsg`. In both modes `i`, `x`, `d`, `o`, `r` and `R` open the row's **detail screen** (`detail.go`, `cleanupPhaseDetail`) and act nothing on the way in: `i` reads, and the second press of a row key runs the action the screen lists — `x` removes the highlighted row alone (the ticks never choose for it; enter's batch is the ticked rows), `d` also deletes its unmerged branch (a seed on the confirm), `o` deletes only its origin ref, `r` rescues it and `R` restores the root (`startRowAction`, `startRescue`, `startRestoreRoot`). The screen renders `detailBlock` (one renderer for `i` and for a single-row confirmation: identity, `Verdict` word and why, the local-only commits, uncommitted and ignored files from `RemoveFuncs.Detail` → `cleanup.ReadRowDetail`, and the preview's losses) and `detailActions` (one entry per action whose predicates hold, plus `esc`), both read off the update loop by `detailCmd` and applied by `detailLoadedMsg` (dropped when its `rowKey` is not the screen's row). `startRemovalOf` records whether the flow started on that screen (`confFromDetail`), so `cancelConfirm` goes back one step — the detail screen when it opened the confirm, the list for enter's batch. A confirmed run clears the screen (`confirmed`), the results and the refreshed list follow. `swapRemoveFuncs`' deferred funcs swap applies on a return to either rest, the list or the detail screen. **The footer** (`row_keys.go`) is the key legend: `rowKeys` lists the keys that work on the highlighted row from the handlers' own predicates (`cleanupLocked`, `originTarget`, `rescue.Offered`, `rootmove.Offered`, the wired `RemoveFuncs`), `fitHints` fits them to two lines at most (long wording, then short), and `layout()` drops it last of all; the title line is only the screen's name. `TestRowKeysMatchTheHandlers` holds footer and handlers together, so a new key goes in both. In manage mode `RunCleanupList` re-enters the list with a re-read report after `r` or `R` (the `RemoveFuncs.Program` seam); `cleanupLocked` locks a row for a hard stop, an `in_use` row or a remote row that is not a proven `origin` branch; a floor never locks a worktree or local branch. The words come from `internal/cleanup/present.go`; the screens never build a `removal.Item` themselves (the engine previews the rows and the confirm screen turns each preview into an item through `Confirmed` or `ConfirmedDeletingBranch`). Behavior and rules: [../../CLAUDE.md](../../CLAUDE.md#cleanup-classifier-and-removal-wt-cleanup-wt-remove) and [../wt-cleanup.md](../wt-cleanup.md).
