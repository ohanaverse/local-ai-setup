# wt TUI

Internals reference for `wt/`, reached from [`wt/CLAUDE.md`](../../CLAUDE.md). Backticked paths are relative to `wt/` unless they start with `../`.

## TUI (Go)

`internal/tui` is the Bubble Tea shell (`tea.WithAltScreen()`). Phases: worktree picker → agent+command picker → model picker → launch (plus the starting, routing, replace-confirm and ollama-warning screens). Each picker is skipped when its selection is already resolved (`prePath` from `-W`/`--cwd`/outside-repo, `-A`, `-M`; a pinned non-running local starts immediately). Every picker uses `ThemedListDelegate` — production code never uses `list.NewDefaultDelegate`.

Start-on-select (`start_flow.go`): Enter on a start row → `phaseStarting` (engine stage + elapsed; esc/q/ctrl+c cancels and the engine tears down what it spawned). **Once cancellation is draining, esc and q are ignored and only ctrl+c quits** — a mashed key can't orphan a half-started server, while a hung teardown still has an escape hatch. **From the routing stage on nothing can be cancelled** (`startState.pastCancel`, #275): the model is loaded, or the start has ended and only the proxy restart is left, so the screen names `[ctrl+c] quit wt` and no cancel, esc and q are ignored and ctrl+c quits — `phaseRouting`'s rule, down to the gap after the key: `tea.Quit` is a command, so the start's `startDoneMsg` can arrive before the `QuitMsg`, and that ctrl+c marks the start `quitting` (`startState.quitting`, on a copy, as `routingState.quitting` is) so `handleStartMsg` drops the result instead of launching; the state is kept, and `flushRouteNotesAfterRun` prints what the engine printed. That window used to be an instant; with the wait on the start's goroutine it is the 10 to 20 seconds of a proxy restart, and an esc there ended in `cancelled` over a model that was running and routed. A cancel pressed before that stage which the engine no longer honoured (it returns nil) ends in `started <id>; launch cancelled`, or in `<id> is not running: …` when the server was gone again after the proxy wait (#343, below). Success goes straight to `proceedToLaunch`; a cancel or ordinary failure rebuilds the table from a fresh inventory with the cursor kept. `*OccupiedError`/`*OccupancyUnknownError` → `phaseReplaceConfirm` (Cancel is the default; "Replace and start" re-issues with `AllowReplace`; `OccupiedError.Occupants` lists every model the start would stop or, on omlx, unload). The single-row auto-launch shortcut applies only to launch rows. **The engine prints into the flow, not onto the screen** (#258, #275). `runStart` hands the engine `lifecycle.Options.Out`, a `startOutput` (`start_output.go`: locked, at most 16 KiB, a line saying how much was dropped past that), so nothing a start prints reaches stderr under the alt screen: what omlx unloaded with its `(not predicted)`, `LiteLLM route not updated: …`, and the proxy restart's warnings. The start's goroutine waits for the proxy restart itself, after the engine returns and before it sends `startDoneMsg`, whose `out` is therefore the whole text; **`Update` waits for nothing in this flow**. After a start that failed that is `waitPendingRoutes()`. **A start the engine reported done is settled by the same goroutine with one call** (`settleStart`, a seam over `lifecycle.SettleStart`, #343, #349): the wait for the proxy, then one question to the provider's server, whether the model is still there, since that wait is where another terminal's `wt stop` lands, and after a `*lifecycle.StoppedError` the wait for the restart the check's route removal started. It is not `finishStart`'s to make: it waits, it is a request to a server and, when the server is gone, a `config.yaml` write that can wait for the file's lock. It is handed the start's `startOutput`, so the route removal's lines and its restart's warnings join the engine's, complete when the call returns. The error travels as `startDoneMsg.err`, so to `finishStart` a server that is gone is a failed start like any other: status `<id> is not running: …` under the start's lines, both recorded for the terminal when there are such lines (a start and a route removal that printed nothing, the ordinary case, leave the message on the status only, as any failed start does: `TestStartWhoseServerIsGoneAndPrintedNothingIsOnTheStatusOnly`), the table re-probed, no launch. **Order against the launch-time route check:** the confirmation comes first and decides whether that check runs at all. `proceedToLaunch` (and with it `checkLaunchRoute`, which since #275 also runs for a row this flow just started) is reached only from a start whose result has no error, so the check never writes back the route the confirmation has just removed — it would, because the table is not rebuilt in between and still shows the row as started. The start is settled for a cancel that lost too, which is about to be reported as `started <id>; launch cancelled`. The flow hands over the start's context as it is, and `lifecycle.SettleStart` drops its cancellation (`context.WithoutCancel`), since under a done context the probe settles nothing; when the server is gone there, the status is the `is not running` line, not `cancelled` (the cancel is not what stopped it). A start the user quit out of at the routing stage is still confirmed by its goroutine, and **`flushRouteNotesAfterRun` waits for that goroutine** (`settleQuitStart`: it reads the start's channel until it is closed, and prints `wt: waiting for the LiteLLM proxy restart…` once the wait has lasted `quitStartGrace`). `main`'s one `WaitPendingRoutes()` ends with the start's own restart, which is also what releases the goroutine's first wait, so without it the process left under the check: the dead model's route still in `config.yaml`, or `config.yaml` rewritten and the restart never run (and a `routeWG.Add` racing `main`'s `Wait`). Only a `quitting` start is waited for; the second ctrl+c while a cancel drains is the way out of a teardown that hangs and waits for nothing. The result is dropped with the rest (`quitting`), so a `*StoppedError` there launches nothing and shows no `is not running` line; what the check printed goes through the `startOutput` that `flushRouteNotesAfterRun` released before it waited, straight to the terminal (`TestQuitAtTheRoutingStageWaitsForTheStartToSettle`). Pinned by `start_confirm_test.go`. Whenever a restart is in flight when the engine returns (`routesPending`) the goroutine sends `StageRouting` itself first, so the screen reads `updating LiteLLM routes`, or `waiting for the LiteLLM proxy restart` while cancelling: after a start that failed or was cancelled that is only when it had already displaced a model, and after one that succeeded under a cancel it replaces the engine's own report of the stage, which goes through a context the cancel has ended and can be lost. **The start screen is wrapped, not only clipped** (`startingView`): a `Starting <id> — <stage> (<elapsed>)` line wider than the terminal is broken between the id and the stage, since the stage is the only reason the screen gives for a key that stopped working (`TestStartScreenSaysItsStageAtEveryWidth`). `statusNote` is that text as the status shows it, the engine's own lines without their `wt: `: on a failed or cancelled start they stand above the failure, one line each; and the text, when there is any, is also recorded verbatim in `pendingRouteNotes` with `wt: <failure>` under it, since a status the next key replaces cannot be the only record of the engine's lines (a start that printed nothing records nothing: its failure is on the status only). After a successful start, where the launch follows, the text joins `pendingRouteNotes` and is printed above the agent's output. If that launch fails the picker comes back, so `finishStart` also leaves the note in `model.startNote` and `launchSelected` puts it above `launch failed: …` (`withNote`); `proceedToLaunch` does the same above `no model selected` when the picker has no row left to launch, the one way back that never reaches `launchSelected`. Whichever of the two runs takes the note once and clears it, so a later launch from the same picker does not repeat it. A second ctrl+c while a cancel drains quits wt before the start reports: `flushRouteNotesAfterRun` then calls `startOutput.release`, which prints what was collected and sends every later write straight to stderr.

> **A status too tall for the terminal has the screen** (`statusAlone`, `model_list.go`). The picker's status is wrapped to the columns the picker has (`modelFrames`, `tuilayout.WrapText`), never cut at the edge: an engine line ends in its reason, and a route line is wider than 80 columns (#209 was the same cut on the agent picker). The lines the wrapped status takes come from the margin, the header and the footer, in that order. A start's report is two lines for every model omlx unloaded, and Bubble Tea drops a too-tall view's lines from the top, which is the status. When the frame as drawn is taller than the terminal, `phaseModelView` draws `tuilayout.MessageAlone` instead: the status wrapped to the width, its middle cut behind `… N lines not shown …` if it is still too tall, and `press a key to go back to the models`. The next key clears the status and does nothing else (ctrl+c quits). It is a measurement of the drawn frame, never a count of status lines, and it does not apply while the list's full help is open (that view may run over a short terminal, and `?` closes it) or while a filter is being typed. Pinned by `TestPickerFitsAStartReportOfAnyLength` at every supported size and by `TestStatusAloneLeavesTheOtherScreensTheirKeys`.

Launch-time route check (`checkLaunchRoute`, `start_flow.go`, #192): `proceedToLaunch` is the funnel every model launch passes through; `launchSelected` is the build-the-command-and-launch half (it never looks up a session — see Sessions). For a launch row whose route goes through LiteLLM (a row this flow just started included, since #275: its start writes the route, but a start whose route write failed still succeeds, and this check is what tries again; with the route there it changes nothing), `proceedToLaunch` calls `tryEnsureModelRoute` — the **non-blocking** form of the check — handing it a buffer of its own for everything the check prints (the retry and the restart's warnings go to the same buffer; nothing process-wide is redirected, so another operation's output cannot land in it). It runs on the update goroutine, so it may never wait: `lifecycle.EnsureModelRoute` bounds its config.yaml lock wait at 10s, and that wait on this goroutine freezes the screen with ctrl+c dead *before* its routing phase has been entered, which is the one screen built to cover a route wait. `TryEnsureModelRouteTo` instead attempts the flock once (an already-cancelled context is what a contended lock hits) and reports whether it got anywhere. **Free lock, unchanged** → record the notes, launch in the same `Update`: no screen, no wait. **Free lock, route written** → `phaseRouting`; **lock contended**, or **a cloud row that is missing and would have to be built** (the write defers the build, `Options.DeferMissingAdd`: resolving an `exec:` `secret_ref` runs its helper synchronously, #253) → `phaseRouting` too, with the outcome not yet known. Either way the rest is in a command: `routingState.settle` re-runs the check through `ensureModelRoute` when the first attempt reported `done == false` (the one place the blocking form is reached from this flow), then calls `waitPendingRoutes()` and only then reads the buffer, all before its `routeDoneMsg` exists; the handler only sizes the model list, records the notes and calls `launchSelected`. The message is dropped when stale (by run id) and when the check is `quitting`. `phaseRouting` owns the keyboard: only ctrl+c does anything — it quits wt and sets `routingState.quitting`, because `tea.Quit`'s `QuitMsg` returns through the message channel and a `routeDoneMsg` landing first would otherwise launch an agent after the user quit. The write is done and the restart cannot be cancelled, so the view advertises no cancel. The captured text goes to `pendingRouteNotes` (`launch.go`) and nowhere else — not to the status line: the launch follows at once, so the only picker screen the user can land on next is the one a failed launch returns to, whose status is that failure (`proceedToLaunch` clears the status at the start of every attempt); `runAndWaitCmd` prints the notes to stderr the moment it releases the terminal, and `Run()` prints whatever is left after the program ends (`flushRouteNotesAfterRun`, which first settles a check the user quit out of with ctrl+c, printing `wt: waiting for the LiteLLM proxy restart…` when that wait is still ahead). The start flow waits for the restart too, but on the start's own goroutine (`runStart`), never in `Update`.

> **A view must never be taller or wider than the terminal** (`internal/tuilayout`, which `wt config` uses too; `layout.go` holds the launcher's frames and keeps the lowercase names its code and tests use — `listFrame`, `fitTo`, `fitList`, `frameSides`, `listExtent`, `drawnFrame`, `clip` — as one-line forwarders). Bubble Tea drops a too-tall view's lines from the *top*, which is where every screen here puts its header and status line, and cuts a too-wide line at the right edge — so a mis-sized list does not clip the list, it silently removes the header, the status, or the last columns. Every list screen renders through a `listFrame` (`modelFrames`, `agentFrames`, `worktreeFrame`, `choiceFrame`); `fitTo` measures that same frame for the list's height (`fitList`) and side columns (`frameSides`), and measures the list itself (`listExtent`) for its least height and for the width at which bubbles really draws within the columns given — a bubbles list is not exactly as wide as it is told. That measuring happens only in `Update`: `View` picks its frame with `drawnFrame` — the fullest frame that leaves the list the height it already has, which is the one `fitTo` sized it for — and renders no probes. `Update` calls `fitLists` after every message, so a resize, a status appearing or clearing, or `?` expanding the help cannot leave a list stale; the standalone `pickModel` (`wt start`/`wt smoke` with no id) does the same through its own `frame()`/`fit()`, with its blocked-row notice as part of the frame. `fitTo` sizes through `tuilayout.SizeList`, which repeats `SetSize` until the page count, the rows per page and the page keys stop changing (at most three passes): bubbles computes rows-per-page from the pagination line and the help as they were *before* the call, and the expanded help is two rows taller once the page keys are enabled. Don't `SetSize` those lists anywhere else; add any new line to the frame, not to `View`; frames `clip` their own free text (status, path, hints) to the width. The agent picker's status is the exception: `agentFrames` wraps it between words (`tuilayout.WrapText`), because that screen is where a refused `-M` pin comes back to and its reason ends in what to do — for an mlx_lm_server pairing, the llmbench command with the pairing's target and draft, which a clip cut off at every width (#209 again). Its frames are, fullest first, path + wrapped status, wrapped status, path + unwrapped status, unwrapped status; the unwrapped form is for a terminal too short to hold the wrapped status above the list, and marks each cut line with an ellipsis (`cutLines`). `TestRefusedPairingPinShowsItsStartCommand` pins the command on screen at 80x24 and 120x50 and the fit at 40x12. The model picker's status is wrapped too (`modelFrames`, #275; see the note on a status too tall for the terminal, above); the worktree list's status line is still clipped. A test that sets state by hand must go through `Update` before measuring — or even reading — `View()`: a list still at its construction size is drawn in whichever frame leaves that much. A terminal too short for the model picker gives up its margin, then the agent/tag header, then the mode line and key hints — never the status or the table; a status too tall even for that sparest frame has the screen to itself (`statusAlone`). `TestEveryListPhaseFitsTheTerminal` measures every screen at widths 40/80/120 and heights 12/24/50.

> **The model table prices every row at one instant, read once per build** (`modelrows.go`). `buildRows` reads `tableInput.now`, or the package clock `pickerNow` when it is zero, once, and prices every row at that instant with `tableRow.pricedAt`: the one place a row is priced. It keeps the instant (`tableRow.at`), the price in force (`config.ModelCost.PriceAt`, a pure function: the clock is always an argument) and whether the model's price depends on the time (`ModelCost.TimePriced`). `tableRow.price` and `tableRow.timePriced` hand those back, so nothing that sorts or draws the table resolves a price again (`TestBuildRowsPricesEachRowOnce`): resolving checks each `cost.time_prices` row against the registry's rules and reads its timezone, and the sort asks for a row's price twice per comparison. A zone is read from the host's zone database once per run (`config.loadZone`, a cache; `TestAZoneIsReadFromDiskOnce`). `rowCostKey` (the cost sort, and with it the default selection) and `costCell` (the COST column) both read `tableRow.price`, never `Model.Cost`'s flat fields. Nothing reads a clock while a screen is drawn: a resize or a cursor move redraws the same rows, so the prices and the order of an open picker do not change under the cursor at a window boundary (`TestAnOpenPickerKeepsThePricesItOpenedWith`); a rebuild (`refreshTable`, after a start attempt) reads the clock again. A row built by hand in a test has a zero `at` and is priced flat. To draw a picker at a chosen instant a test sets `tableInput.now`, or replaces `pickerNow` for a whole program (`TestModelPickerWithTimePricedModelsFitsTheTerminal`).
>
> **A time-priced row is marked, and the mark costs width** (`modeltable.go`). `costCell` puts `~` (`timePricedMark`) after the three numbers of a row whose model has a `cost.time_prices` row that is applied, and a table with such a row has the heading `COST (~ varies by time)` (`costLegend`) in place of `COST`. The heading is 23 characters and is used only when the column is at least that wide, which a marked cell of three prices (24) makes it, so the heading never makes a row wider. The table is still not the table it would be with no marked row, in two ways. (1) The mark makes the COST column one character wider, so every column after it needs one more column of list width: at the one width where 1D only just fitted, the marked table shows no 1D, and likewise for 7D, 30D and SURVEY, each at one width. (2) Where COST is the last column drawn, its heading is the end of the header, and `Columns.Fit` wants the header to clear the list's title bar by `tuilayout.TitleRoom` (3). A trailing `COST` is 4 characters and never the limit (the rows are), while the 23-character legend plus 3 is 26 against rows of 24: the marked table needs three columns more than a plain one before COST is drawn, so at three list widths it has no COST column where a table of single prices has one. Neither is a fit failure (a column is shown whole or not at all, and `TestModelPickerWithTimePricedModelsFitsTheTerminal` holds both pickers to every size), and both are stated to the user in `docs/wt-cloud-sync.md`. The mode line is why (2) hides no price: the line under the launcher's table names the highlighted row's price (`modelItem.cost`, from `costNote`, joined to the `LiteLLM: …` text by `modeLine` in `modelFrames`) whether or not the column is drawn. It adds no line, so the frames' heights are what they were. The price is on it whole or not at all, because `clip` cuts the footer at the edge with no ellipsis and a price cut there reads as another price: `modeLine` is given the inner width, drops the mode text when the two do not fit together, and drops the price when it does not fit alone (`TestModelPickerNamesTheHighlightedModelsPrice` pins it at 80x24, 40x12 and 120x50, with LiteLLM on and off). The mark is in front of the numbers there (`cost~`), where no cut can part it from them. The standalone picker (`wt start`, `wt smoke`) has no mode line and gets the column only.
>
> **The model table drops whole columns on a narrow terminal** (`modeltable.go`, `tuilayout.Columns`). The header and every row share one `tuilayout.Columns`; `tuilayout.FitTo` (what `fitTo` and the standalone `pickModel` call) finds it through the rows' `TableColumns()` and shows the columns that fit the list's width, giving up `colDropOrder` — SURVEY, 30D, 7D, 1D, COST, LOC, FAMILY — and never MODEL, STATUS or RUNNING. Nothing is rebuilt on a resize: rows redraw from the shared layout, so the inventory is not re-probed and the cursor, marker and filter survive. `modelItem.line` stays the *full* row and is the filter value, so a query still matches a hidden column. With everything shown the table is byte-for-byte the old one (`TestModelTableUnchangedWhenItFits`).

> **`wt config` is a second Bubble Tea program** (`internal/configeditor`), with the same two rules. Its Models tab draws a `tuilayout.Columns` table through `modelsFrames` and is sized by `tuilayout.FitTo` after every message (`fitModels`), which then cuts the MODEL column — and with it the middle of the ids longer than it (`middleCut`) — when the three columns that are never dropped do not fit; `modelsFrames` gives up, in order, the blank lines, the selected row's path, table rows down to one, for a pairing row its target and draft (`modelsDetailLines(false)`; `TestPairingRowsFitTheTerminal`), the key hints and the id line (with the line for a malformed `fetch`/`draft` under it, `malformedLine`, in `config.Model.Malformed`'s phrases). The status is never given up: when it is so long that even the sparest frame is taller than the terminal, `modelsView` draws the tab bar and the status without the table, because Bubble Tea would otherwise drop the top of that very status. That screen, and the form's error when it has the screen to itself, is drawn by `tuilayout.MessageAlone` (`alone.go`): the key hint is always the last line, and a message taller than the terminal even so (one that ends with a long registry path) loses lines from its *middle*, behind one marker line that counts them (`… N lines not shown …`), so that its start and the end of the path stay on screen — never `lipgloss`'s `MaxHeight`, which cuts from the bottom with no mark (`TestMessageAloneCutsTheMiddleAndKeepsTheHint`, `TestALongRefusalKeepsItsHintAndThePathsEnd`; #318). A test that asserts on such a message sets the registry path's length with `newTabMachineAt`, not through `TMPDIR`. The table's title bar is styled by `tuilayout.StyleTableTitle`, the same call the launcher's tables make. A probe's rows can hold one id twice (a registry `Validate` refuses, listed so that it can be repaired): `applyModels` keeps the cursor by id and, among rows that share it, by where it stood. Free text is wrapped by `flow`, between words only (lipgloss also breaks at a hyphen, which is inside every model path; `flow` and `wrapText` are `tuilayout.Flow` and `tuilayout.WrapText`, which the launcher's agent picker wraps its status with too); the remove prompt wraps its text to the terminal's width, and where that makes it taller than the terminal `modelsRemoveView` gives up its two blank lines and then its closing sentence before the bottom is cut — never a line of the question or the path while those are left to give (`TestRemovePromptGivesUpLinesBeforeThePath`). The model form (`models_form.go`, hand-built on `bubbles/textinput` like the agent form) draws as many fields as the terminal has rows for, always including the focused one, with a marker row for the fields above and below (`formWindow`, `modelFormLayout`); its title wraps, a fixed value too long for its row loses its middle and an unfocused one its end. While the add form's cursor is on Provider, `modelFormLayout` puts one dim line above the key hints that names `wt model add mlx_lm_server <target> --draft <draft>` (`modelFormPairingHints`, a shorter spelling at 40 columns): the Provider choice does not offer mlx_lm_server and nothing else on the tab says where a pairing is added. The line is part of `foot`, so it is counted like the hints and costs the fields a row on a short terminal; it is left out beside an error and wherever it would leave the fields fewer than three rows (`TestAddFormPairingLineFitsTheTerminal`). Its Family field offers the registry's families as suggestions; the form accepts one itself — right, with the cursor at the end of the text, sets the field to the suggestion whole — and bubbles' own accept binding is off: bubbles v1.0.0 accepts wherever the cursor is, keeps the case of what was typed, and panics when a value is set after a suggestion matched; its previous-suggestion key (`ctrl+p`) leaves the index at -1 when nothing matches, which `CurrentSuggestion` then indexes with, so `updateModelForm` asks only when the match list is not empty and the index is not negative (`TestModelFormPrevSuggestionWithNoMatchDoesNotPanic`). A save runs in a command (`saveModelFormCmd`: `modeladmin.CheckAdd`, then the ollama lookup, then the write), and what it refuses is drawn over the hints: a `modeladmin.FieldError` moves the cursor to its field, any other refusal — an id the registry holds twice (`config.ErrModelAmbiguous`), a row whose `fetch` the writer will not write back, the one refusal the form adds `(fix the entry in <registry>)` to (`saveErrorText`, for a row that opened with `Row.Malformed` set; a refusal a field of the form repairs, such as a hand-written row with no family, names no file) — moves nothing, and one too long to leave the fields three rows (the focused field and the two markers) has the screen to itself until the next key (`errorAlone`), which only brings the form back: a form never draws one or two fields with nothing counting the rest. A saved form puts the cursor on its model when the re-probe lands (`selectID`) and marks the routes pending like a removal; `n`, `enter`, `d` and `r` typed while that probe is out add `probing providers...` to the status (`noteProbeOut`). A quit held for a registry write — a removal or a form's save — (`leave`, `quitPending`) goes through `quit` when the write is in, so agent edits made while it waited get the unsaved-changes prompt; edits already answered with "discard" are not asked about again (`discardHeld`, which a refused write undoes). A save-before-quit that fails brings the Agents tab forward (`showQuitSaveFailure`): `m.status` is drawn only there. The tab's load error is worded `config load error: `, not `registry: ` — the probe loads `config.toml` too. Nothing on the tab reads a file or dials a server in `Update`: the probe (`probeCmd`) and every registry write are commands, and a probe's result carries a generation number so that a late one cannot replace a later one's rows. A bubbles list sends its filter's result back as a message that does not name the list; every command either tab's list returns goes through `tagFilter`, and the result comes back as a `filterMatchesMsg` for the right one — an editor that drops it has a `/` that filters nothing. Both lists have bubbles' own quit keys off (`DisableQuitKeybindings`): `esc` is one of them, and the list's quit goes round the editor's. The tab reaches the machine only through `Options.Models` (`ModelsDeps`: load, probe, seeding environment, ollama lookup), which `cmd/wt` fills from its own seams and a test fills with a machine of its own. `TestModelsTabFitsTheTerminal` measures it at widths 40/80/120 and heights 12/24/50.

> **TTY required.** `WithAltScreen` opens `/dev/tty`; from a pipe/CI it fails with `could not open a new TTY`. Flag paths (`--version`, `wt rotate`) skip the TUI. `-W`/`--cwd` need a TTY only when `-A` or `-M` is omitted (command agents like `shell` launch directly with no model layer).
